## 1. 解耦边界

| 原计划里的条目 | 本版处理 | 理由 |
|---|---|---|
| `PermissionEngine.grant` 收权 | ✅ **本版做**（I3 唯一内容） | 它堵的是"拿到 Bean 就能自我授权"，与认证机制无关，可独立验证 |
| 凭据映射不到 `ACTIVE` Agent 即 403 | ⛔ **拆出**（记作 I3-b） | 需要令牌名与档案绑定，属认证策略；与收权混做会让 I3 的验证结果不可解释 |
| 令牌轮换 / 吊销 / scope | ⛔ 拆出 | 属认证侧能力，与 I3 无耦合 |
| 审计 HMAC + 外锚 | ✅ 独立为 I4，I3 验证通过后再做 | 两者都触及"证据链"，但同时改会让回归失败时无法定位 |

**不做并行**：I3 提交并跑完四个模块回归 → 才开始 I4。

## 2. grant 收权：具体范围

**被收掉的**（`com.towndemontower.core.executor.PermissionEngine`）：
`grant(String, String...)`、`revoke(String, String...)`、`revokeAll(String)` → 包内可见。
包外再写 `engine.grant(...)` **编译不过**（`DemoRunner` 与 5 个测试当场报错，已改为经端口）。

**保留可读的**：`permissionsOf`、`isGranted`、`assertAllowed`、`assertAllowedByAgent` —— 鉴权判断本身不受影响。

**新的唯一写入口**：`PermissionProvisioner`

| 方法 | 语义 |
|---|---|
| `grant(agentId, perms...)` | 追加授予 |
| `grant(agentId, Collection)` | 同上（集合重载） |
| `revoke(agentId, perms...)` | 精确回收，返回实际移除数 |
| `revokeAll(agentId)` | 整员回收，返回实际移除数 |
| `replace(agentId, perms)` | 覆盖式授予（先回收再授予），改档/换角色用 |
| `actor()` | 授权主体标识，写进审计 |

**审计**：真正改变状态时写 `PERMISSION_GRANTED` / `PERMISSION_REVOKED` /
`PERMISSION_REVOKED_ALL` / `PERMISSION_REPLACED`，payload 形如
`actor=starter-wiring|agent=AGT-0001|fs:write`。空授予、回收 0 条不写，避免噪声。

**诚实边界**：这是**编译期收口**，不是内核强制。反射、同包类、替换 Bean 仍可绕过
（docs/17 已列）。它消除的是"默认路径"与"顺手提权"，并把每次变更变成显式且留痕的动作。

## 3. I4：审计 HMAC + 外锚

### 3.1 算法：SHA-256 → HMAC-SHA256

`AuditCrypto`（新增）统一链摘要：

- 密钥只读环境变量 `TOWNDEMONTOWER_AUDIT_KEY`，强度规则复用 `SecretPolicy`
  （与门禁密钥同一套：≥32 字符、≥12 种字符、占位值黑名单）；
- 有密钥 → HMAC-SHA256；无密钥 → **退化**为 SHA-256 并保留旧行为（不阻断启动）；
- 两者输出都是 64 位十六进制，长度一致，不因模式不同而暴露差异。

**为什么必须换**：SHA-256 链只能回答"有没有被改"。攻击者拿到日志后可以逐条改写 payload、
重算 hash、连 prevHash 一起修正，`verifyChain()` 仍返回 true。没有密钥算不出 HMAC，
这类"整链重算"当场失效——`V19AuditHardeningTest` 里有一段**对照实验**：
同样一份伪造链，无密钥时被接受、有密钥时被拒。

### 3.2 外锚：挡截断与整段替换

链内哈希对"删掉最后几条"完全无感，因为剩下的部分依然自洽。`AuditAnchor` 在日志同级
写 `<file>.anchor`：

```
records=<总记录数>	hash=<末条 hash>	mac=<HMAC(key, records|hash)>
```

| 攻击 | 谁发现 |
|---|---|
| 改某条 payload | 链内哈希（与 v1.8 相同） |
| 删尾部若干条 | 锚点条数 > 实际条数 → 启动拒绝 |
| 整段替换成另一份"自洽"日志 | 末条哈希与锚点不符 |
| 连锚点一起改 | 锚点 MAC 不匹配 |

写入时机：**每条记录追加后立即更新**（原子替换）。代价是每条审计 2 次写盘，
换来"任意时刻崩溃，锚点都不落后于日志"。这个取舍写在代码注释里，不藏着。

### 3.3 升级兼容

- 旧日志是用 SHA-256 算的：校验时先按当前密钥算，不匹配再按 SHA-256 算一次，
  通过即认作旧段（继续放行，不判篡改）；
- 旧锚点 `mac=-`（无密钥时代）：接受，并在初始化时用当前密钥重写一份带 MAC 的锚点；
- 因此"先上线、后配密钥"不会把历史日志锁死。

## 4. 完成标准

### I3（全部满足才算完成）

1. `PermissionEngine` 的 public 方法表里**没有** `grant` / `revoke` / `revokeAll`（反射断言，3+2 项）；
2. 包外直调 `grant` 编译失败（`DemoRunner`、`CoreTest`、`V12`、`V15`、`V16`、`StarterDemo`、`AgentAccessTest` 均已迁移）；
3. 端口行为与原语义一致：追加 / 精确回收 / 整员回收 / 覆盖 / 空入参无副作用（22 项断言）；
4. 经端口变更留下带 `actor` 的审计，空操作不写，未挂审计的端口不写（8 项）；
5. `permissionsOf` 返回不可变副本，读接口保持 public（4 项）；
6. 四模块回归全绿，且**没有放松任何既有断言**。

### I4（全部满足才算完成）

1. 有密钥时链摘要走 HMAC-SHA256，且与 SHA-256 结果不同（3 项）；
2. 伪造"整链重算"在 HMAC 模式下 `verifyChain()` 为 false，无密钥对照为 true（2 项）；
3. 无密钥时退化为 SHA-256：正常链可验、单点篡改可发现、`mode()` 如实报告（4 项）；
4. 外锚随写随更新，重启后条数一致，继续写不破坏一致性（5 项）；
5. 删尾记录 → 重启拒绝且原因指向"截断"（3 项）；
6. 改内容 / 改锚点 MAC / 伪造锚点 → 重启拒绝（4 项）；
7. 旧 SHA-256 日志 + 新密钥可正常打开并继续写，锚点自动升级为带 MAC（5 项）；
8. 自检新增 `AUDIT_KEY_MISSING`(WARN)，不因缺密钥而阻止启动。

## 6. 已知代价与未覆盖

- **每条审计多一次写盘**（锚点）。高频审计场景需要改成"批量锚点"（每 N 条或每 T 秒），
  届时会牺牲"最后 N 条被截断可见"这一点，需要重新权衡。
- **无密钥仍可运行**：`AUDIT_KEY_MISSING` 只是 WARN。若要强约束，可把 severity 提到
  CRITICAL，代价是所有未配密钥的接入方将无法启动。
- **锚点与日志同机**：能改日志的人通常也能删锚点（删掉后按"首次初始化"重建）。
  真正的防线是把锚点推到异地（对象存储 / 另一台主机），本版未做。
- **`PermissionProvisioner` 是 public 工厂**：显式调用 `of(engine)` 仍可获得写能力。
  收权解决的是"无意/顺手"，不是"蓄意"。要更强需引入可信第三方签发的授权凭据。
