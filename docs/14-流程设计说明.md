# 流程设计说明：固定流程 + 可插拔策略（v1.4 现状）

> **结论**：当前实现是**固定流程（固化管线）**，不是可编排流程。
> 可变的只有"每个环节用哪个实现"和"每个工具声明什么元数据"，
> **环节的集合、顺序、依赖关系在代码里写死**，运行期无法增删节点或改变走向。
> 设计面向**个人使用（单人 + 单 Agent 串行）**；团队协作所需的地基已具备，但闭环尚未补齐。

本文所有结论均以源码为准，关键位置在文末「证据索引」。

---

## 1. 三层结构：哪些固定、哪些可变

必须先区分三件容易混为一谈的事：

| 层 | 内容 | 可变性 | 变更方式 |
|---|---|---|---|
| **① 执行管线（拓扑）** | 10 个治理环节及其顺序 | **完全固定** | 只能改源码重编译；无配置项、无扩展点 |
| **② 业务生命周期** | 模式状态机、任务状态机 | **固定** | 转换表硬编码在构造器里；非法转换直接抛异常 |
| **③ 策略与参数** | 各环节的实现类、工具元数据、属性配置 | **有限可变** | 换 Bean 实现 / 加注解 / 改 properties |

一句话概括：**骨架焊死，肌肉可换。**

```
                         ┌─ ① 拓扑：这 10 个环节，这个顺序，不能少一个 ─┐
请求 → Audit → ModeToolPolicy → IntentFormat → Schema → Capability
     → Permission → RiskGate → TaintCheck → Snapshot → Sandbox → 真实方法
                         └─ ③ 每一环的"实现"可替换（策略层） ─────────┘
```

## 2. 固定流程：10 个阶段与不可更改的顺序

### 2.1 阶段清单（外 → 内）

| # | 环节 | 职责 | 拒绝时的错误码 |
|---|---|---|---|
| 1 | `AuditDecorator` | 记录每一次调用与结果，**任何分支（含异常）都落审计哈希链** | —（永远执行） |
| 2 | `ModeToolPolicyDecorator` | 模式白名单：当前模式是否允许使用该工具 | `MODE_TOOL_NOT_ALLOWED` |
| 3 | `IntentFormatDecorator` | 意图格式与置信度：置信度过低要求补充信息；把"建议"类表述拒掉 | `INTENT_FORMAT_INVALID` / `NEED_MORE_INFO` |
| 4 | `SchemaDecorator` | 必填参数与未知工具校验 | `SchemaValidationException` |
| 5 | `CapabilityDecorator` | 能力范围校验 | `CapabilityException` |
| 6 | `PermissionDecorator` | RBAC：`agentId` 是否持有该工具所需权限 | `PERMISSION_DENIED` |
| 7 | `RiskGateDecorator` | 风险分级裁决：R0/R1 放行，R2 转人工审批，R3 直接拒绝 | `PENDING_APPROVAL` / `R3_DENIED` |
| 8 | `TaintCheckDecorator` | 污染检查：会话读过不可信来源后，禁止写/外发 | `TAINTED_WRITE_BLOCKED` |
| 9 | `SnapshotDecorator` | 有副作用的工具执行前留快照（可回滚） | `SNAPSHOT_FAILED` |
| 10 | `SandboxedToolExecutor` | 链尾：交给沙箱策略（进程级 / Docker 容器级）执行真实方法 | `SANDBOX_UNAVAILABLE` |

### 2.2 为什么这个顺序改不了

顺序不是随意排的，每一步都依赖前一步的结论。**任意两步交换都会产生安全漏洞或误判**：

| 顺序约束 | 如果调换会怎样 |
|---|---|
| Audit **必须最外** | 放到内层，则被前置环节拒绝的调用不会留痕——"谁试图干了什么"这件事丢失，审计链失去追责价值 |
| Mode **在 Schema 之前** | 先校验参数再看模式，攻击者可以用"参数齐全但该模式不允许的工具"试探系统边界，返回的报错还会泄露工具签名 |
| Permission **在 RiskGate 之前** | 先做风险裁决再查权限，R2 会先给无权限者开一张审批单——等于用审批流程替代了权限校验 |
| Snapshot **必须在 Sandbox 之前** | 快照是"写之前的现场"，放到执行之后就只能叫"事后记录"，无法回滚 |
| TaintCheck **在 Snapshot/Sandbox 之前** | 污染会话若先落快照再被拒，会留下无意义的快照噪声，且真实写操作可能已部分发生 |

### 2.3 不可跳过的环节

代码层面**没有任何"跳过某环节"的能力**：`ExecutorFactory.buildDefault` 逐层 `new` 出固定链，没有 `withXxx(false)`、没有条件装配、没有链定义文件。

唯一的"事实跳过"是**策略层降级**——传入一个空实现让环节恒放行：

| 想跳过的环节 | 实际做法 | 代价 |
|---|---|---|
| 风险闸门 | 传入恒放行的 `RiskGate` 实现 | 审计里仍记为"已检查"，实际没裁决 |
| 审批 | `ApprovalPolicy` 恒返回 `APPROVED` | R2 不再阻塞 |
| 模式白名单 | `ModeToolPolicy.allowedTools()` 返回全集 | 三模式隔离失效 |
| 权限 | `PermissionEngine` 不 grant 任何权限（反向：全拒绝） | — |

这类降级**改变了治理语义，但没有改变拓扑**——顺序还在，只是每步都放行。这是"关掉安检门"，不是"重新设计动线"。

### 2.4 业务生命周期也是固定的

**模式状态机**（3 条转换，硬编码）：

```
ARCHITECT_PLANNING ──PLAN_APPROVED──► DEV_EXECUTION ──ENTER_AUDIT──► AUDIT_REVIEWING
        ▲                                                                    │
        └────────────────────────── REPLAN ──────────────────────────────────┘
```

> **刻意的强制返工**：代码里**没有** `AUDIT_REVIEWING → DEV_EXECUTION` 的直连。
> 审计态发现问题必须先回到规划态重排，不允许"边审边改"。这是本项目最重要的一条流程约束。

**任务状态机**（7 条转换，硬编码）：

```
PENDING ──INIT──► CODING ──PLAN_APPROVED──► EXECUTING ──DONE──► DONE
                    │                          │  ▲
                    │ EMERGENCY_STOP           │  │ RESUME
                    └──────────► PAUSED ◄──────┘  │
                                   └──────────────┘
                    （EXECUTING 亦可 EMERGENCY_STOP → PAUSED）
```

两个状态机与执行管线**互相独立**：管线管"一次调用能不能过"，状态机管"一个任务走到哪一步"。
三者都不可配置，非法转换抛 `ModeTransitionInvalidException` / `IllegalTransitionException` 并留审计。

## 3. 可配置的部分：范围与方式

### 3.1 工具元数据（声明式，最常用）

给方法加 `@AgentSkill`（或直接注册 `SkillDescriptor`）即可声明**该工具**的治理属性：

| 注解属性 | 默认 | 影响 |
|---|---|---|
| `name` | 必填 | 工具在 `SkillRegistry` 的 key |
| `risk` | `R2` | **决定审批路径**：R0/R1 放行、R2 转审批、R3 拒绝；未知默认 R2（保守） |
| `requiredPerms` | `{}` | RBAC 需要的权限，随注册授予配置的 agent |
| `capabilities` | `{}` | 能力范围 |
| `requiredArgs` | `{}` | Schema 必填参数（与形参名对应） |
| `sideEffect` | `true` | 是否触发快照 |
| `sandbox` | `ephemeral` | `read-only` / `ephemeral` / `none` |
| `confidence` | `1.0` | 低于阈值要求补充信息 |
| `reason` / `expectedEffect` / `rollbackHint` | 空 | 审计与人工审批的上下文 |

**可配置的是"每个工具的性质"，不是"工具的编排"。** 加一个工具 = 在既有管线上多一个可通过检查的对象，不会新增环节。

### 3.2 环节实现替换（Spring Bean 覆盖）

starter 里 7 个策略 Bean 全部带 `@ConditionalOnMissingBean`，业务方提供同类型 Bean 即接管：

`ShellAstAnalyzer` · `RiskGate` · `PermissionEngine` · `SnapshotService` · `AuditStore` · `ApprovalPolicy` · `ModeToolPolicy` · `SkillInvoker`

> 注意：这替换的是**某个环节的内部逻辑**（"怎么判风险"），不是**环节本身**（"要不要判风险"）。

### 3.3 模式白名单（有限可配置，但默认写死）

`DefaultModeToolPolicy` 在构造器里硬编码三张表：

| 模式 | 允许的工具 |
|---|---|
| ARCHITECT_PLANNING | splitTask, writeDesign |
| DEV_EXECUTION | readFile, writeFile, runCompile, restartService, deployService, deleteData |
| AUDIT_REVIEWING | readDiff, runRuleScan, readTestReport |

可以整体替换该策略（如 delivery / agents 模块各自提供独立白名单实例），但**模式枚举本身固定为 3 个**，无法在运行期新增模式。

### 3.4 属性配置

| 前缀 | 可配项 |
|---|---|
| `towndemontower.*` | `enabled`、`mode`、`agentId`、`tenantId`、`sessionId`、`taskId`、`ownerUserId`、`tainted`、`autoGrantDeclaredPerms` |
| `towndemontower.delivery.*` | 开关、是否治理、agent-id、storage（memory/file）、data-file、demo-data、seed-mode |
| `towndemontower.agents.*` | 同上（Agent 注册表） |

> **一处设计张力（值得记下）**：starter 的 `autoGrantDeclaredPerms` 默认为 `true`——
> 只要方法上标了 `@AgentSkill(requiredPerms=...)`，该权限就自动授予配置的 agent。
> 这在单人场景下省事，但与 v1.4 注册表"档案是 RBAC 权威来源"的定位存在冲突：
> 谁写注解谁就能给自己授权，等于绕开集中授权流程。团队化时应默认关闭此项，
> 让权限只能从 Agent 档案下发。

### 3.5 门禁脚本参数（局部可配）

`GateScript` 每个脚本自带 `timeout` 与 `maxRetry`（≤3），失败自动重试、超限 escalate。
这算"单个检查步骤的参数可调"，仍不是"步骤编排"。

### 3.6 明确**不可**运行期配置的

| 项 | 现状 |
|---|---|
| 岗位模板（`RoleTemplate`） | `switch` 硬编码，加岗位要改代码 |
| 风险分级规则（R0~R3 判定） | `DefaultRiskGate` 内置规则；可换实现，不可配置规则表 |
| 审批人 / 审批链 | `HumanApprovalPolicy` 为桩；无路由配置 |
| 状态机转换表 | 构造函数里 `add(...)`，无外部定义 |
| 治理链拓扑 | 无任何配置项 |

## 4. 它离"可编排"还差什么

如果要做成可编排流程，当前缺的是**流程定义层**：

| 缺少的能力 | 说明 | 现在的替代物（及其局限） |
|---|---|---|
| 流程定义文件 | 无 BPMN / YAML / DAG 定义，节点与边不可声明 | 无 |
| 节点编排器 | 无调度器按图执行、无并行网关、无条件分支节点 | `ExecutorFactory` 固定 `new` 链 |
| 人工任务节点 | 无法把"等人审批"作为流程中的一个可停留节点 | `ApprovalPolicy` 返回 ticketId 后流程即结束，不驻留 |
| 多 Agent 编排 | 无子任务分派、无跨 Agent 权限/审计传递 | `PipelineState.subTasks` 只是**记录**，不驱动执行 |
| 流程版本与热更新 | 无版本化、无灰度 | 改流程 = 改源码 + 重启 |
| 补偿事务（Saga） | 无跨节点补偿编排 | 仅单点快照回滚 |

> `PipelineState` 里的 `subTasks` 容易让人误以为"支持子任务编排"——它只是把子任务名
> 落盘以便断点恢复，**没有任何东西读它来调度执行**。

## 5. 面向个人还是团队

### 5.1 结论

**面向个人使用**（单人 + 单 Agent 串行执行）设计与验证。团队协作的地基已铺，但关键闭环缺失，**现在还不能当团队系统用**。

### 5.2 支撑"个人使用"的证据

| 维度 | 现状 | 对团队意味着什么 |
|---|---|---|
| **身份** | 无登录、无账号体系；`agentId` 是调用方传入的字符串；agents 模块的 Agent 是**虚拟主体**，不对应真人 | 无法回答"这是谁操作的"，追责只能追到 ID |
| **租户** | `tenantId` 仅在 `ExecutionContext` 里透传，无任何按租户过滤、隔离、配额的实现 | 多团队共用会互相看见数据 |
| **存储** | 默认内存仓储（`InMemoryXxxRepository`），文件模式为单文件全量重写 | 多实例部署会互相覆盖 |
| **审批** | `HumanApprovalPolicy` 是桩：R2 返回一个 ticketId 就结束，没有审批人、没有通知、没有回写 | "转人工"实际上转给了空气 |
| **并发** | 无任务队列、无抢占、无配额；`CancellationToken` 只能急停**本进程内**在途调用 | 两个团队同时跑会互相拖垮，且无法限流 |
| **执行粒度** | 一次 `execute()` 走一条链、调一个工具，**串行**；无并行分支 | 无法表达"三个人同时干三件事再汇合" |
| **流程形态** | 固定管线 + 两个固定状态机（见 §2） | 无法按团队习惯定制流程 |
| **部署** | 单进程 Spring Boot，演示用 `main` 启动 | 无集群、无选主、无分布式锁 |

### 5.3 已为团队协作预留的地基（有价值，但未闭环）

| 已具备 | 为什么它对团队重要 |
|---|---|
| **审计哈希链**（SHA-256 追加写，任何分支都记录） | 多人多 Agent 共用一本不可篡改账本，是团队治理的前提 |
| **RBAC + Agent 注册表** | "谁能干什么"有了权威来源，下线自动回收权限 |
| **写前快照** | 误操作可回滚，团队协作中谁改坏了能定位 |
| **事务一致性（Outbox + 事件）** | 多实例部署时决策与事件不丢，这是横向扩展的前置 |
| **固定的强制返工环节**（AUDIT 不可直连 DEV） | 团队里"边审边改"是最常见的失控点，代码层面直接堵死 |
| **策略层可替换**（IAM / 审批网关 / 审计存储） | 接企业账号体系、审批系统时不用改治理链 |

### 5.4 判断依据小结

设计**意图**明显指向团队协作（多 Agent 治理、RBAC、审计链、审批、急停），
但**实现**刻意停在"单机可验证的最小闭环"：

- 一个人的多个 Agent ✔
- 一个人的串行任务 ✔
- 多个人同时操作同一套数据 ✗
- 多个人各有权限边界 ✗（有 RBAC 骨架，无账号绑定）
- 多人审批流 ✗
- 多 Agent 并行协作 ✗（明确排到 v2.0）

这是合理的演进顺序：**先把"治理一个人"做扎实，再谈"治理一个团队"**——
权限回收、审计链、强制返工这些机制在单人场景下就能验证正确性，扩到团队时才不会放大错误。
