# 个人开发者的"可编排"：用代码声明意图，而不是填表单

> **核心论点**：对个人开发者而言，"可编排"的价值不在"有图形界面"，而在
> **把流程意图写进文本、和业务代码放在同一个编辑器与同一次 commit 里**。
> 平台化的可视化编排把流程搬到数据库和 GUI 里，对一个人维护的项目来说，
> 增加的是上下文切换成本和不可 review 的资产，而不是能力。

---

## 0. 命名约定（先钉死，避免后文歧义）

| 名称 | 指什么 |
|---|---|
| `agentflow` | 编排层本身：流程定义模型（IR）、编译器、运行器、Java Starter / Python 包 |
| `agenthub` | CLI 命令：`agenthub init` / `agenthub validate` / `agenthub run` |
| `agenthub.yml` | 默认流程定义文件名 |
| `@Flow` / `@Step`（Java）、`@flow` / `@step`（Python） | 注解式编排的入口 |

三者不是三个产品，是**同一套 IR 的三种声明面**（见 §2）。

---

## 1. 先回答"为什么不是表单"

把"表单"的代价具体化，否则这句话只是口号。对个人开发者，表单式编排的实际成本是五条：

| 代价 | 具体表现 |
|---|---|
| **不可 review** | 流程存在数据库里，导出是截图或一份随时失真的 JSON；review 时看不出"上周谁把 review 节点从阻塞改成了跳过" |
| **不可 diff** | 改一个节点参数，界面上只有"保存成功"，没有 `- risk: R1 / + risk: R2` 这样的一行差异 |
| **不可复用** | 别人的最佳实践只能靠截图+口述传授；代码形态下是 `git clone` + 改两行 |
| **两套真相** | 流程在 GUI、实现代码在 IDE。改了方法签名，流程里还指着旧参数，只有运行时才发现 |
| **CI 缺席** | 校验发生在"点保存"那一刻，CI 里跑不到；文本形态可以 `agenthub validate` 卡在合并前 |

对应的，文本声明换来的是：**流程是可 diff 的一等公民资产**，与代码同源、同版本、同评审。

---

## 2. 编排层可变，治理层固定（承接上一版结论）

必须先把两件事分开，否则"可编排"会被误解成"连安检门也能拖掉"：

| 层 | 内容 | 可变性 |
|---|---|---|
| **编排层**（本文主题） | 调用哪些工具、按什么顺序、谁能调、失败怎么办 | **可变**——三种形态都在描述这一层 |
| **治理层**（既有实现） | 每次工具调用必经的 10 个环节及其顺序 | **固定**——`Audit → Mode → Format → Schema → Capability → Permission → RiskGate → Taint → Snapshot → Sandbox` |

> 一句话：**编排决定"调用序列"，治理决定"每次调用要过哪些检查"。**
> 个人开发者要的自由是第一层；平台产品常见的错误是把第二层也做成可拖拽的——
> 那意味着有人能把 `Audit` 节点拖走，审计链当场失效。

所以三种形态**共享同一个运行时**：

```
agenthub.yml  ─┐
@Flow/@Step   ─┼─►  FlowDefinition（IR）  ─►  FlowCompiler  ─►  FlowRunner
flow.py       ─┘     （roles + nodes + edges）   拓扑排序/环检测     │
                                                                     │ 逐节点
                                                                     ▼
                                              executor.execute(intent, ctx)  ← 固定 10 环节
                                                                     │
                                                                     ▼
                                                        审计哈希链 / RBAC / 快照
```

三种形态的差别只在**怎么把 IR 写出来**，不在**IR 怎么执行**。这是"轻量在入口、不轻量在保障"的结构性保证。

## 3. 形态一：纯 YAML / JSON 编排（首选）

### 3.1 适用场景

- 流程有明确的多步骤、多角色分工，且**步骤之间的依赖关系比分支逻辑更重要**；
- 希望流程能 code review、能 fork 别人的模板、能在 CI 里校验；
- 同一条流程会被反复执行（发布检查、周报生成、回归跑批）；
- 一个人维护，但想让"流程长什么样"这件事一眼可见。

### 3.2 核心思路：两段式声明

`roles` 声明"谁"，`flow` 声明"做什么、依赖谁"。角色段直接复用 v1.4 的 Agent 注册表（`role` / `skills` / `permissions`），不引入第二套身份概念。

```yaml
# agenthub.yml
version: 1

roles:
  pm:
    role: PM                      # 映射到 AgentRole
    skills: [splitTask, writeDesign]
    permissions: [plan:write, delivery:read]
  dev:
    role: DEVELOPER
    skills: [writeFile, runCompile, readLog]
    permissions: [fs:write, build:run, log:read]
  reviewer:
    role: QA
    skills: [readDiff, runRuleScan, readTestReport]
    permissions: [review:read]

flow:
  - id: plan
    role: pm
    uses: splitTask               # 对应 SkillRegistry 中的工具名
    with:
      requirement: "{{ inputs.requirement }}"

  - id: design
    role: pm
    uses: writeDesign
    needs: [plan]
    with:
      topic: "{{ steps.plan.output }}"

  - id: code
    role: dev
    uses: writeFile
    needs: [design]
    with:
      path: "src/Main.java"
      content: "{{ steps.design.output }}"

  - id: compile
    role: dev
    uses: runCompile
    needs: [code]
    with:
      module: core

  - id: review
    role: reviewer
    uses: readDiff
    needs: [compile]
    with:
      ref: HEAD
    gate: true                    # 作为质量门禁：不通过则流程中止
    on_fail: stop                 # stop | continue
```

三段命令即可完成"写—验—跑"：

```bash
agenthub validate agenthub.yml    # CI 里也能跑：schema、工具名、变量引用、环检测
agenthub run agenthub.yml --input requirement="给看板加导出"
```

### 3.3 模板复用：模板就是一个文件

```bash
agenthub init --template review-gate    # 拉到本地 agenthub.yml，直接改
```

模板复用的机制简单到不需要"模板市场"：**一个 yml 文件就是一份可分享的模板**。
别人 fork 后改两行（换个工具、换个角色），`git diff` 就是他的改造说明。
这比"在平台里复制一份流程、改参数、导出一张图"轻一个数量级。

### 3.4 取舍

| 得到 | 放弃 |
|---|---|
| 流程可 diff、可 review、可 fork | **不能写复杂逻辑**：一旦在 YAML 里做 `if/else`、循环、字符串处理，就会长成一门残缺的编程语言 |
| CI 可校验（合并前就能发现工具名拼错、变量引用不存在、节点成环） | 动态生成流程困难（步骤数依赖运行时数据时，YAML 写不出来） |
| 与语言无关，换实现不用改流程 | 复杂表达式要靠模板引擎，调试体验差 |
| 结构显式，能自动生成流程图 | 多人同时改一个文件会有 merge 冲突（但这是所有代码资产的通病） |

> **明确的边界**：当流程里出现第三个条件分支时，不要给 YAML 加语法，**换形态三**。
> 给配置语言加控制流是这类工具最常见的滑坡。

### 3.5 为什么对个人开发者足够轻量

- 需要新增的文件：**1 个**；
- 需要启动的外部服务：**0**（无数据库、无服务端、无账号）；
- 需要学的概念：`roles` + `flow` + `needs`，三个；
- 校验命令一条，出错信息能指到行（schema 校验在编译期完成，不是运行时才炸）。

## 4. 形态二：注解 / 装饰器即编排（代码级）

### 4.1 适用场景

- 已经有一个 Spring 或 Python 代码库，流程与业务方法**一一对应**；
- 不想为同一套逻辑维护第二份 YAML（两份真相是维护成本的大头）；
- 流程的生命周期跟着代码走（改流程 = 发版），不需要运行期热改。

### 4.2 核心思路：注解只声明"位置与治理属性"，方法体仍是业务代码

Java（`agentflow-spring-starter`）：

```java
@Flow(name = "release-check", roles = {
        @Role(id = "dev",      role = AgentRole.DEVELOPER),
        @Role(id = "reviewer", role = AgentRole.QA)
})
public class ReleaseCheckFlow {

    @Step(id = "compile", role = "dev", uses = "runCompile")
    public CompileResult compile(@Input("module") String module) {
        return buildService.compile(module);       // 业务代码，原样保留
    }

    @Step(id = "review", role = "reviewer", uses = "readDiff",
          needs = {"compile"}, gate = true)
    public ReviewResult review(@From("compile") CompileResult result) {
        return reviewService.scan(result.diffRef());
    }

    @Step(id = "publish", role = "dev", uses = "deployService",
          needs = {"review"}, onFail = OnFail.STOP)
    public void publish(@From("review") ReviewResult r) {
        releaseService.publish(r.approvedVersion());
    }
}
```

Python（`agentflow` 包）：

```python
from agentflow import flow, step, Input, From

@flow("release-check", roles={"dev": "DEVELOPER", "reviewer": "QA"})
class ReleaseCheck:

    @step(id="compile", role="dev", uses="runCompile")
    def compile(self, module: Input("module")):
        return self.build.compile(module)

    @step(id="review", role="reviewer", uses="readDiff",
          needs=("compile",), gate=True)
    def review(self, result: From("compile")):
        return self.review.scan(result.diff_ref)

    @step(id="publish", role="dev", uses="deployService", needs=("review",))
    def publish(self, r: From("review")):
        self.release.publish(r.approved_version)
```

启动期扫描注解 → 用 `needs` 建有向边 → 拓扑排序 → 得到**与 YAML 完全相同的 IR**。
运行期逐节点调用方法，每次调用仍经 `executor.execute()` 走固定 10 环节。

### 4.3 框架兜底什么（这是"免填表单"的底气）

| 兜底项 | 机制 |
|---|---|
| 权限 | `uses` 对应的 `SkillDescriptor.requiredPerms` 自动生效，角色缺权限直接 `PERMISSION_DENIED` |
| 风险 | 工具声明 R0~R3，R2 自动转审批、R3 直接拒绝，业务代码无需感知 |
| 审计 | 每次调用落哈希链，方法级参数与结果可追溯 |
| 快照 | `sideEffect=true` 的工具执行前留痕 |
| 参数校验 | `requiredArgs` 与 `@Input` 对齐，缺参在 Schema 环节拒绝 |
| 返回值传递 | `@From("compile")` 由框架按拓扑序注入，不需要手写变量池 |

**写业务代码即编排**：开发者只回答"这个方法在流程里叫什么、依赖谁"，不回答"怎么鉴权、怎么记账"。

### 4.4 取舍

| 得到 | 放弃 |
|---|---|
| 零新增文件（在已有类上加注解） | **流程结构被代码结构绑死**：重命名方法、拆分类会隐式改变流程图 |
| IDE 全程可用（跳转、重构、类型检查、单测） | 跨进程/跨服务表达不了（注解是单进程内的；跨服务要退化成一个 RPC 工具节点） |
| 与现有 `@AgentSkill` 同源，扩展点极小 | 流程不可热改：改流程 = 改代码 = 重新部署（对个人项目通常无所谓） |
| 单测直接测方法，不需要跑流程引擎 | 流程图要靠静态分析生成，不能手改（改图不回写代码） |

### 4.5 与既有实现的最小差异

现有 `@AgentSkill` 已解决"**单个工具**进治理"；`@Flow` / `@Step` 只多两件事：

1. `needs` → 边（用于拓扑排序）；
2. `@From` → 节点间数据传递（按拓扑序注入返回值）。

其余（风险、权限、快照、审计、沙箱）**完全复用**，不新增治理逻辑。这也是为什么它轻：**没有第二套运行时**。

## 5. 形态三：单文件脚本（CLI 编排）

### 5.1 适用场景

- 一次性或探索性任务：先跑通再说，不想先设计结构；
- 流程里需要真正的逻辑：循环重试、条件分支、读外部 API、动态决定步骤数；
- 想快速把几个工具串起来验证效果，验证完再决定要不要固化成 YAML。

### 5.2 核心思路：`init` 给骨架，`run` 直接执行

```bash
agenthub init flow.py            # 生成一个可运行的最小骨架
agenthub run flow.py --input requirement="给看板加导出"
```

生成的骨架（Python）：

```python
from agentflow import run, flow

@flow("adhoc")
def main(ctx):
    plan = run("splitTask", role="pm", requirement=ctx.input("requirement"))
    design = run("writeDesign", role="pm", topic=plan.output)

    # 需要动态逻辑时，直接写 Python —— 这是 YAML 做不到的部分
    for target in design.modules:
        run("writeFile", role="dev", path=f"{target}/README.md", content=design.summary)
        result = run("runCompile", role="dev", module=target)
        if not result.ok:
            run("writeDesign", role="pm", topic=f"修复 {target} 的编译错误")

if __name__ == "__main__":
    main()
```

`run()` 是 SDK 的唯一入口：它内部构造 `IntentObject` + `ExecutionContext`，
走**同一条固定治理链**。脚本形态不提供"绕过治理的快捷方式"。

### 5.3 一条刻意的设计约束：绕过必须比遵守更麻烦

脚本形态最大的风险是"直接调业务 API，审计链断掉"。因此：

| 设计 | 原因 |
|---|---|
| `run()` 是默认路径，一行调用即进链 | 顺手的路就是受治理的路 |
| 裸调用需要显式 `ungoverned=True`，且会在审计里写一条 `UNGOVERNED_CALL` 标记 | 绕过不是禁止，但**必须留痕**，事后能查出来 |
| `agenthub run` 结束时打印本次调用的治理摘要（节点数 / 拒绝数 / 审批数） | 个人开发者也能一眼看出"有没有裸奔" |

### 5.4 取舍

| 得到 | 放弃 |
|---|---|
| 表达力等于宿主语言，写循环/条件/外部调用毫无障碍 | **无静态结构**：运行前不知道流程长什么样，`validate` 只能做语法与工具名的粗校验 |
| 一个文件、零配置、改一行重跑 | 不可复用：别人只能复制整个脚本，改不动就 fork 一份 |
| 适合验证阶段快速试错 | 不可生成流程图（只能运行时 dump 调用序列） |
| 无需构建、无需部署 | 版本管理粒度粗（一个脚本一个整体，diff 噪声大） |

### 5.5 为什么它仍然"够轻"

- 需要新增的文件：**1 个**；
- 需要写的样板：`init` 已生成，开发者只往里填 `run()` 调用；
- 不需要定义 roles、不需要建图、不需要理解拓扑排序——**脚本的执行顺序就是流程顺序**。

代价是失去了"结构可校验"，所以它的定位是**入口形态**，不是长期形态：
跑通后再用 `agenthub export --to yml` 固化成 YAML，是这个工具链刻意留的升级路径。

## 6. 选型指引

| 判据 | 选 YAML | 选注解 | 选脚本 |
|---|---|---|---|
| 流程结构稳定、会被反复执行 | ✅ | ✅ | — |
| 需要 code review 流程本身 | ✅ | ✅（在代码里） | ✗（diff 噪声大） |
| 需要 fork 别人的模板 | ✅ | ✗ | ✗ |
| 已在 Spring/Python 代码库里、流程与代码一一对应 | — | ✅ | — |
| 流程里有循环/条件/动态步骤数 | ✗ | 部分（写法别扭） | ✅ |
| 一次性验证、探索 | — | — | ✅ |
| 跨语言、换实现不改流程 | ✅ | ✗ | ✗ |

**组合用法（推荐）**：默认 YAML；单个节点逻辑复杂时，用
`uses: script:./steps/custom.py` 把脚本挂成一个节点——结构留在 YAML 里，复杂度关在脚本里。
这样"可 review 的骨架"与"能写逻辑的叶子"各就各位。

## 7. 轻量的量化对比

| 维度 | YAML | 注解 | 脚本 |
|---|---|---|---|
| 新增文件数 | 1（yml） | 0（在已有类上加注解） | 1（py/sh） |
| 需要的新概念 | roles / flow / needs | @Flow / @Step / @From | run() |
| 上手命令 | `agenthub run` | 正常构建启动 | `agenthub run` |
| 需要数据库 | 否 | 否 | 否 |
| 需要服务端 / GUI | 否 | 否 | 否 |
| 需要账号体系 | 否 | 否 | 否 |
| 流程可静态校验 | 强（schema + 图 + 变量引用） | 中（编译期注解处理） | 弱（仅语法） |
| 治理是否自动生效 | 是 | 是 | 是（默认路径） |

三种形态的共同点：**都不需要"起一个平台"**。这对个人开发者是决定性的——
平台意味着进程、端口、数据库、账号，以及"三个月后回来发现自己忘了怎么启动"。

## 8. 落地映射（与现有代码的关系）

| 组件 | 归属 | 说明 |
|---|---|---|
| `FlowDefinition` / `StepDefinition` / `RoleSpec` | `core`（纯 Java，零依赖） | 三种形态共同的 IR |
| `FlowCompiler` | `core` | 拓扑排序、环检测、`{{ steps.x.output }}` 引用校验、工具名与 `SkillRegistry` 对账 |
| `FlowRunner` | `core` | 按拓扑序逐节点 `executor.execute()`；`gate=true` 节点失败即中止 |
| `agenthub` CLI | 新增薄模块 | `init` / `validate` / `run` / `export` |
| `@Flow` / `@Step` | `spring-starter` 扩展 | 启动期扫描构图，复用既有 `AgentSkillAspect` 的执行通道 |
| `agentflow`（Python） | 独立包 | 装饰器与 `run()`，通过 HTTP 或子进程调 Java 运行时 |

**不改动的部分**：`ExecutorFactory.buildDefault` 的 10 环节与顺序、两个状态机、
RBAC、审计哈希链、快照、沙箱。编排是加在它们**之上**的一层调度，不是对它们的替换。

这也解释了为什么"个人开发者的可编排"能做得这么轻：
**治理是框架兜底的常量，编排只是变量的排列。** 一个人不需要配置常量，
只需要把自己的意图按顺序写出来——写在一个他能 diff、能 review、能 fork 的文件里。
