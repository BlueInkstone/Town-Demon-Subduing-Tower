## 1. 具体目标

### 1.1 目标（可验收）

| 编号 | 目标 | 验收方向 |
|---|---|---|
| G-1 | 把审计链从「冷数据」变成**可复算的行为报告**：按 `agentId` 说清「谁、在什么窗口、触发了多少次待审批 / 高危拒绝」 | 报告与人工复算一致（AC-4） |
| G-2 | 让「是否收紧某 Agent 的可执行范围」从后台静默动作变成**有人批准、有据可查、可回滚**的动作 | 权限变更 100% 有批准记录（AC-3） |
| G-3 | 全程不破坏既有基线：模型只提议、闸门硬裁决；模式由状态机推进；权限显式下发；审计只追加 | 只读阶段零权限 / 模式变更（AC-2） |
| G-4 | 分析器故障不构成新的静默失效面 | 故障退化判据（AC-6） |
| G-5 | 为方向 A / D 留好接口，不引入新的绕过面 | 本文不含改链、改建单口子的需求 |

### 1.2 明确**不**追求的目标

- 不追求「自动提升拦截率」——那会诱导把证据当控制输入，并放大误伤。
- 不追求「实时」——行为判定基于时间窗聚合，不是逐调用裁决。
- 不追求「智能」——不引入模型 / LLM 判断 Agent 是否可疑。
- 不追求把审计链改造成控制总线。

## 2. 目标用户与使用场景

| 角色 | 是谁 | 要回答的问题 | 用到的功能 |
|---|---|---|---|
| 接入方开发者 | 个人开发者 / 1~3 人小队（与 `docs/16` 目标用户一致） | 「我这几个 Agent 里，哪个总在触发人工审批？」 | 只读报告（FR-3） |
| 治理策略维护者 / 运维 | 负责配规则、批单的人 | 「要不要临时收紧它？依据是什么？什么时候恢复？」 | 规则配置（FR-4）、建议单（FR-7~FR-9） |
| 审批人 | 与提交者不同的角色（禁自批） | 「这条降权建议能不能批？」 | 人工批准 / 驳回（FR-8） |
| 安全复核人 | 事后审计 / 复盘 | 「这次收紧是谁批的、依据哪段审计、什么时候失效？」 | 全链路留痕与回放（FR-10、FR-12） |
| **受影响方**（非直接用户） | 被降权 Agent 的调用方 / 业务 | 「我的调用为什么被拒了？」 | 拒绝原因必须可解释（FR-9、NFR-5） |

| 场景 | 描述 | 预期结果 |
|---|---|---|
| S-1 例行巡检 | 维护者每周跑一次报告，看各 `agentId` 的待审批 / R3 频次 | 得到脱敏报告，**系统无任何配置变化** |
| S-2 可疑行为处置 | 某 `agentId` 连续触发待审批，分析器产出建议单 | 建议单进人工审批；**未批准前零权限变更** |
| S-3 到期回收 / 复盘 | TTL 到期或人工回滚后，复核整条链路 | 权限恢复，审计链完整且未被改写 |

## 3. 核心功能需求（FR）

### A 组 · 只读分析（P0，方案 1）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-1 | 以**只读**方式扫描审计链（`AuditStore.all()`），按 `agentId` / 时间窗聚合；不得写回审计记录，不得改变治理链拓扑 | P0 | 扫描前后审计链哈希不变（AC-2） |
| FR-2 | 统计口径固定且可复算：`PENDING_APPROVAL`（R2 转人工）、`R3_DENIED`、拒绝率、连续触发次数；**口径写进文档**，禁止隐式把别名码混算（见 L-2） | P0 | golden 用例与人工复算一致（AC-4） |
| FR-3 | 输出结构化报告：时间窗、规则版本、样本数、各 `agentId` 指标、异常标记；**脱敏**，不回显审计原文、参数值、凭据 | P0 | 报告不含敏感字段（AC-10） |
| FR-4 | 规则可配置：阈值、窗口长度、**最小样本数**、启用开关；**默认关闭**，显式配置才运行 | P0 | 默认关闭时零行为差异（AC-1） |
| FR-5 | 出结论前必须校验链完整性（`verifyChain()`）；链校验失败 / 数据不足 / 样本低于阈值 → **不产出降权结论**，报告标注「证据不足」 | P0 | 故障注入用例（AC-6） |
| FR-6 | 失败退化：分析器异常 / 不可用 / 证据不足时，不改变治理链既有裁决 ——既不因它放宽闸门，也不因它全拒业务；且不产生任何权限变更 | P0 | 同 AC-6 |

### B 组 · 人工决策（P1，方案 2；仅在 D-1 选中时启用）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-7 | 产出结构化**降权建议单**（含触发依据的审计区间、规则版本、`agentId`、建议范围、TTL）；建议单**只能由分析链生成**，不得提供「管理端点建单」口子（`ApprovalAdminController` 明确不建单，见 L-6） | P1 | 不存在任何外部建单入口 |
| FR-8 | 建议单复用既有人工审批通道：`ApprovalCenter` 的批准 / 驳回 / 超时即拒；**禁自批**（`SELF_APPROVAL`）、非 PENDING 不得再决策 | P1 | AC-7 |
| FR-9 | **人工批准后**才由 Agent 注册表**显式下发**收紧，带 TTL、到期自动回收、支持一键回滚；拒绝原因对调用方可解释；`AgentMode` 不切换、模式状态机不介入 | P1 | AC-3 / AC-8 |
| FR-10 | 全链路留痕：扫描、出报告、生成建议单、批准 / 驳回、下发、到期回收、回滚，每一步进审计链（含规则版本、依据区间、`TimeProvider` 时间戳）；**审计链本身不因回滚被改写** | P1 | AC-9 |

|---|---|---|---|

- 报告覆盖了哪些证据、没覆盖哪些（尤其是 SDK 侧）？

## 6. 范围边界

### 6.1 范围内

- Java 主线审计链（`HashChainAuditStore` / `FileAuditStore`）的**只读**消费
- `ApprovalCenter` 既有人工审批通道、`Agent` 注册表既有显式授权入口、`TimeProvider`、`AdminGuard` 既有鉴权
- 报告 / 建议单 / 收紧生命周期（生成 → 批准 → 下发 → 到期 → 回滚）及其审计留痕
- 与 `docs/33` 管理接口一致的错误码与响应信封（若 D-2 选端点）

### 6.2 明确不在范围内

| 不在范围内 | 理由 |
|---|---|
| 方案 3 全自动降权、后台按规则自动收紧 | 与 C-1 / C-2 / C-4 冲突，原则未定（`docs/08` §C.2 / §C.3） |
| 直接写权限表、切换 `AgentMode`、放行 R3、模式切换 | v1.5 / v1.6 / v1.17 明确的高风险能力边界 |
| 修改 core 装饰器链拓扑、改风险闸门裁决逻辑 | 治理链顺序写死，分析器不是闸门 |
| 修改审计链格式、就地重算既有链 | 破坏证据；存量链如要迁移须 `chainVersion` 单独评审（`docs/35` §6.5） |
| 提供「管理端点建单」 | `ApprovalAdminController` 明确只提供看单 / 批单 / 驳单，建单只能由治理链生成 |
| 把 Python / TypeScript SDK 的审计链**本身**纳入 M1 统计 | 三语言链格式互不兼容（`docs/35` D-01）；错误码口径已打通，但链证据须先完成审计链统一（单独评审，不允许就地重算） |
| 跨语言契约统一 golden 用例（比对 `risk` / `code` / `audit hash` / `ticket`） | 方向 D 第 ⑤ 步；错误码口径已由方向 D 定稿，M1 通过 `--normalize-aliases` 打通（默认关闭） |
| 多 Agent 编排、多模态预处理、意图级快照、提示词哨兵、红队演练 | 方向 B / v2.0 其他排后项 |
| UI 页面 / 可视化看板（本期） | v1.17 已定「本轮只做后端」；报告走端点或 CLI |
| 引入模型 / LLM / 外部分析服务 | NFR-6 确定性要求 |
| 「绝不静默失效」对外宣传语 | 方向 A-1 未落地前不得对外宣称（`docs/08` A-4） |

## 7. 成功衡量标准（AC，完成定义）

| 编号 | 验收判据 | 对应 |
|---|---|---|
| AC-1 | 开关默认关闭时，审计事件、Bean 装配、端点、业务行为与现状完全一致 | FR-4 / NFR-10 |
| AC-2 | M1 全程**零**权限变更、**零**模式变更、**零**闸门裁决变更；扫描前后审计链哈希不变 | FR-1 / G-3 / NFR-3 |
| AC-3 | 所有生效的收紧都能追溯到一条**人工批准**记录；无批准即无下发，比例 100% | FR-8 / FR-9 / G-2 |
| AC-4 | 同一批审计记录 + 同一规则版本，报告结果与人工复算逐项一致 | FR-2 / NFR-8 |
| AC-5 | 链校验失败 / 样本不足 / 规则未配 → 报告标注「证据不足」，不产出降权结论 | FR-5 |
| AC-6 | 故障注入（分析器异常、不可用、数据不足、链校验失败）：不放宽闸门、不全拒业务、不产生权限变更，且事件进审计 | FR-6 / G-4 |
| AC-7 | 自批被拒（`SELF_APPROVAL`）、非 PENDING 单不能重复决策、超时即拒 | FR-8 |
| AC-8 | TTL 走 `TimeProvider`；冻结时钟可测；重启后仍按原 TTL 生效；到期自动回收并可一键回滚 | FR-9 / NFR-7 |
| AC-9 | 扫描、报告、建议、批准、下发、回收、回滚七类事件可回放；回滚后审计链未被改写 | FR-10 / NFR-3 |
| AC-10 | 报告与错误信息不含审计原文、参数值、凭据等敏感内容 | FR-3 / NFR-5 |
| AC-11 | Java 主线既有回归基线不退化、静态扫描 0 违规（**1575/1575 为文档基线，验收时须实跑**） | NFR-9 |

### 7.1 质量指标口径（PM 定义，基线待实测后设定）

| 指标 | 定义 | 目标 |
|---|---|---|
| 报告覆盖率 | 可分析记录数 / 总记录数（须声明未覆盖的 SDK 侧证据） | 首期允许 < 100%，但**必须如实标注** |
| 误报率 | 人工驳回的建议单 / 建议单总数 | **不预设数字**；先跑一个观察周期再定基准 |
| 批准时延 | 建议单生成 → 人工决策的中位耗时 | 仅观测，不作 SLA |
| 退化次数 | 因证据不足 / 分析器异常进入退化的次数 | 异常即告警，不追求 0 |
| 权限变更可追溯率 | 有完整批准 + 审计链的变更 / 全部变更 | **必须 100%** |

## 8. 已知限制条件与前置依赖

| 编号 | 限制 | 影响 | 应对 |
|---|---|---|---|
| L-1 | 三语言审计链格式不兼容（Java 竖线 + HMAC，SDK 冒号 + SHA-256；Python `prev_hash` vs TS `prevHash`） | 首期只能分析 Java 链，SDK 证据不可用 | D-3 限定 Java；报告显式声明覆盖率（`docs/35` D-01） |
| L-2 | 错误码集合分裂，三方仅 2 个同名常量；`PENDING_APPROVAL` 在 SDK 叫 `APPROVAL_REQUIRED` | 按码统计会把同一语义漏算 / 重复算 | **方向 D 已定稿 `contract/error-codes.json` 并提供三语言归一绑定**；M1 默认仍固定 Java 规范码（D-3），显式 `--normalize-aliases` 可打通 |
| L-3 | 审计是**证据不是控制输入**；日志重放 / 重复上报 / 注入可制造拒绝服务（把正常 Agent 刷成高频 PENDING） | 自动执行会放大攻击面 | 只读 + 最小样本 + 链校验 + 人工批准（FR-5 / FR-8） |
| L-4 | 链可信依赖 HMAC 密钥与外锚；无密钥时只能查篡改、挡不住整链重算 | 证据不足时结论不可信 | FR-5 前置 `verifyChain()`，报告标注降级模式 |
| L-5 | R2 高频**不等于**恶意，可能是正常高危业务 | 存在误报，会误伤 | 只出建议单，不自动执行；误报率需观察周期 |
| L-6 | v1.17 管理端点默认关闭（未开时 Controller Bean 不装配）、复用 `metrics-token` 做 `X-Governance-Token`；审批端点**不提供建单** | 报告出口与建议单入口受约束 | D-2 决策；FR-7 禁止外部建单 |
| L-7 | `ApprovalCenter.DEFAULT_TTL = 1 小时`；`create/approve/deny/expireOverdue` 由调用方传 `Instant` | 「24 小时」需显式配置并与 `TimeProvider` 接线 | NFR-7；接线方式由 Arch 定 |
| L-8 | `ApprovalTicket` 面向「工具调用」（`tool` / `impactNote` / `rollbackPlan`），与「按 `agentId` 降权」不同形 | 建议单数据模型不能直接复用 | 列为 §9 的 Arch 待决问题，本文不替 Arch 决定 |
| L-9 | 自动降权与「权限显式下发」「模式由状态机推进」冲突（C-1 / C-2） | 方案 3 无法在本期落地 | M3 不排期，先单独评审原则 |
| L-10 | 全量扫描是 O(n)，大链可能拖慢；阈值未压测 | 性能上限未知 | NFR-2 要求不进主链；分段 / 索引与阈值由 Arch + 压测确定，本文不编数值 |
| L-11 | Java 1575/1575、Python 108/108、TS 91/91 各自通过只说明内部自洽 | 不能推出跨语言契约一致 | `docs/35` 结论；方向 D 是 C 的前置之一 |

**前置依赖**
- 方向 A：链可信 / 内部故障不静默（A-1 ~ A-3）——决定「证据能不能用」。
- 方向 D：wire schema 与错误码映射——决定「统计口径能否跨语言」；未落地前按 D-3 限定 Java。
- 方向 B：无依赖，可并行。

### 12.3 假设与偏差（按「最合理解释」落地，逐条说明）

| # | 假设 / 偏差 | 理由 |
|---|---|---|
| A-1 | 分析器放 `core` 新包 `analysis`，与 `bypass` 同层，不进 starter 自动装配 | §9 的 Arch 未决项；只读消费 core 审计链、零依赖、不引入 Bean / 端点，是零冲突的最小落点 |
| A-2 | **时间窗按「最近 N 条记录」而非时间范围** | Java `AuditRecord` 只有 seq/action/payload/prevHash/hash，**不含时间戳**；报告仍用 `TimeProvider` 记录生成时刻，TTL 等时间语义留 M2 |
| A-3 | 默认关闭 = 库层 `enabled=false`；**运行 CLI 即一次显式启用** | 离线 CLI 没有常驻进程，不调用就没有任何分析行为；框架内不装配，NFR-10 逐字节等价 |
| A-4 | **AC-6 的「事件进审计」本轮不实现** | 与 AC-2「扫描前后审计链哈希不变」、FR-1「只读」直接冲突。M1 选择只读：退化只体现在报告 `status`、notes、CLI 输出与 stderr；审计事件留到 M2 一起做 |
| A-5 | `agentId` 用「前两位 + SHA-256 前缀」脱敏 | AC-10 要求不回显审计原文 / 凭据，同时 S-1 场景仍需区分不同 Agent；掩码稳定可关联 |
| A-6 | 统计口径沿用 `AuditDecorator`：`PENDING_APPROVAL` 不计拒绝，其余非 `OK` 计拒绝；**默认只认 Java 规范码（D-3）** | 不引入新口径；方向 D 定稿后，`--normalize-aliases` 显式开启时按 `contract/error-codes.json` 归一再统计，默认关闭保持 D-3 行为不变（L-2） |
| A-7 | 链校验只读解析 `FileAuditStore` 行格式，复用 `AuditCrypto.chain`，**不 new FileAuditStore** | 该构造器会追加段头、重写锚点，属写操作，会破坏 FR-1 / AC-2 |
| A-8 | 非 `SKILL_INVOKED` 或形状不符的记录计入跳过与覆盖率分母，不参与指标 | Java 侧审计 payload 形状不统一（`AgentSkillAspect` 拒绝路径就没有 `agent=`），不猜测、不抛异常 |
| A-9 | 单个 Agent 样本也要求 ≥ `minSamples` 才允许标记 | L-5 误报约束：避免单样本拒绝率 1.0 直接触发结论 |
| A-10 | CLI 有标记 Agent 仍返回退出码 0 | M1 只出报告、不做裁决，不是门禁；`BypassScanMain` 的非 0 语义不适用于此处 |
