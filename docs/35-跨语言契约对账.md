## 0. 对账口径

| 层次 | 内容 | 判定 |
|---|---|---|
| L1 · 线上 REST | `/towndemontower/metrics`、`/integrity`、`/admin/approvals[...]`、响应信封、视图字段 | ✅ 基本对齐 |
| L2 · 进程内治理契约 | `IntentObject` / `SkillDescriptor` / `ExecutionContext` / `SkillResult` / `ApprovalTicket` / `RiskLevel` / 错误码 / 接口签名 | ❌ 未对齐 |
| L3 · 审计证据 | `AuditRecord` 字段与落盘格式、哈希链公式、序号/时间基准、MAC | ❌ 不兼容 |

方法：逐文件读源码，按「字段命名 → 类型 → 必填性与默认值 → 序列化 → 边界条件」五项比对。
**本次为静态对账**；Java 1575/1575、Python 108/108、TS 91/91 各自通过，只说明各语言内部自洽，不能推出契约一致。

### 2.7 `AuditRecord` 与落盘格式

| 项 | Java | Python | TypeScript |
|---|---|---|---|
| 字段 | `seq`, `action`, `payload(String)`, `prevHash`, `hash` | `seq`, `action`, `payload(dict)`, `timestamp`, `prev_hash`, `hash`, `mac` | `seq`, `action`, `payload(Record)`, `timestamp`, `prevHash`, `hash`, `mac` |
| `seq` 起点 | **1** | **0** | **0** |
| 链头 | `"GENESIS"` | `"0"*64` | `"0"*64` |
| 摘要输入 | `seq`、`action`、`payload`、`prevHash` 用竖线拼接（无时间） | `seq:action:json(payload,sort_keys):timestamp:prev_hash` | `seq:action:JSON.stringify(payload,keys.sort()):timestamp:prevHash` |
| 算法 | HMAC-SHA256（有密钥时）/ SHA-256 退化 | 恒 SHA-256 | 恒 SHA-256 |
| MAC | 由 `AuditCrypto` 决定 | `mac` 恒 `""` | `mac` 恒 `""` |
| 时间 | 不入链 | `datetime.utcnow().isoformat()`（无时区后缀） | `new Date().toISOString()`（带 `Z`） |
| 落盘 | `FileAuditStore` 自有分段/锚点格式 | 每行 `to_json()`（`ensure_ascii=False`），键 `prev_hash` | 每行 `JSON.stringify(record)`，键 `prevHash` |

> **可直接复现的不兼容**：Python `FileAuditStore` 写出的行用 `prev_hash`，TS `FileAuditStore._loadExisting()` 读的是 `prevHash`，
> 读不到就退化成 `"0"*64`。同一份审计文件换语言读，链校验必然失败。
> 另外 Python 的 `json.dumps` 默认分隔符带空格（`{"a": 1}`）、默认 `ensure_ascii=True`；
> TS 的 `JSON.stringify` 是紧凑格式且保留 UTF-8 原字符 —— 即使键序都排序，**摘要输入仍不同**。

## 4. 默认值与边界条件

| 条件 | Java | Python | TypeScript | 判定 |
|---|---|---|---|---|
| `confidence` 越界 | `IntentFormatDecorator` → `INTENT_FORMAT_INVALID` | 构造与 `from_dict` 校验 | 仅 `createIntent` 校验，直接写 interface 不校验 | ⚠️ |
| `confidence < 0.5` | `NEED_MORE_INFO`（不拒绝，让系统决定） | 无特殊处理 | 无特殊处理 | ❌ |
| 建议文本 | `reason` 含「建议」/ `suggest` / `you may consider` → 拒收 | 无 `reason` 字段，`text` 无校验 | 同 | ❌ |
| 未知/空 `risk` | **R2**（unknown-default R2，fail-closed） | 默认 **R1** + 前缀/关键词启发式，兜底 R1 | 需显式 `risk`；无 descriptor 时兜底 R1 | ❌ **同一意图可能一方放行、一方转人工** |
| R3 带 `force` | 仍拒绝 | `context.force` 存在但从不被读取 | 同 | ❌ 悬空字段造成误导 |
| R2 处理 | 生成审批单，按策略可 `PENDING_APPROVAL` 挂起 | 直接返回拒绝 `APPROVAL_REQUIRED` | 直接返回拒绝 `APPROVAL_REQUIRED` | ❌ 审批流语义不同 |
| `requiresPlanApproval` | 未装配/未批准 → `PLAN_APPROVAL_REQUIRED`（强制） | 字段存在，`client.py` 无任何判定 | 字段存在，`client.ts` 无任何判定 | ❌ **声明了但不生效** |
| `tainted` + `sideEffect` | `TaintCheckDecorator` → `TAINTED_WRITE_BLOCKED` | 无 | 无 | ❌ |
| 命令模板空值 | `hasCommandTemplate()`：`null`/空白均视为未声明 | `if descriptor.command_template:`：空串跳过、空格串进入校验 | 同 Python | ⚠️ |
| 命令总长 | 2048 | 2048 | 2048 | ✅ |
| 单参数长 / 参数个数 | 256 / 16 | 无 | 无 | ❌ |
| 控制字符 | 禁 shell 控制操作符、引号、`\n\r\t` 及 `c<0x20`/`0x7f`；单值槽禁 `-`/`~`/`#` 开头 | 禁 shell 控制操作符与引号（注释中明确不检查 `\t\n\r`）；单值槽只禁 `-` 开头 | 同 Python | ❌ 某些注入形态在 SDK 可过 |
| `{name*}` 最少词数 | **至少 1 个词** | 允许 0 个 | 允许 0 个 | ❌ |
| 意图参数卫生 | `IntentArgsValidator`：长度上限、控制字符、路径穿越、参数个数 | 无 | 无 | ❌ |
| 审计 `seq` 起点 | 1 | 0 | 0 | ❌ |

## 5. 差异点与潜在不兼容项汇总

| ID | 差异 | 影响 | 级别 |
|---|---|---|---|
| D-01 | 审计链摘要公式、序号起点、链头、时间入链、MAC 三方不同；Python/TS 落盘键 `prev_hash` vs `prevHash` | **跨语言无法互相校验审计链**，换语言读同一份文件链必断；HMAC 防重算能力在 SDK 缺失 | **P0** |
| D-02 | 错误码集合分裂，三方仅 2 个同名常量；成功码有/无 | 按码分支的重试、告警、审批流跨语言失效 | **P0** |
| D-03 | `IntentObject` 字段集不同（Java 6 / SDK 4），Java 禁建议文本而 SDK 有 `text` | 同一意图无法三语言互传；审批单的影响说明与回滚计划无从生成 | **P0** |
| D-04 | 未知风险默认 Java R2 / SDK R1；`force` 悬空；计划审批与污点规则在 SDK 不生效 | **安全语义被放宽**：同一输入在不同语言得到不同裁决，SDK 可被误认为等价替代 | **P0** |
| D-05 | `SkillResult` 错误码/消息/审批单号字段名与成功表示不同 | 上层解析结果失败 | P1 |
| D-06 | `ExecutionContext.mode` 值域完全不同（`AgentMode` 枚举 vs `"NORMAL"`）+ 缺 `taskId`/`tainted`/`cancellationToken` | 模式白名单、状态关联、急停能力无法对齐 | P1 |
| D-07 | `SkillDescriptor` 三套命名，缺 `sideEffect` / `sandboxPolicy` | 工具元数据无法互换，污点写阻断无法实现 | P1 |
| D-08 | `ApprovalTicket` 仅 `tool` 共有 | 审批数据无法互通 | P1 |
| D-09 | 接口签名不同（`classify` vs `evaluate`、`appendAuto` vs `append`、同步 vs 异步） | 无法写同一套跨语言适配器/契约测试 | P1 |
| D-10 | 命令模板边界差异（`\t\n\r`、`~`/`#`、参数长/个数、`{name*}` 最少 1 词） | 某些命令形状在 SDK 通过、在 Java 被拒（或反之） | P1 |
| D-11 | TS `MetricsReport.counters` 声明为固定 snake_case 结构，Java 实际返回动态 Map | TS 侧指标解析类型不可信；Python 未归一化 | P1 |
| D-12 | Python `to_dict()` 输出 snake_case、TS 对象为 camelCase、Java 无内建序列化器 | **目前不存在权威 wire schema**，任何「对齐」都只能靠人工映射 | P1 |
| D-13 | Python 时间 `...isoformat()` 无时区后缀 / TS `toISOString()` 带 `Z`；`json.dumps` 与 `JSON.stringify` 分隔符、非 ASCII 转义不同 | 摘要输入、日志时间口径不一致 | P2 |

**正向结论**：L1 REST 管理接口层（端点、鉴权头、`ApiResponse`、`ApprovalStatus`、`ApprovalView`、`IntegrityReport`、`AnchorReplicaView`）三方**确实对齐**，Python 的 camelCase→snake_case 映射是完整且正确的。这是目前唯一可以自称「对齐」的部分。

## 6. 统一契约基准（已定稿 2026-11-11）

> **已定稿**：本节规范已落到仓库根 `contract/towndemontower-wire.schema.json`（结构）与
> `contract/error-codes.json`（错误码与统计口径），二者是三语言共用的**唯一权威**；
> 一致性由 `contract/verify_codes.py` 校验（零依赖，可直接当 CI 门禁）。
> 基准取 Java core 的**语义**，命名取线上已对齐的 camelCase。
>
> **注意**：基准定稿 ≠ 实现符合。三语言的 `IntentObject` / `SkillResult` / 审计链仍未改造，
> §7 的总判定「不能宣称三语言契约一致」依然成立。

### 6.1 Wire 规则

1. 所有跨语言传输的字段一律 **camelCase**；Python 内部可保留 snake_case，但 `to_dict()/from_dict()` 必须做双向映射。
2. 可选字段统一用 `null`，不用 `undefined`；缺失字段按默认值补全且**显式写出**，避免「省略 vs 默认值」二义。
3. 枚举一律用字符串值（`R0`..`R3`、`PENDING/APPROVED/DENIED/EXPIRED`、`ARCHITECT_PLANNING/DEV_EXECUTION/AUDIT_REVIEWING`）。
4. 时间统一 `ISO-8601 UTC` 且带 `Z`；数值 `confidence` 用 JSON number，`seq` 用整数。
5. JSON 规范化固定为：键按字典序、分隔符 `,` / `:`（无空格）、`ensure_ascii=false`、UTF-8。

### 6.2 规范数据结构

```json
{
  "IntentObject": {
    "tool": "string (required)",
    "args": "object (required, default {})",
    "confidence": "number (required, 0.0-1.0)",
    "reason": "string|null (required)",
    "expectedEffect": "string|null (required)",
    "rollbackHint": "string|null (required)"
  },
  "SkillDescriptor": {
    "name": "string", "risk": "R0|R1|R2|R3 (required)",
    "requiredPerms": "string[] (default [])",
    "capabilities": "string[] (default [])",
    "requiredArgs": "string[] (default [])",
    "sideEffect": "boolean (required)",
    "sandboxPolicy": "string|null (required)",
    "commandTemplate": "string|null (default null)",
    "requiresPlanApproval": "boolean (default false)"
  },
  "ExecutionContext": {
    "sessionId": "string|null", "taskId": "string|null", "tenantId": "string|null",
    "agentId": "string|null", "ownerUserId": "string|null",
    "tainted": "boolean (default false)",
    "mode": "ARCHITECT_PLANNING|DEV_EXECUTION|AUDIT_REVIEWING (required)",
    "cancellationToken": "opaque|null"
  },
  "SkillResult": {
    "success": "boolean", "code": "string (required, success = OK)",
    "message": "string|null", "output": "any|null", "approvalTicketId": "string|null"
  },
  "ApprovalTicket": {
    "id": "string", "taskId": "string|null", "tool": "string",
    "riskLevel": "R0|R1|R2|R3", "impactNote": "string|null", "rollbackPlan": "string|null",
    "status": "PENDING|APPROVED|DENIED|EXPIRED"
  }
}
```

`text` 不进契约（Java 明确禁止建议文本）；SDK 的 `force`、`invocationId`、`description`、`auditId`、`ticketId`、`mac` 如需保留，只能作为**语言本地扩展**，不得出现在 wire 中。

### 6.3 统一错误码与别名映射

以 `ErrorCodes.java` 为**唯一权威集合**，补齐 Java 中散落的字面量常量，并按别名收敛：

| 规范码 | 别名（各语言现有写法，过渡期允许输入、输出一律用规范码） |
|---|---|
| `INTENT_FORMAT_INVALID` | Python `INTENT_FORMAT_ERROR`、TS `INTENT_INVALID`、Python `SCHEMA_VIOLATION`、TS `SCHEMA_MISMATCH` |
| `R3_DENIED` | Python/TS `RISK_REJECTED` |
| `PENDING_APPROVAL` | Python/TS `APPROVAL_REQUIRED` |
| `CAPABILITY_NOT_ALLOWED` | Python/TS `CAPABILITY_EXCEEDED` |
| `TAINTED_WRITE_BLOCKED` | Python `TAINT_BLOCKED` |
| `MODE_TOOL_NOT_ALLOWED` | Python `MODE_NOT_ALLOWED`、TS `MODE_DENIED` |
| `SANDBOX_UNAVAILABLE` | Python `SANDBOX_VIOLATION`、TS `SANDBOX_DENIED` |
| `INTERNAL_ERROR` | ~~TS `EXECUTION_ERROR`~~ —— **本轮不归一**：语义未澄清（§6.3 要求先澄清），列入 `contract/error-codes.json` 的 `unmappedRequiresReview`，统计时只算普通拒绝 |
| `UNGOVERNED_INVOCATION` / `COMMAND_TEMPLATE_MISMATCH` / `INPUT_REJECTED` / `PLAN_APPROVAL_REQUIRED` | 已同名，保持不变 |

`OK` 为唯一成功码；SDK 成功结果必须补 `code="OK"`。TS 独有的 `AUDIT_FAILED`、Python 独有的 `APPROVAL_EXPIRED` / `APPROVAL_SELF_DENIED` 需评审后决定是纳入规范集合还是降级为本地错误。

**已落地部分（2026-11-11）**：`contract/error-codes.json` 收编 30 个规范码（含 `OK` 与 5 个原本散落的 Java 字面量）、12 条别名映射、20 条 golden；三语言各有薄绑定（Java `ErrorCodeCatalog` / Python `codes.py` / TS `codes.ts`），提供 `canonicalize` 与统一 `countsAsDenied`。方向 C / M1 通过 `--normalize-aliases` 显式开启后即可按同一口径统计 SDK 别名证据；默认仍只认 Java 规范码（D-3）。

**`SkillResult` 结构统一已落地（2026-11-12）**：`code="OK"` 已补齐，三语言 `toWire()` / `to_wire()` 输出同一份 5 字段 camelCase 结构，golden 见 `contract/skill-result.golden.json`（5 个 case，含别名归一）。**仍未做**：`sideEffect` / `tainted` / 计划审批强制、审计链统一、跨语言结构 golden 全量对账。

### 6.4 统一边界与默认值

| 项 | 规范 |
|---|---|
| 未知/空 `risk` | **R2**（fail-closed，取 Java 语义） |
| `confidence` | 0.0–1.0；`< 0.5` → `NEED_MORE_INFO` |
| `reason` | 含「建议」/ `suggest` / `you may consider` → `INTENT_FORMAT_INVALID` |
| R3 | 一律 `R3_DENIED`，`force` 无效（字段移出契约） |
| R2 | 生成审批单 → `PENDING_APPROVAL`，由人工决策，不得直接拒绝 |
| `requiresPlanApproval=true` | 未批准 → `PLAN_APPROVAL_REQUIRED`（三语言都必须强制） |
| `tainted && sideEffect` | `TAINTED_WRITE_BLOCKED`（三语言都必须实现） |
| 命令模板 | 总长 2048 / 单值 256 / 参数 16；禁 `\t\n\r` 与控制符；单值槽禁 `-`/`~`/`#` 开头；`{name*}` **至少 1 词**；空白模板视为未声明 |
| 意图参数卫生 | 长度上限、控制字符、路径穿越、参数个数上限（对齐 `IntentArgsValidator`） |

### 6.5 统一审计链

```
seq       : 从 1 开始（Java 语义）
genesis   : "GENESIS"
payload   : 规范化 JSON（§6.1 规则 5），action 与 payload 之间不含歧义分隔符
摘要输入   : seq + "|" + action + "|" + canonicalJson(payload) + "|" + prevHash
timestamp : 记录但不参与摘要，统一 ISO-8601 UTC 带 Z
算法       : HMAC-SHA256（密钥来自环境变量）；无密钥时显式标记降级，不得静默等价于 SHA-256
落盘键     : camelCase（prevHash / hash / mac），每语言读写同一格式
```

已有数据迁移：为存量链打 `chainVersion` 标记，旧链按旧算法校验、新链按新算法，**不允许就地重算**（会破坏证据）。

## 7. 对账结论

| 层次 | 结论 |
|---|---|
| L1 REST 管理接口 | ✅ **通过**（1 处 P1：TS `counters` 类型声明与服务端动态 Map 不符） |
| L2 进程内治理契约 | ❌ **不通过**：字段集、命名、必填性/默认值、错误码、接口签名、边界条件均未统一，且 SDK 在 4 处安全语义上比 Java 宽松 |
| L3 审计证据 | ❌ **不通过**：哈希公式与落盘格式互不兼容，跨语言无法互验；SDK 无 HMAC 防重算能力 |

**总判定：不能宣称「三语言契约一致」。** 现有 108/108、91/91 单测只证明各 SDK 内部自洽，
它们各自对齐的是「core 的一部分概念」，不是同一份契约。当前可对外表述的只有：
「REST 治理管理接口对齐；进程内治理契约正在对账」。

**建议的推进顺序**（2026-11-12 进度）：
1. ✅ 静态对账 + 统一基准建议稿（本文）
2. ✅ **定稿 §6 基准**：`contract/towndemontower-wire.schema.json` + `contract/error-codes.json`（三语言共用，唯一权威）
3. 🟡 **部分完成**：错误码别名映射 + 常量补齐 + 三语言归一绑定 + 统计口径打通（golden 20 条）、**`SkillResult` wire 结构统一**（`contract/skill-result.golden.json` 5 个 case、`toWire()` / `to_wire()`、成功码 `OK`、本地字段兼容保留）；**未做** `sideEffect` / `tainted` / 计划审批强制、其余 4 个数据结构的 wire 出入口
4. ⬜ 审计链统一 + `chainVersion` 迁移方案（改动最大，须单独评审，**不允许就地重算**）
5. ⬜ 写跨语言 golden 用例：同一批输入在三种实现上比对 `risk`、`code`、`audit hash`、`ticket`，纳入 CI
6. ⬜ 全部通过后，才把 README / `docs/08` 的措辞改回「对齐 core 契约」

> 当前状态：**统一基准已定稿、跨语言统计口径打通、`SkillResult` wire 结构统一**，
> 但其余结构、安全语义与审计链实现未统一，因此总判定「不能宣称三语言契约一致」不变；
> 第 6 步仍未到可以做的时候。

> 与 `docs/08` 方向 D 的关系：方向 D 的「跨语言契约一致性」不是写几个用例就能关掉的项，
> 它前置依赖一份**权威 wire schema**；在 schema 定稿前写对账用例，只会把当前的分歧固化成测试断言。
