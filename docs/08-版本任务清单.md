### 方向 C · 审计驱动的动态防御（AuditAnalyzer，对应 B-3）

> 这是四条方向里**与既有基线冲突最多**的一条；**M1（方案 1 只读报告）已于 2026-11-11 实现**，M2 / M3 仍不排期。PM 需求说明、实测结果与逐条假设见 `docs/36-方向C-需求说明.md` §12。
> 下面保留冲突清单与可选路径，作为需求说明与后续 M2 的上游依据。
> 观点原意：定期扫审计哈希链，某个 `agentId` 频繁触发 `PENDING_APPROVAL` 就自动降置信度 / 24 小时内只放行 R0/R1。
> 名词对照：笔记里的 `R2_PENDING` 即本仓 `PENDING_APPROVAL`；当前审计链「只写不分析」，v1.17 管理接口只提供查询与链校验。

#### C.1 冲突清单

| # | 冲突对象（既有基线 / 现状） | 为什么冲突 |
|---|---|---|
| C-1 | **v1.6 权限只能显式下发**：`auto-grant-declared-perms=false`，权限只经 `permissions-bootstrap` 或 Agent 注册表下发 | 「后台按行为自动降权」等于绕过显式授权入口，静默改写某个 `agentId` 的可执行范围；降权虽是收紧，仍是一次无人批准的权限变更 |
| C-2 | **v1.5 模式只能由状态机推进**（`GovernedModeSession`） | 「只放行 R0/R1」若实现为切模式，就绕过了状态机；若实现为工具白名单收紧，也要先定它与 `ModeToolPolicy` 谁优先，否则两条规则互相覆盖 |
| C-3 | **审计链的定位：只追加、可校验的证据**（SHA-256 链 + HMAC + 外锚） | 把审计日志当控制输入，等于让「证据」直接驱动「裁决」。日志被重放、重复上报或注入时，可反过来制造拒绝服务：把正常 Agent 刷成高频 PENDING，诱使系统降权。证据必须是只读的 |
| C-4 | **v1.13 / v1.17 审批由人工决策、机制层钉住**（`TrustedApprovalPolicy`、14 个只读 + 人工决策管理接口） | v1.17 刻意不开放「模式切换 / 权限授予 / 放行 R3」等高风险能力。自动降权若不经人工确认，等于给后台开了一条「无人批准也能改权限」的新通道，正好踩在这条边界上 |
| C-5 | **v1.15 `TimeProvider` 契约 + 可回滚要求** | 「24 小时」是时间窗：必须走 `TimeProvider`、可测试、重启后仍生效；否则重启即恢复权限，行为不一致，也无法回放与回滚 |
| C-6 | **fail-closed / 默认安全** | 分析器挂掉、数据不足、链校验失败时怎么办？保持原状（等于不降权）、全拒（业务停摆）、还是沿用上次结论？没有定义就会产生新的静默失效面 |

#### C.2 可选方案

| 方案 | 做法 | 与基线冲突 | 代价 / 前置条件 | 结论 |
|---|---|---|---|---|
| **1 · 只出报告（观察态）** | 定时扫审计链，按 `agentId` 统计 `PENDING_APPROVAL` / R3 / 拒绝率，产出**只读**报告（挂 v1.17 管理端点或离线 CLI）；不改权限、模式、闸门 | **无**：分析器只读，输出是信息不是裁决 | 新增只读分析器 + 报告格式；报告需脱敏，不回显审计原文 | ✅ **推荐先做** |
| **2 · 建议单 + 人工批准（半自动）** | 分析器产出「降权建议单」，进 `ApprovalCenter` / v1.17 审批端点；人工批准后才由注册表**显式**下发，TTL 到期自动失效并留痕 | **低**：写操作走既有审批 + 显式授权通道 | 复用审批中心、计划单落盘与 `TimeProvider`；需新增建议单类型与到期回收 | ✅ **推荐目标态** |
| **3 · 全自动降权（限定作用域）** | 后台按规则自动收紧，但**只改本次调用的风险上限**，不写权限表、不切模式；带 TTL、一键回滚、每条变更进审计 | **中高**：仍属机制侧自动裁决，须先解决 C-3 / C-4 | 必须满足 §C.3 全部前置条件，且默认关闭、显式配置才启用 | ⚠️ 条件满足后再评估 |
| **4 · 不做** | 维持「审计只写不看」，靠人工看报表 | 无 | 零成本，但审计数据价值没用起来 | 可接受的下限 |

#### C.3 若最终选方案 3，必须先满足

1. 分析器**只读**审计链；所有变更只能产出「建议 / 风险上限调整」，不得直接写权限表或 `AgentMode`。
2. 每条自动调整都进审计哈希链（含触发依据的审计区间、规则版本、TTL、`TimeProvider` 时间戳），可回放、可一键回滚；审计链本身**不因回滚被改写**。
3. 分析器不可用 / 数据不足 / 链校验失败时，**退化到方案 1（只报告）**：既不静默放行，也不全拒业务。
4. 默认关闭，显式配置才启用；规则变更需人工审批（复用 v1.17 审批端点），并纳入方向 D 的跨语言契约一致性用例。

### 方向 D · 跨语言契约一致性

**第一、二步已完成（2026-11-10 / 11-11）**：静态契约对账见 `docs/35-跨语言契约对账.md`；**wire schema 与错误码口径已定稿**，落在仓库根 `contract/`（`towndemontower-wire.schema.json`、`error-codes.json`），三语言归一绑定与统一 `countsAsDenied` 口径已打通，一致性由 `contract/verify_codes.py` 校验。方向 C / M1 可用 `--normalize-aliases` 按同一口径统计 SDK 别名证据（默认关闭，保持 D-3）。

**总判定不变**：REST 管理接口层基本对齐，但**进程内治理契约未对齐、审计链格式互不兼容，当前仍不能宣称「三语言契约一致」**——基准定稿不等于实现符合。

v2.0 已排期的「SDK 联调与契约一致性测试」延伸为长期方向：下一步是 `SkillResult` 结构统一、`sideEffect` / `tainted` / 计划审批强制，再写同一输入在三种实现上比对风险级、错误码、审计摘要与审批单的 golden 用例并纳入 CI；审计链统一须单独评审，**不允许就地重算**。它是方向 C 的前置——先有可对齐的链与口径，才谈得上用链驱动防御。

### 方向间的关系（不冲突约束）

- A / B / C / D **彼此独立，可分别排期**；任何一条都不得修改「模式状态机」「显式授权」「审计链只追加」三处基线。
- 依赖顺序只体现在数据可信度上：C 依赖 A 的「链可信 / 内部故障不静默」与 D 的「对账口径」，不依赖 B。
- B-1 的回滚只回滚业务态、B-2 默认关闭、B-4 隔离演练，都是为了避免新方向反过来引入新的绕过面。

> **定级建议**：A-2 / A-4 只是核对与文案，成本最低；A-1、B-1、B-2 属 P1 候选；方向 C 先做方案 1（只出报告），再评估方案 2，**方案 3 在原则未定前不排期**；B-4 与方向 D 可挂到 v2.0 质量验证项下一起做。
