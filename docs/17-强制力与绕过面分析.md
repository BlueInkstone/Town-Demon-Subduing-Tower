# 强制力边界与绕过面分析

> 结论先行：本项目的管理机制是**框架层（进程内）强制**，不是操作系统层、更不是内核层强制。
> 治理边界 = JVM 进程边界。它挡得住"用错"，挡不住"想绕"。

## 1. 三层强制力的判定

| 层级 | 强制机制 | 本项目是否具备 | 判定依据 |
|---|---|---|---|
| **内核层** | seccomp-bpf / LSM(AppArmor,SELinux) / namespaces / cgroups：由内核在系统调用处拒绝 | ❌ 无 | 全仓无 seccomp、无 eBPF、无 LSM profile、无 `unshare`；JVM 启动参数与容器配置中均无相关项 |
| **操作系统层** | 独立用户 / chroot / 文件权限 / 独立进程 / 容器 | ⚠️ 局部、可选 | 仅 `SandboxStrategy` 一族涉及 OS 边界，且**只覆盖被声明为 shell 的工具**；默认装配的 `ProcessSandboxStrategy` 与宿主同用户、同文件系统、无 chroot |
| **框架层** | Spring AOP 代理 + 装饰器链 + 内存策略对象 | ✅ 是 | `ExecutorFactory.buildDefault` 用 `new` 逐层包出对象链（`ExecutorFactory.java:29-39`），`AgentSkillAspect` 用 `@Around("@annotation")` 拦截（`AgentSkillAspect.java:63`） |

**判定要点**：强制力的来源是"Java 方法调用必须先经过 Spring 代理对象"，而不是"内核拒绝某个系统调用"。这意味着治理的适用范围不是"这台机器上的写操作"，而是"经由被代理的那几个方法发起的调用"。

`SandboxedToolExecutor` 这个名字容易误读：它不创建沙箱，只是链尾的一个普通类（`SandboxedToolExecutor.java:16`），实际执行是 `invoker.invoke(...)` → AOP 里就是 `pjp.proceed()`（`AgentSkillAspect.java:91`），**在被治理对象所在 JVM 内直接反射调用**。所谓"Sandbox"环节在默认装配下是空壳。

唯一真实的 OS 边界是可选的 Docker 路径：`DockerSandboxStrategy` 会拼 `--network none --memory 128m --cap-drop ALL --read-only`（`DockerSandboxStrategy.java:78-99`），但它是另一条 Executor 实现（`DockerSandboxExecutor`），需显式替换链尾才生效，且只用于 shell 类工具。

## 2. 绕过途径（按"谁能做到"分层）

### 2.1 业务开发者：零成本、静默失效

| # | 途径 | 机制 | 后果 |
|---|---|---|---|
| B1 | **自调用** `this.restart()` | Spring AOP 基于代理，`this` 是裸对象，不经过代理 | 治理完全跳过，**审计里一行都没有**；无报错 |
| B2 | `private` / `final` / `static` 方法加注解 | CGLIB 无法覆写 | 注解是装饰品，调用不受管 |
| B3 | 直接调下层 Service（Controller 不经过 `@AgentSkill` 方法） | 治理点是注解，不是能力 | 同一 JVM 内任何代码都能绕过；"写注解才受管"意味着**不写就不受管** |
| B4 | 工具方法体内自己做 IO | 治理只覆盖"入口那一次调用"，不覆盖其副作用 | `Runtime.exec` / `Files.write` / JDBC / HTTP 全在链外 |

B4 是最本质的一条：**治理的对象是"调用"，不是"效果"**。RBAC 检查的是"你能不能调 `writeFile`"，不是"这个进程能不能写 `/etc`"。

### 2.2 有 Spring 配置权：换实现即换规则（官方支持）

`TownDemontowerAutoConfiguration` 的每个组件都是 `@ConditionalOnMissingBean`（第 70-138 行），设计意图是"可替换"，副作用是**"替换"等于"取消"**：

| # | 途径 | 效果 |
|---|---|---|
| C1 | 自定义 `RiskGate` Bean 恒返回 `R0` | 风险闸门失效，R3 命令按 R0 放行，链结构不变、审计照写 |
| C2 | 自定义 `AuditStore` 空实现 | 审计链归零，`verifyChain()` 永远 true |
| C3 | 自定义 `ApprovalPolicy` 恒 `APPROVED` | 所有 R2 直接放行 |
| C4 | 自定义 `Executor` Bean | 整条链被替换，`@AgentSkill` 仍在，但不再有 10 个环节 |
| C5 | `towndemontower.enabled=false` | 切面不装配（`TownDemontowerAutoConfiguration.java:60-61`），注解彻底失效 |
| C6 | `towndemontower.auto-grant-declared-perms=true`（**默认值**） | 谁写注解谁给自己授权（`AgentSkillAspect.java:132-134`），绕开注册表的授权流程 |

C1~C4 都不需要改一行 core 源码，也不需要重启到"异常状态"——**系统看起来完全正常，审计链也是"合法"的**，只是规则被换成了恒真。这比攻击更危险的地方在于：它不留任何痕迹。

### 2.3 提权与身份伪造

| # | 途径 | 说明 |
|---|---|---|
| D1 | 直接调 `PermissionEngine.grant(agentId, "*")` | `grant` 是 public 方法（`PermissionEngine.java:25`），任何持有该 Bean 的代码都能自我授权；**此操作不写审计**（审计只在装饰器链上） |
| D2 | 反射改 `ExecutionContext` / `IntentObject` | 两者都是普通 POJO，`ExecContext` 可任意构造；改 `agentId` 即换身份 |
| D3 | 反射改私有字段 | `setAccessible(true)` 在 JDK 21 默认仍允许（未开 `--illegal-access=deny`）；可把 `PermissionEngine.agentPerms` 直接塞满 |
| D4 | 置 `SnapshotService.failNext=true` | 该字段是 `public volatile`（`SnapshotService.java:16`），可让所有写操作失败（DoS）；`snapshots` 是 `public final List`（第 15 行），可直接 `clear()` 抹掉快照记录 |

**但 D 类在当前形态下意义有限**，因为存在一个更彻底的问题：

> REST 层没有任何认证。`AgentController` 构造 `ExecutionContext` 时 `agentId` 直接取 `props.getAgentId()`（`AgentController.java:278-281`），不看请求头、不看 token。
> 也就是说：**所有能访问 8081 端口的人，都是同一个主体 `agents-console-agent`，都持有 `agents:read` + `agents:write`。**
> 这里不存在"越权"，因为不存在"区分"。提权的前提是有权限边界，而这一层还没有边界。

### 2.4 直接调底层 API（出治理面）

| # | 途径 | 说明 |
|---|---|---|
| E1 | 工具方法体内起子进程 | 见 B4；`ProcessSandboxStrategy` 即使启用，也是 `sh -c`（`ProcessSandboxStrategy.java:58-62`），**与 JVM 同用户、同文件系统、无 chroot、无 cgroups**——只是换了个进程，没换权限 |
| E2 | Docker 沙箱加参数 | `extraArgs` 原样拼在 `docker run` 上（`DockerSandboxStrategy.java:94`），可注入 `-v /:/host`、`--privileged`、`-u 0`；`--read-only` 被 `-v` 挂载卷穿透 |
| E3 | docker CLI 权限即宿主机权限 | 沙箱由 JVM 用户执行 `docker`（第 118 行）；该用户在 `docker` 组时**等价于宿主机 root**，容器隔离形同虚设 |
| E4 | 网络 | `--network none` 有效，但仅对走 Docker 的工具；走 Process 沙箱或方法体内 HTTP 时不受限 |

E1 的要点：`--cap-drop ALL` 之类是**容器运行时**对容器内进程的约束，管不到"没进容器的那个进程"。

### 2.5 修改配置文件 / 审计数据

| # | 途径 | 说明 |
|---|---|---|
| F1 | 启动参数覆盖 | Spring 属性优先级：命令行 `--towndemontower.enabled=false` > 环境变量 > 配置文件。能改部署命令的人可直接关治理 |
| F2 | 改审计存储 | 默认 `HashChainAuditStore` 是内存 `List`（`HashChainAuditStore.java:16`），进程重启即丢；`append(AuditRecord)` 是 public（第 21 行），可注入**任意自洽记录** |
| F3 | 整链重写 | 哈希链是 SHA-256 明文链，**无 HMAC、无私钥、无外部锚定**。攻击者拿到写权限后可重算整条链，`verifyChain()` 照样返回 true |
| F4 | 落库版 | 走 v1.2.1 的 `GovernanceDecisionRepository` 时是普通 JDBC 表，无 append-only 约束、无触发器，DBA 可 `UPDATE` |
| F5 | 改代码重打包 | core 零依赖、单 jar，改 `ExecutorFactory` 一行即换链 |

F3 是审计设计上最需要说清的一点：**哈希链保证的是"断链可见"，不是"篡改不可能"**。前者防误删、防局部改动；后者需要密钥或外部时间戳锚定，当前都没有。

## 3. 五个具体高危点（代码级）

1. **风险闸门的参数名依赖**
   `DefaultRiskGate` 只在 `intent.args.get("command")` 是 `String` 时才过 AST（`DefaultRiskGate.java:33-35`）。参数名叫 `cmd` / `script` / 放在 `List` 里 → AST 完全不执行，风险退回注解声明值。而注解里的 `risk` 是**被治理者自己写的**。等于"自己申报风险等级"。
2. **AST 规则是正则黑名单**
   `SimpleShellAstAnalyzer` 匹配 `rm -rf` / `kubectl delete` / `drop table` / 重定向（第 17-22 行）。`rm -r -f`（拆开）、`find -delete`、`shred`、`dd of=`、`base64 -d | sh` 全部不在名单内。
3. **`autoGrantDeclaredPerms` 默认开启**
   与 v1.4"注册表是 RBAC 权威来源"直接冲突：写注解即授权，注册表被架空。
4. **"快照"不能回滚**
   `SnapshotService.beforeWrite` 只是往 `List<String>` 里加一行 `SNAP[...] args=... rollback=...`（`SnapshotService.java:19-27`）。没有文件副本、没有 diff、没有恢复入口。**"写前快照"实际是"写前记一笔日志"。**
5. **污点标记是静态布尔**
   `ctx.tainted` 来自配置 `props.isTainted()`（`AgentSkillAspect.java:85`），全进程一个开关。没有数据流追踪：模型读了不可信网页，`tainted` 不会自动变 true。

## 4. 风险分级（按攻击者位置）

| 攻击者位置 | 可控途径 | 可否彻底绕过 | 现实风险 |
|---|---|---|---|
| 业务开发者（无意误用） | B1~B4 | 静默绕过且无感知 | **高**：这是最常发生的，且没有任何告警 |
| 有代码提交权 | B/C/F5 | 可以 | 中高：可留 code review 痕迹 |
| 有配置/部署权 | C1~C6、F1 | 可以，且系统看似正常 | **高**：无痕 |
| 有宿主 root / docker 组 | E2~E4、F3/F4 | 可以 | 高：审计链可重算 |
| 能访问 HTTP 端口（任意人） | D 类简化版 | 不需要绕过，直接就是最高权限 | **高**：无认证 |

## 5. 这个机制到底能承诺什么

**能承诺**（当前实现，可验证）：
- 走注解的调用路径上，10 个环节一定按固定顺序执行，跳过不了（除非改代码/换 Bean）；
- 被拒绝的调用同样进审计（`AuditDecorator` 在 try/catch 两侧都写，`AuditDecorator.java:28-39`）；
- 内存审计链的局部篡改可被发现（`verifyChain` 重算比对）；
- Docker 不可用时 fail-closed（`SANDBOX_UNAVAILABLE`），不静默降级为无隔离。

**不能承诺**：
- 不能防住"不写注解"的调用；
- 不能防住"换一个恒真的策略 Bean"；
- 不能防住"改配置关掉开关"；
- 不能防住"在工具方法体里自己开子进程"；
- 不能防住"重算哈希链"；
- 不能防住"未认证的 HTTP 调用者"。

一句话定位：**它是"同信任域内的防误操作 + 事后追溯"机制，不是"跨信任域的防恶意"机制。**

## 6. 加固顺序（若要把边界往外推）

| 优先级 | 措施 | 针对 |
|---|---|---|
| P0 | 关闭 `auto-grant-declared-perms` 默认值，权限只能从注册表下发 | C6 |
| P0 | REST 层加认证，`agentId` 取自凭据而非配置；端口默认不做公网暴露 | D 类简化版 |
| P0 | 危险工具改"白名单命令模板"而非自由 shell；风险等级由 `SkillRegistry` 侧定义，不接受注解自报 | 高危点 1、2 |
| P1 | 启动参数/环境变量绕过检测：启动时若 `enabled=false` 或策略 Bean 非内置实现，打印显式告警并写审计首条 | C1~C5、F1 |
| P1 | 审计链加 HMAC（密钥来自 `CredentialBroker`）+ 周期性把链头哈希外发/落独立的只增表 | F3、F4 |
| P2 | 快照改为真实文件副本 + 恢复入口，否则从功能列表里删掉"可回滚" | 高危点 4 |
| P2 | 全工具强制走 Docker 且禁止 `extraArgs` 注入挂载；沙箱 CLI 用独立低权用户执行 | E1~E3 |
| P2 | 污点追踪接到真实数据流（读外部内容 → 标记会话），而非静态配置 | 高危点 5 |
