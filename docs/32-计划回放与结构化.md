# 32 · 计划回放与结构化（v1.14）

> v1.13 交付了计划审批闸门，但留了两个边界：计划单只在内存、批准范围只到任务。
> v1.14 把这两个边界收掉，同时保证旧调用方零改动。

---

## 1. 结构化计划

### 1.1 模型

```java
PlanArtifact plan = PlanArtifact.of("发布 order-service", List.of(
        PlanStep.of("applyPatch", "改三个配置文件"),
        PlanStep.of("runTests", "跑回归"),
        PlanStep.of("", "人工复核")));

String id = plans.request("agent-1", "task-1", plan);
plans.approve(id, "human-1", "同意");
```

- `PlanStep.tool` 是这一步允许使用的工具名；为空表示"只写意图、不绑定工具"。
- `PlanStep.intent` 必填，避免出现空步骤。
- `PlanArtifact.tools()` 去重并保留声明顺序，供闸门判断覆盖范围。

### 1.2 闸门语义

| 计划形态 | 放行范围 |
|---|---|
| 只有摘要（`PlanArtifact.text`，v1.13 旧格式） | 任务级：该任务内所有声明 `requiresPlanApproval` 的工具 |
| 有步骤，但没有一个步骤点名工具 | 任务级（同上） |
| 有步骤且点名了工具 | **只放行名单里的工具** |
| 计划已批准但工具不在名单 | `PLAN_APPROVAL_REQUIRED`，文案回显计划单号与覆盖范围 |

一个只写意图、不写工具名的步骤**不会**顺带放行任何工具。这是刻意的：
"看看再说"不是一张空白支票。

### 1.3 扩大范围：显式修订

`request` 对已批准任务幂等（防止重复提交把批准单顶掉），所以"批准后发现还要多用一个工具"
不能靠 `request` 扩范围，改用：

```java
String revised = plans.revise("agent-1", "task-1", PlanArtifact.of("改删都要", List.of(
        PlanStep.of("applyPatch", "改代码"),
        PlanStep.of("deleteFile", "删临时文件"))));
plans.approve(revised, "human-2", "同意扩范围");
```

- 新单是 `PENDING`，旧单保留可追溯；
- 新单批准前，该任务的**所有**计划要求工具都暂停（fail-closed），不留"旧批准继续用"的空档；
- 最新单已是 `PENDING` 时 `revise` 复用，不堆待办；
- 审计动作记为 `PLAN_REVISED`。

## 2. 计划单回放

### 2.1 存储 SPI

```java
public interface PlanApprovalStore {
    void save(PlanApproval approval);   // 每次状态流转追加快照
    List<PlanApproval> load();          // 启动时按写入顺序回放
}
```

- 默认 `InMemoryPlanApprovalStore`：单测/脚本/内嵌场景，行为与 v1.13 一致。
- `FilePlanApprovalStore`：追加写文件，启动回放。
- Spring 自动配置默认装配文件存储，路径 `<state-dir>/plans.log`，可用
  `towndemontower.plan-file` 显式覆盖。

### 2.2 文件格式

```
#PLAN-STORE v1
b64(id) \t b64(agent) \t b64(task) \t b64(summary) \t STATUS \t requestedMs \t decidedMs \t b64(by) \t b64(note) \t stepsEnc
```

- 每个自由文本字段单独 Base64，换行/Tab/中文不会破坏行结构。
- `stepsEnc` 为 `b64(tool):b64(intent)` 逗号连接；Base64 URL 字母表不含 `:` `,`，无需二次转义。
- 每次提交、批准、否决各写一条完整快照；回放时同 id 后写覆盖先写。

### 2.3 回放规则

1. **单号续接**：加载时把序号推到历史最大值，重启后新单号继续递增，不撞旧单。
2. **最新单确定性**：先比 `requestedAt`，同毫秒再比单号序号；不依赖 Map 遍历顺序。
3. **损坏即拒绝**：任一无法解析的行抛 `IllegalStateException`，应用启动失败。
   不跳过、不猜测——计划是审批事实来源，"读不出来当没有"会让已批准任务重新被拦，
   更糟的是让不该放行的计划被当成不存在。

## 3. 三个刻意的取舍

1. **追加写、不回改**  
   文件线性增长，但任何时刻的状态都能回放，不需要在审批链里做隐式清理；
   压缩/归档留给运维侧。
2. **结构化才收窄**  
   只有显式工具名才构成范围，避免"写了个步骤就默认全放行"。
3. **坏文件拒绝启动**  
   可用性让位于审批事实的完整性；生产应把文件放在受控目录，并配合审计哈希链对账。

---

## 4. 如实标注的边界

- 追加式存储**不自动压缩**；状态变更频繁时需要轮转/归档。
- 本地文件**无签名**：防误读不防篡改；生产环境应放在受控目录并配合审计对账。
- 计划仍是"人给的方案"，本版不包含自动规划器。
- 审批仍是任务级身份 `(agent, task)`；计划范围解决的是"工具粒度"，不是"步骤顺序/依赖"。
- 同一任务已批准后，重复 `request` 幂等返回原单（v1.13 语义）；扩大范围必须走显式
  `revise` 并重新审批，不存在"静默替换已批准计划"的路径。
