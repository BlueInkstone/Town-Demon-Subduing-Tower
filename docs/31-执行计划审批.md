# 31 · 执行计划审批（v1.13 / Plan-and-Execute 入口）

> 错误码 `PLAN_APPROVAL_REQUIRED` 从 v1.0 起就在表里，但一直没有**产生方**。
> 本版把"先出方案、人工确认后再动手"从文档承诺变成可执行闸门。

---

## 1. 它解决什么问题

高风险工具（改配置、删数据、批量发布）不能由 agent 看到就做。治理链需要一条**任务级**卡点：

1. agent 先提交"这个任务打算怎么做"的计划；
2. 人（不是提交者自己）批准；
3. 只有计划处于 `APPROVED`，声明了要求的工具才允许执行。

v1.13 之前，`requiresPlanApproval` 并不存在，`PLAN_APPROVAL_REQUIRED` 也从未被返回——
也就是说这条流程在代码里是空的。

---

## 2. 使用方式

### 2.1 工具声明

```java
@AgentSkill(
        name = "releaseService",
        risk = "R2",
        requiredPerms = {"release:apply"},
        requiredArgs = {"service"},
        requiresPlanApproval = true)
public String release(String service) {
    GovernancePass.require("releaseService");
    // 真正的高风险动作
    return "released:" + service;
}
```

缺省 `false`，存量工具零影响。

### 2.2 提交 / 审批

```java
PlanApprovalService plans = ...;           // core 直接 new，Spring 由自动配置注入
String id = plans.request("agent-1", "task-1", "重启 order-service，先备份再滚动发布");

plans.approve(id, "human-1", "同意");       // 审批人不能是 agent-1
// 或 plans.reject(id, "human-1", "窗口期不合适");
```

### 2.3 闸门行为

`RiskGateDecorator` 在**命令模板校验和风险分级之前**检查最新计划：

| 状态 | 结果 |
|---|---|
| 没有计划单 | `PLAN_APPROVAL_REQUIRED`：当前任务尚未提交计划 |
| `PENDING` | `PLAN_APPROVAL_REQUIRED`：文案回显计划单号 |
| `APPROVED` | 放行，继续走后续装饰器 |
| `REJECTED` | 拒绝；必须重新提交，不能直接 `approve` 改口 |
| 声明了要求但服务未装配 | **拒绝**（fail-closed），不把漏配当成不需要审批 |

---

## 3. 三个刻意的取舍

1. **禁自批**  
   提交者不能审批自己的计划，否则"提交 + 自己批"两步就能绕过整条流程。
2. **按 (agent, task) 生效**  
   批的是"这个任务的这份计划"，换任务必须重批；防止一次审批被无限复用。
3. **否决不可补批**  
   `REJECTED` 后再 `approve` 直接抛错。允许"先否再改口"，审批记录就失去意义。

另外，同一 (agent, task) 已有 `PENDING` 或 `APPROVED` 时，重复 `request` 幂等返回原单号：
既避免待办堆积，也避免"多提几次就能换掉已批准的计划"。

---

## 4. 审计

计划生命周期进**同一条审计哈希链**：

| action | 触发 |
|---|---|
| `PLAN_REQUESTED` | 新建计划单 |
| `PLAN_APPROVED` | 人工批准 |
| `PLAN_REJECTED` | 人工否决 |
| `PLAN_REVISED` | v1.14 显式修订（新 PENDING 单） |

payload 只记 `id / agent / task / status / by`，**不写计划摘要**：
摘要由调用方提供，可能含路径、服务名等敏感信息；审批链只需回答"谁在什么时候批了哪张单"。
幂等复用与"重复批准已批准单"不重复记账。

Spring 自动配置把 `AuditStore` 注入 `PlanApprovalService`，所以 `V113PlanWiringTest`
可以直接在审计链里查到提交与批准记录。

---

## 5. 如实标注的边界

- **内存态**：计划单不跨重启留存。重启后闸门仍 fail-closed（重新提交即可），
  但"跨重启回放"尚未实现；`all()` 已按可列举设计，便于后续落盘回放。
  → **v1.14 已收掉**（见 `docs/32-计划回放与结构化.md`）。
- **任务级粒度**：批准后该任务内所有声明要求的工具都放行，尚未细化到"单工具/单步骤"。
  → **v1.14 已收窄到工具范围**（旧格式计划仍按任务级）。
- **摘要非结构化**：v1.13 只有文本摘要；v1.14 新增 `PlanArtifact/PlanStep`，但仍是"人给的步骤"，不是自动规划产物。
- **不是自动规划器**：本版只提供"计划 → 审批 → 执行"的治理闸门，不替 agent 生成计划。
