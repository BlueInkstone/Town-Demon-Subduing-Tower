# 26 · 锚点副本与回滚检出（I4-c）

> 本文记录 v1.10 的唯一交付项：给审计外锚加一份**本机之外**的证词，
> 用来挡住 v1.9.2 之后仍然敞着的那一类攻击——**把整个目录回滚到旧快照**。

---

## 1. 补的是哪个洞

v1.9.2 之后，审计证据有三个层次：

| 层 | 挡什么 | 挡不住什么 |
|---|---|---|
| 链内哈希（v1.9） | 单条记录被改 | 整链重算、尾部截断 |
| 外锚 MAC（v1.9.2） | 连锚点一起改（没密钥算不出 mac）、尾部截断 | **本地锚点被一起回滚** |
| 锚点副本（v1.10） | **整目录回滚** | 副本收集端本身被删（见 §6） |

前两层都有一个共同前提：**本地那套文件是"当前真实状态"**。而如果攻击者（或者一次
误操作的恢复演练）把 `audit.log` 与 `audit.log.anchor` 一起换回三天前的备份，那么——

- 链是自洽的（三天前它本来就是自洽的）；
- 锚点的 MAC 是对的（那是当时用同一把密钥算的）；
- `mismatch()` 全部通过。

**本地无论怎么校验都发现不了**。唯一能发现它的，是一个"还记得当时写到第几条"的
外部参照物。这就是副本。

---

## 2. 行为

### 2.1 配置

```properties
# 空 = 只有本地锚点（v1.9.2 行为，自检报 ANCHOR_SINGLE_COPY/INFO）
towndemontower.audit-anchor-replicas=file+offhost:/mnt/audit-vault/anchor.ledger,https://collector.example.com:8443/anchor
# 副本不可读/不可写时是否拒绝（默认 true）
towndemontower.audit-anchor-replica-required=true
```

每段一个副本，逗号或分号分隔，三种形式：

| 形式 | 隔离级别 | 用途 |
|---|---|---|
| `file:<路径>` | 权限域（同机） | 挡住"删日志"；`offHost=false`，**自检报 WARN** |
| `file+offhost:<路径>` | 运维声明跨失败域 | 另一块盘 / NFS / 独立挂载点。**声明是声明，框架核不实** |
| `http(s)://<主机>/<路径>` | 真跨主机 | 唯一真正"本机之外"的形式；loopback 地址自动判为 `offHost=false` |

**写错就启动失败**：`s3://bucket/x` 这类无法识别的段落会抛异常并列出可用形式。
理由很直接——拼错的副本地址若被当成"没配"，运维会以为异地证据已经在跑，
这比启动失败危险得多。

### 2.2 写入路径

本地锚点写入后，把同一个快照（`records/hash/mac/at`）推给所有副本：

- **先把所有副本都试一遍**再决定是否抛异常。一个副本挂了不该让后面的副本饿死，
  否则"部分可用"会退化成"全都不可用"。
- `replica-required=true` 且有失败 → 抛 `IllegalStateException`，写入被拒。
  这意味着**审计写不下去时治理调用也会失败**——这是有意的：证据写不下来，
  就不该继续执行可审计的动作。
- `replica-required=false` → 只记进 `replicaErrors()` / `replicaFailures()`，
  自检报 `ANCHOR_REPLICA_BEST_EFFORT`(WARN)。

### 2.3 启动校验

拉回每个副本的最后一行为对账：

| 副本状态 | 判定 |
|---|---|
| 比本地**新**（条数更多） | **拒绝启动**：本地审计被回滚或删除 |
| 条数相同但哈希不同 | **拒绝启动**：日志被改写，或副本属于另一条链 |
| 比本地**旧** | 正常落后（推送失败过 / 副本刚接入），照常启动 |
| 读不出来 | `required=true` 拒绝启动；否则只记入自检与端点 |

**"读得到且与本地矛盾"永远致命，不受 `replica-required` 影响。** 那个开关表达的
是"副本暂时不可用能不能先起来"，不是"证据对不上能不能先起来"。这条区分是本版最
重要的语义边界——把两者混成一个开关，等于给了"副本报警时关掉开关继续跑"这条捷径。

---

## 3. 两份副本读数

实现里刻意留了两份状态，因为它们回答不同的问题：

| API | 含义 | 谁该看 |
|---|---|---|
| `replicaStates()` | 最近一次已知状态（启动核对 + 之后每次推送刷新） | 监控：现在副本落后多少、有没有在失败 |
| `startupReplicaStates()` | 启动核对那一轮的结果 | 排障：这次启动时副本落后了多少 |

为什么需要两份：构造末尾会把锚点重写一遍并推送——**那正是"修复副本落后"的动作**，
于是 `replicaStates()` 里的落后量瞬间归零。如果只保留一份，"这次启动时副本落后 3 条"
这条诊断永远看不到，而这恰恰是判断"副本是不是长期收不到推送"的唯一线索。

同理，`replicaStates()` 不留在"启动那一刻的快照"：副本恢复后端点还报着红、
新接入副本永远显示空——两种都会让人不再信任这个读数。

## 4. 可观测

`/integrity`（`metrics-endpoint=true` + `X-Governance-Token`）新增：

```json
{
  "auditAnchorReplicas": [
    {"name": "file+offhost:/mnt/audit-vault/anchor.ledger", "offHost": true,
     "records": 1284, "readable": true}
  ],
  "auditAnchorReplicaFailures": 0,
  "auditAnchorReplicaErrors": {}
}
```

自检发现项：

| 码 | 级别 | 触发 |
|---|---|---|
| `ANCHOR_SINGLE_COPY` | INFO | 未配置副本；说明"整目录回滚"仍是敞口 |
| `ANCHOR_REPLICA_NOT_OFFHOST` | WARN | 有副本但都不在本机之外；只做到权限域隔离 |
| `ANCHOR_REPLICA_BEST_EFFORT` | WARN | `replica-required=false` |
| `ANCHOR_REPLICA_DEGRADED` | WARN | 当前有副本处于推送失败状态（附累计次数） |
| `ANCHOR_TOKEN_MISSING` | WARN | 配了 http(s) 副本但 `TOWNDEMONTOWER_ANCHOR_TOKEN` 未设置 |

全部是 INFO/WARN，**没有 CRITICAL**：副本是"证据强度"的增强项，不是启动的前提。
把"没配异地副本"做成拒绝启动，只会让人把它配成一个假地址糊过去。

## 5. HTTP 收集端协议

极简两动作，自建收集端不需要引入任何东西：

```
POST <url>     body: records=1284	hash=<h>	mac=<m>	at=1730000000000
               2xx = 已持久化（收集端不能先回 200 再异步写）
GET  <url>     返回最新一行原文；204 / 404 = 还没有
```

令牌以 `X-Anchor-Token` 头发送，来源 `TOWNDEMONTOWER_ANCHOR_TOKEN`（与门禁密钥、
调用令牌、审计密钥同一规矩：只走环境变量）。**没有令牌也照发**，是否拒绝由收集端
决定——本类不替它做安全判断。

实现用 JDK 自带 `java.net.http`，core 至今零外部依赖。

## 6. 已知代价与未覆盖

**① push 在写路径上，默认每条一次。** `anchorBatch=1`（v1.9.2 的默认，本版不改）
时每条审计一次 HTTP。远端副本请配 `audit-anchor-batch`（如 16）把开销均摊——
代价是落后窗口内尾部截断不可见（见 docs/25 §3）。这是**必须自己权衡**的一组配置，
默认值不替你选。

**② `file+offhost:` 是声明，不是证明。** 框架无法验证那块盘真的在另一个失败域。
写错的声明会静默让隔离级别变成"看起来隔离"。

**③ 收集端本身是单点。** 副本收集端被删（或从未真正持久化却回 2xx），
回滚检出就失效。框架能做的只是"2xx 必须意味着已落盘"这条协议约定。

**④ 副本内容就是锚点，不含日志。** 副本只能证明"当时写到第 N 条、末条是 H"，
不能还原被删掉的内容。取证仍需日志本体（或日志的另一份备份）。

**⑤ 启动校验只比对最新一行。** 账本中途的某行被删，靠 `FileAnchorReplica` 的
MAC 链检出（有密钥时）；无密钥时只靠"条数只能增"这条单调性。

**⑥ 不做重试与异步队列。** 推失败就是失败，要么拒绝写入（required=true），
要么记进计数（false）。不做本地缓冲重放——那会造出"副本看起来跟上了"的假象。

## 7. 验证记录

| 模块 | 数量 | 变化 |
|---|---|---|
| core | **511** | +71（`V19AnchorReplicaTest`） |
| starter | **195**（+tx 14） | +33（`V19AnchorReplicaWiringTest`） |
| delivery | 219 | 不变 |
| agents | 241 | 不变 |
| **全仓** | **1180 / 1180** | +104 |

`V19AnchorReplicaTest` 覆盖：文件副本推送/拉取、账本 MAC 链（删中间行被检出）、
无密钥时靠单调性发现回滚、副本比本地新 → 拒绝启动、条数同哈希不同 → 拒绝启动、
副本落后 → 正常启动、`required=true` 下副本不可读 → 拒绝启动、`required=false`
下同样情形只计入降级、HTTP 副本用 JDK `HttpServer` 走真实 POST/GET、收集端返回
非 2xx 时的失败路径。

`V19AnchorReplicaWiringTest` 覆盖：默认零副本 + `ANCHOR_SINGLE_COPY`、副本真的收到
推送（账本条数与哈希对齐本地锚点）、同机副本触发 `ANCHOR_REPLICA_NOT_OFFHOST`、
`file+offhost:` 消掉该告警、配错地址启动失败且提示可用形式、降级模式报
`ANCHOR_REPLICA_BEST_EFFORT`、`/integrity` 暴露副本条数与失败计数。

过程中修掉一个真问题：`replicaStates()` 原本只在启动核对时写一次，之后不再刷新，
导致副本恢复后端点仍报红、新接入副本永远显示空。改为每次推送后更新，并单独保留
`startupReplicaStates()` 以免启动诊断被"修复动作"抹掉。
