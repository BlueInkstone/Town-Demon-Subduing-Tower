二、为什么只有两档

Java 8 档为什么不能再高

core 与 gateway 的存在意义之一就是"能塞进别人的老系统"。抬到 11 或 17，这一条就没了。 代价是明确的：这两块代码里不许出现 record、var、文本块、 List.of、Stream.toList()、instanceof 模式匹配、箭头式 switch。 写了会被 javac --release 8 当场拦下。

Spring 档为什么下不来

Spring Boot 3.2.5 自己就是 class 61。用 --release 8 去编一个引用它的类， 编译器直接报 class file has wrong version 61.0。这不是本项目的取舍，是上游的硬门槛。

为什么不能抬到 21 / 25

Spring Boot 3.2.5 内嵌的 ASM 读不了 class 69（Java 25）。把三个 Spring 模块的 java.version 写成 25，应用会在扫描自己的自动配置类时抛 ClassFormatException，连启动都到不了——这个坑本项目踩过，且当时 mvn test 返回 Tests run: 0 假绿，把它盖了两天。

已经踩过的第二个坑：增量编译会保留 target/classes 里的旧字节码， mvn install 把 class 65 原样装进本地仓库、再随 lib/ 分发出去， 在 JRE 8 上启动就是 UnsupportedClassVersionError。 只改 pom 里的 release 不会触发全量重编，clean 不能省。

三、三条硬规矩

  • 手写 javac 必须带 --release：core/gateway 用 --release 8， Spring 侧用 --release 17。漏掉它就按本机 JDK 出字节码——这是所有事故的共同起点。
  • 发布走 mvn clean package，不用增量产物；分发包只认 target/ 下的东西。
  • 验收看主版本号：读 jar 内任一 class 的第 7–8 字节，必须是 52 或 61，没有例外。

四、自己复核（三条命令）

# 1) 看每个 jar 的字节码档位（应只出现 52 与 61）
python -c "import glob,zipfile;
for j in sorted(glob.glob('*/target/*.jar')):
    v=sorted({(lambda h:h[6]*256+h[7])(zipfile.ZipFile(j).read(n)[:8]) for n in zipfile.ZipFile(j).namelist() if n.endswith('.class')})
    print(j, v)"

# 2) 用 JDK 8 编 core 并跑测试（JAVA_HOME 指向 JDK 8）
mvn -o -f towndemontower-core/pom.xml test

# 3) 用 JDK 17 跑 Spring 侧（JAVA_HOME 指向 JDK 17）
mvn -o -f towndemontower-spring-starter/pom.xml test
能对外怎么说：core 与 gateway 在 Java 8 和 Java 17 上均可编译并运行（真机实测）； Spring 三模块要求 Java 17；分发必须使用 clean 构建的产物。

五、这份页面没覆盖的

  • 只测了 Windows + HotSpot。ARM、OpenJ9、Linux 没有实测，不要当成同等担保。
  • Spring 三模块的测试跑通了，但 surefire 只认出 4 个 JUnit 用例，其余是 main 自运行器手工跑的； Tests run: 0 不能当"全覆盖"。
  • core 的吞吐压测入口（V114AuditThroughputBench）没计入上面数字，它是压测不是兼容性断言。
