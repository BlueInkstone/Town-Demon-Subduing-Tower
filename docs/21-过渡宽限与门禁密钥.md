# 过渡宽限与门禁密钥来源收敛（v1.7）

> 本期只做两件事，都围绕"变更的破坏性"：
> ① `enabled=false` 从「全放行」改成「全拒绝」是**破坏性变更**，因此给一次性的告警放行窗口；
> ② 门禁密钥**只认环境变量**，删掉系统属性回退与内置开发密钥，缺了就 fail-closed。

## 2. 过渡机制：首次告警放行，之后拒绝

### 2.1 触发条件（三个都成立才进入宽限）

1. `towndemontower.enabled=false`；
2. `disabled-behavior` **不是** `allow`（写了 `allow` 就是知情弃权，走另一条分支，且自检记 CRITICAL）；
3. `legacy-grace=true`（默认）且审计通道可用（`audit != null`）。

### 2.2 状态机

```
        ┌─────────────── 进程启动 ───────────────┐
        │                                        │
   [ARMED] ──第一次被拦的调用──▶ [CONSUMED]
      │                              │
      │  放行 + 审计 + SEVERE 日志    │  之后每次调用
      │                              ▼
      └──────────────────────▶ [DENY]  GOVERNANCE_DISABLED
```

- **只前进不回退**：`consumed` 是 `AtomicBoolean.compareAndSet`，并发首调也只有一个能过；
  没有 TTL、没有按天重置、没有按工具分别计次。
- **要重新武装只能重启进程**（状态在内存，不落盘——落盘会让"重启后又能放行一次"变成可循环的后门）。
- **放行前先留痕**：先 `audit.appendAuto("LEGACY_GOVERNANCE_GRACE", tool|agent|reason)`，再返回放行；
  审计写失败会抛异常（v1.6 规则），因此"留不下痕"就不会走到放行。

### 2.3 三条分支的完整行为对照

| 配置 | 第一次调用 | 第二次及以后 | 自检 findings |
|---|---|---|---|
| `enabled=true`（默认） | 正常过链 | 正常过链 | — |
| `enabled=false` + `legacy-grace=true`（默认） | **放行**（审计 `LEGACY_GRACE` + SEVERE 日志） | `GOVERNANCE_DISABLED` | `GOVERNANCE_DISABLED`(WARN) + `LEGACY_GRACE_ARMED`(WARN) |
| `enabled=false` + `legacy-grace=false` | `GOVERNANCE_DISABLED` | `GOVERNANCE_DISABLED` | `GOVERNANCE_DISABLED`(WARN) |
| `enabled=false` + `disabled-behavior=allow` | 放行（不治理） | 放行（不治理） | `DISABLED_ALLOW`(**CRITICAL**，strict 下拒绝启动) |

### 2.4 为什么宽限是"一次"而不是"一段时间"

宽限窗口越长，越接近一个真实的后门。给**一次**的语义很明确：

- 老应用升级后不会在第一次调用就崩，运维能看到 SEVERE 日志和一条审计；
- 但它换不来"继续跑一天的容忍"——第二次就断，逼着人当晚改配置；
- 攻击者即使能触发第一次，也拿不到持续通道，且留下可检索的审计记录。

### 2.5 已知代价（不掩饰）

宽限放行的那一次调用**不经过整条治理链**（审计、模式白名单、RBAC、RiskGate 全部跳过）。
这是"过渡"的必然代价，因此用五条约束把它压在最小面：只一次、进程级、必须留痕、
必须有人显式开启（默认值可关）、且在自检里持续可见。

## 3. 门禁密钥：只读环境变量

### 3.1 读取路径（唯一）

```java
System.getenv("TOWNDEMONTOWER_GATE_KEY")
```

**没有第二个来源**。V1.5 的 `环境变量 > 系统属性 > 内置开发密钥` 三级回退已全部删除：

| 旧来源 | 删除原因 |
|---|---|
| `-Dtowndemontower.gate.key` | 系统属性会写进 `application.properties`、启动脚本、容器编排文件，也可能被 `jcmd` / 进程转储读出来 |
| 内置 `DEV_KEY` 常量 | 随源码公开，等于没有密钥——攻击者自己算 HMAC 就能伪造"合法签名" |

`KEY_PROP` 常量仍在（标 `@Deprecated`）但**不再被读取**，仅为源码兼容；`usingDevKey()`
语义改为"当前没有可用密钥"，同样标 `@Deprecated`。

### 3.2 校验规则（四道）

| 规则 | 阈值 | 挡住什么 |
|---|---|---|
| 非空 | 去空白后非空 | 未配置 / 只配了空格 |
| 最小长度 | ≥ 32 字符 | `short-key` 这类凑数密钥 |
| 占位值黑名单 | `changeme` / `test` / `secret` / `password` / 原开发密钥串等 16 项 | 从模板里复制粘贴的示例值 |
| 字符种类 | ≥ 12 种不同字符 | `"a"×64`、`"changeme"` 重复四遍这类"长度够但熵为零"的值 |

判定结果只有三态：`OK` / `MISSING` / `WEAK`。**没有第四态叫"用默认值凑合"**。

### 3.3 缺失时的行为（fail-closed，分两层）

| 层 | 时机 | 行为 |
|---|---|---|
| 门禁执行 | `GateScriptRunner.run()` | 直接返回 `GATE_KEY_UNAVAILABLE`，`attempts=0`——**脚本一次都不执行**，不把"验不了"当"验过了" |
| 需要签名 | `SimpleGateScript` 四参构造 / `expectedHash()` | 构造期抛 `IllegalStateException`，异常信息只说缺什么（变量名 + 长度要求），**不回显任何密钥内容** |

### 3.4 启动自检的严重级别（刻意选择）

| finding | 级别 | 理由 |
|---|---|---|
| `GATE_KEY_MISSING` | **WARN** | 门禁脚本默认并未装配。若判 CRITICAL，任何只加依赖、还没用门禁的接入方都会启动失败，直接破坏"四步接入"的承诺。**真正的强制点在 `run()`**：用到就拒 |
| `GATE_KEY_WEAK` | **CRITICAL** | 已经配了却配成一个假密钥，是明确的错误配置，strict 下应当拒绝启动 |

即：**没配**允许启动但用不了门禁；**配错**不允许启动。

### 3.5 测试与内嵌场景

单测不能设置进程环境变量，因此保留显式注入通道：

```java
new GateScriptRunner(executor, keyBytes);                     // 显式注入
new SimpleGateScript(name, cmd, timeout, retry, keyBytes);    // 显式签名
```

这是"把密钥交给对象"，不是"源码里写死密钥"——仓库中不存在任何可用的密钥字面量
（`V17GateKeyEnvTest` 用反射断言 `DEV_KEY` 字段已删除）。

## 4. 顺带推进：容器沙箱加固（I7 / CP-9）

原本排在后面的两项，因为改动集中在同一个类、成本极低，本期一并做掉：

| 项 | 之前 | 现在 |
|---|---|---|
| 运行身份 | 未加 `-u`，`alpine` 默认 uid 0 | 默认 `--user 65534:65534`；显式指定 `root`/`0` 直接抛异常 |
| 进程数 | 无限制 | 默认 `--pids-limit 64` |
| `extraArgs` | 原样拼进命令行 | 白名单 `-u/--user/--pids-limit/--cpus`，其余构造期抛异常 |

`extraArgs` 之所以必须白名单而不是黑名单：`-v /:/host`、`--privileged`、`--net=host`、
`--pid=host`、`--device`、`--security-opt=seccomp=unconfined` 任意一条都足以击穿沙箱，
而黑名单永远追不上 `docker run` 的新旗标。白名单的代价是"以后加参数要改代码"，
这个代价是可接受的——沙箱参数不该由调用方自由扩展。

**I8（Schema 参数白名单）本期未做，理由**：通过 `@AgentSkill` 进入链的参数由
`MethodSignature.getParameterNames()` 从形参名生成，调用方**无法**塞入未声明的键；
真正能夹带参数的是工具实现自己（它直接构造 `Map` 调 core）。因此
`SchemaDecorator` 加白名单挡不住这条路径，而 CP-9 的白名单正好挡在 docker 参数拼装处——
这是同一个风险的正确拦截点。I8 保留为"工具实现可信度下降时"的补充手段。

## 5. 验证

| 模块 | 测试 | 数量 |
|---|---|---|
| core | 原有 5 个套件 143 + `V17GateKeyEnvTest` 24 + `V17SandboxHardeningTest` 26 | **193** |
| starter | 5 + 40 + 24 + 6 | **75**（另有 tx 14 独立计数） |
| delivery | 79 + 43 + 56 + 41 | **219** |
| agents | 78 + 50 + 73 | **201** |
| **全仓** | | **688 / 688** |

新增断言覆盖的关键点：

- 密钥三态判定（长度 / 占位值 / 字符种类）各一条；
- 环境缺失时 `run()` 返回 `GATE_KEY_UNAVAILABLE` 且 `attempts == 0`；
- 环境缺失时四参 `SimpleGateScript` 构造即失败；
- 环境**已配**时走真实读取路径完成一次签-验闭环（同一个测试文件双向覆盖，`skipped` 计数公开）；
- 反射断言 `DEV_KEY` 字段已不存在；
- 宽限：首次放行 + 审计留痕、第二次拒绝 + 审计留痕、**换工具也不重置**、`legacy-grace=false` 首次即拒；
- 沙箱：默认带 `--user`/`--pids-limit`、12 种越界参数逐个断言被拒、白名单参数仍可用且可覆盖默认值。

## 6. 升级指引

```properties
# 情况一：本来就没关治理 —— 什么都不用做
# 情况二：曾用 enabled=false 当"关掉治理"用
towndemontower.enabled=true                 # 推荐：恢复治理
# 或（不推荐，需同时关 strict，且自检记 CRITICAL）
towndemontower.disabled-behavior=allow

# 情况三：使用了门禁脚本 —— 必须设置环境变量
# export TOWNDEMONTOWER_GATE_KEY=<至少 32 字符、≥12 种字符的随机串>
```

> 密钥生成示例：`openssl rand -base64 48`（不要把它写进 `application.properties`，
> 也不要提交进仓库；容器场景用 Secret 挂环境变量）。
