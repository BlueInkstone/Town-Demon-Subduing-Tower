# 墨铠网关接入指南（镇妖塔网关形态）

> 形态范围见 `docs/38-网关形态改造范围.md`；本文件只讲"怎么接"和"**哪些地方现在还不够用**"。
> 最后一次对齐代码：2026-11-12，对齐依据是本地实跑（JRE 8 与 JDK 25 各一轮），不是设计稿。

## 1. 它是什么

墨铠网关是一个**独立可运行的裁决服务**：暴露 `POST /api/evaluate`，调用方在动手前把意图打包成
`IntentObject` 发过来，网关返回"允许 / 拒绝 / 待审批"。**网关只裁决、不执行**——它不替你跑工具，
也挡不住"不调网关就直接执行"的调用方。强制力上限 = 调用方遵守协议的程度。

两点容易误解的实现事实：

- **不是 Spring 服务**。HTTP 用 JDK 内置 `com.sun.net.httpserver`，运行期依赖只有 `towndemontower-core`
  和 jackson（三件）。`src/main/resources/application.properties` 是早期 Spring Boot 方案的遗留，
  **当前代码不读它**，照着改里面的值不会生效（配置方式见 §3）。
- **字节码目标是 Java 8**（class 52），用 `jre1.8.0_511` 实跑通过；构建用 JDK 17。

**版本基线（全仓统一）**：core / gateway 编译到 **Java 8**（class 52）；starter / delivery / agents
编译到 **Java 17**（class 61，Spring Boot 3.2.5 的下限）。**不要再把任何模块抬到 21 / 25**——
Spring Boot 3.2.5 内嵌 ASM 读不了 class 69，会让应用在扫描自动配置类时直接
`ClassFormatException` 起不来（本项目踩过：starter 用 25 编译后，delivery / agents 的 Web 测试全挂）。

## 2. 跑起来

```bash
# 1) core 先进本地仓库（网关按坐标依赖它，不是同仓聚合模块）
cd towndemontower-core
mvn -o clean install -DskipTests

# 2) 打包网关
cd ../towndemontower-gateway
mvn -o clean package

# 3) 运行
INKARMOR_API_TOKEN=你的令牌 PORT=8080 java -jar target/towndemontower-gateway-0.1.0.jar
```

产物是两个东西，**必须一起拷走**：

| 产物 | 内容 | 体积 |
|---|---|---|
| `target/towndemontower-gateway-0.1.0.jar` | thin jar，只有网关自己的 class + Manifest（`Main-Class` + `Class-Path: lib/...`） | 约 15 KB |
| `target/lib/` | `towndemontower-core` + jackson `annotations/core/databind`，共 4 个 jar | 合计约 2.4 MB |

`Class-Path` 里的 `lib/` 是**相对 jar 所在目录**解析的，所以整包可以拷到任意目录、用任意工作目录启动；
但只拷 jar 不拷 `lib/` 会在启动时 `NoClassDefFoundError`。

**打包必须带 `clean`。** 增量编译会保留 `target/classes` 里的旧产物，`install` 会把旧 JDK 编出的高版本
字节码原样装进本地仓库、再拷进 `lib/`——本次就是这样踩到的：`lib/towndemontower-core-0.1.0.jar` 是
class 65（Java 21），在 JRE 8 上 `java -jar` 直接 `UnsupportedClassVersionError`。只改 pom 里的
`release` 不会触发全量重编，`clean` 之后才是 52。

验证办法（不必启动服务）：读 jar 内任一 class 的主版本号，应为 52。

## 3. 配置（只认环境变量）

`GatewayConfig` 依次读环境变量、再读同名 `-D` 系统属性，**没有配置文件加载**。

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `INKARMOR_API_TOKEN` | 空 | 客户端必须携带的令牌；为空时**拒绝所有请求**（403），不是放行 |
| `PORT` | `8080` | 监听端口 |
| `INKARMOR_GATEWAY_AGENT_ID` | `gateway-default-agent` | 服务端配置身份，用于权限与审计 |
| `INKARMOR_GATEWAY_MODE` | `DEV_EXECUTION` | 模式白名单，取值见 `AgentMode` |
| `INKARMOR_GATEWAY_TAINTED` | `false` | 是否把请求标记为不可信输入 |
| `INKARMOR_GATEWAY_AUDIT_PATH` | `./data/audit/gateway.log` | 审计落盘路径（相对路径按进程工作目录解析） |
| `TOWNDEMONTOWER_AUDIT_KEY` | 无 | 审计链 HMAC 密钥；不设则退化为 SHA-256 链 |
| `INKARMOR_GATEWAY_MAX_BODY_BYTES` | `4194304`（4 MiB） | 请求体硬上限，超过直接 413（不读进内存） |
| `INKARMOR_GATEWAY_THREADS` | `8` | 工作线程数（固定池） |
| `INKARMOR_GATEWAY_TIMEOUT_SECONDS` | `30` | 请求/响应超时，`0` 表示不限；见 §8 的有效性说明 |

注意 `application.properties` 里的 `server.port`、`inkarmor.gateway.*` 全部**不生效**，端口看 `PORT`。

## 4. 协议

请求体 = `IntentObject`（6 字段，见 `contract/towndemontower-wire.schema.json`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `tool` | string | 已注册工具名（如 `deleteData` / `runCompile` / `deployService`） |
| `args` | object | 工具参数 |
| `confidence` | number | 置信度 0~1，**缺失即 `INTENT_FORMAT_INVALID`**（不默认成 0.9）；`< 0.5` → `NEED_MORE_INFO` |
| `reason` | string | 意图说明；含"建议"/"suggest"/"you may consider" → `INTENT_FORMAT_INVALID` |
| `expectedEffect` | string | 预期效果 |
| `rollbackHint` | string | 回滚提示 |

可选覆盖字段 `context`：`{ agentId, mode, tainted, sessionId, taskId, tenantId, ownerUserId }`；
不传则取 §3 的服务端配置。

响应包（`code/message/data/error`）：`data` 即 `SkillResult` 的 5 字段
（`success / code / message / output / approvalTicketId`）。外层 `code=0` 只表示"网关处理了这次请求"，
裁决结论看 `data.code`。

| HTTP 状态 | 外层 code | 什么时候 |
|---|---|---|
| 200 | 0 | 已裁决（含拒绝、待审批、低置信、参数超长——都在响应体里） |
| 400 | 400 | 请求体不是合法 JSON |
| 401 | 401 | 令牌缺失或错误 |
| 403 | 403 | 服务端未配置 `INKARMOR_API_TOKEN` |
| 405 | 405 | 非 POST |
| 413 | 413 | 请求体超过 `INKARMOR_GATEWAY_MAX_BODY_BYTES` |

以上**全部**都会写审计，包括 400/401/403/405/413 这些没进裁决链的拒绝（见 §8 审计说明）。
探活走 `GET /api/health`：不需要令牌、**不写审计**，返回 `{"code":0,"data":{"status":"up","uptimeSeconds":N}}`。

## 5. 鉴权（fail-closed）

每次请求必须带 `X-Inkarmor-Token: <令牌>`，令牌 = 服务端 `INKARMOR_API_TOKEN`。
缺失/错误 → `401`；服务端未配置令牌 → `403`。**不可用 ≠ 放行**。

## 6. 客户端示例（不发布 SDK 包）

- Python 薄包：`towndemontower-gateway/python/inkarmor_guard.py`（标准库，零依赖）

```python
from inkarmor_guard import inkarmor_guard

    ...  # 只有网关裁决为"允许"才执行
```

## 7. 已实测行为

2026-11-12 本地实跑：JRE 8 启动分发包，23 项用例全过；另有网关模块单测 21 项、Python 薄包单测 6 项、
协议 golden 结构复算 69 项。**审计覆盖面**：38 次 `/api/evaluate` 调用 → 38 条审计，一条不多一条不少；
两次 `/api/health` 探活不产生记录。

| 请求 | 结果 |
|---|---|
| `deleteData`（R3） | `R3_DENIED`，文案带"转人工终端处置" |
| `deployService`（R2） | `PENDING_APPROVAL` + 单号，连续调用单号不重复（`T1`、`T2`…） |
| `restartService`（R1） / `runCompile`（R0） | `OK` |
| 缺令牌 / 错令牌 | HTTP 401 `UNAUTHORIZED`（**写审计**，`stage=AUTH`） |
| 非 POST | HTTP 405 `METHOD_NOT_ALLOWED`（写审计，`stage=METHOD`） |
| 非法 JSON | HTTP 400 `BAD_REQUEST`（写审计，`stage=BODY`） |
| 请求体超上限 | HTTP 413 `PAYLOAD_TOO_LARGE`（写审计，`stage=BODY`） |
| 缺 `confidence` / `context.mode` 非法 | 200 + `INTENT_FORMAT_INVALID`（写审计，`stage=INTENT`） |
| `confidence=0.1` | 200 + `NEED_MORE_INFO` |
| `reason` 含"建议" | 200 + `INTENT_FORMAT_INVALID` |
| 参数含控制字符 / 超 1MiB | 200 + `INPUT_REJECTED`（写审计，`stage=INPUT`） |
| 模式改成 `AUDIT_REVIEWING` 后调 `runCompile` | 200 + `MODE_TOOL_NOT_ALLOWED` |
| `readFile`（已从白名单移除，注册表里也没有） | 200 + `MODE_TOOL_NOT_ALLOWED` |
| `GET /api/health` | 200 `{"status":"up"}`，**不写审计**；`POST` 则 405 |
| 21 次连续请求（20 次 R2 + 1 次 R3） | 20 张不重复单号 + 1 次 R3 拦截，全部记账 |

**审计行格式**（两条路径统一，按 `|` 切分后前缀列的含义与顺序不变）：

```
# 走完裁决链（action=SKILL_INVOKED）
工具|结论|task=..|mode=..|agent=..|owner=..
工具|结论|task=..|mode=..|agent=..|owner=..|error=<内部异常类名>   # 仅异常分支，多一列且在末尾

# 入口层拒绝（action=GATEWAY_REJECTED）
工具|结论|stage=<METHOD|BODY|AUTH|INTENT|INPUT>|task=..|mode=..|agent=..|owner=..
```

`task` 缺失时字面量是 `null`（与链内其它审计行一致），`agent` / `owner` 缺失时是空串。

## 8. 已知局限（接入前必须知道）

结构性缺口还剩三条（其中一条需要产品先拍板），其余已在本轮补上。

**① 审批单没有闭环。** R2 转出来的单号是进程内自增（`T1`、`T2`…），没有接审批中心，网关也没有
查询 / 批准 / 拒绝工单的端点，进程重启即丢。也就是说 R2 只能当"硬拦截 + 提示人去别处执行"用，
**不能指望在网关侧把这一单批掉**。R1 本来就不进审批分支，直接放行。
补这一项要新增端点，与 `docs/38` §2「不做管理端点建单」的边界冲突，需要先拍板再动。

**② 限流只是"有上限"，不是"限流"。** 线程池固定且用**无界队列**：并发打满后请求会排队，既不拒绝也不
返回 429，极端情况下排队请求会吃内存。请求体上限（413）挡的是"单个超大 body"，挡不住"海量小请求"。
按 IP / 令牌维度的限流没有做。

**③ 请求超时是尽力而为。** 走 JDK `HttpServer` 的内部开关
（`sun.net.httpserver.maxReqTime` / `maxRspTime`），实现是定时检查后直接断连接、不给响应。
它挡的是"慢速灌包占住线程"，不保证精确，也不构成对调用方的 SLA。

**④ 镜像未验证。** `Dockerfile` 已按 thin jar + `lib/` 结构改写（原先只拷 jar，改打包方式后会启动失败），
但本机没有 docker 守护进程，**未实测**。要用镜像就先把 §7 的用例在容器里跑一遍再依赖它。

**⑤ 审计与行为统计的口径差异。** 入口层拒绝记为 `GATEWAY_REJECTED`，不是 `SKILL_INVOKED`。
离线行为分析器只认后者，所以网关部署在前面时，它的"覆盖率"会低于 100%（入口拒绝被计入"跳过"）。
这是有意的：一次没带工具名的请求不该算进某个 Agent 的拒绝率，否则猜令牌就能把某个 Agent 顶成"高风险"。
