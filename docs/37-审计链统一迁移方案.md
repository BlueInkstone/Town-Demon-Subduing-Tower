## 1. 目标格式（chainVersion = 2）

### 1.1 记录行

单行紧凑 JSON，键按字典序，camelCase，`ensure_ascii=false`，UTF-8：

```json
{"action":"SKILL_INVOKED","algorithm":"HMAC-SHA256","chainVersion":2,"hash":"...","mac":"","payload":"{\"code\":\"OK\",\"tool\":\"read\"}","prevHash":"GENESIS","seq":1,"timestamp":"2026-11-12T00:00:00Z"}
```

恰好 9 个字段：`chainVersion` / `seq` / `action` / `payload` / `timestamp` /
`prevHash` / `hash` / `mac` / `algorithm`。缺字段即格式错误，不允许静默补默认值。

### 1.2 摘要公式（**沿用 Java 既有算式，不引入新拼接**）

```
hashInput = seq + "|" + action + "|" + payload + "|" + prevHash
hash      = HMAC-SHA256(key, hashInput)   有合格密钥
          = SHA-256(hashInput)            无密钥（algorithm 必须写 SHA256-DEGRADED）
```

- `seq` 从 **1** 开始；首条 `prevHash = "GENESIS"`。
- `timestamp` 为 ISO-8601 UTC 带 `Z`，**只记录、不进摘要**。
- `payload` 是 **UTF-8 字符串**：结构化负载由写入方按规范化 JSON
  （键字典序、`,`/`:` 无空格、`ensure_ascii=false`）序列化成字符串；
  Java 现有 `tool|OK|task=...` 这类描述串**原样保留**。
- 竖线只是摘要串内部的分隔符，字段边界由落盘 JSON 保证 —— 这解决了
  `docs/35` §6.5 指出的「action 与 payload 之间含歧义分隔符」问题，
  同时不必改变 Java 已被加固、外锚、M1 行为分析器依赖的算式。

### 1.3 为什么保留 Java 的算式而不是另起一套

- `HashChainAuditStore` / `AuditCrypto` / 外锚 `AuditAnchor` / 锚点副本 /
  启动自检 / `V19*` 回归测试全部绑定 `seq|action|payload|prevHash`。改算式等于
  推翻已交付的防重算能力，与「零回归」冲突。
- Java 的链已有 HMAC（防整链重算）与显式降级报告；SDK 恒 SHA-256 才是弱的一方。
  统一方向应是 **SDK 向 Java 靠拢**，不是反过来降级 Java。
- `payload` 定义为字符串而非强制 JSON 对象，是为了不改 M1 行为分析器
  （`AuditBehaviorAnalyzer` 按 `tool|code|...` 解析 payload）与
  `AgentSkillAspect` / `AuditDecorator` 的写入格式。

### 1.4 密钥

- 只从环境变量 `TOWNDEMONTOWER_AUDIT_KEY` 取，UTF-8 字节直接作 HMAC key。
- 强度判定三语言统一：`minLength=32`、`minDistinctChars=12`、占位值清单（见
  `contract/audit-chain.json` 的 `keyPolicy`），对齐 `core/security/SecretPolicy.java`。
- 不合格一律视为「未配置」，降到 `SHA256-DEGRADED` 并写进行里，**不回退任何默认密钥**。
- 无密钥不等于有密钥：`algorithm` 字段必须显式区分，避免静默等价。

## 2. 版本号怎么标

- **行内** `chainVersion: 2`，每条记录都带，不依赖文件级元数据。
- **段头**沿用 Java 的 `#SEGMENT <uuid> prev=<lastTail>`，格式不变；
  段头本身不带版本号，靠其后的记录行判定该段版本。
- `chainVersion = 1` **不写入**，只作为「无该字段的旧行」的读取分派标签。
  即：字段缺失 ⇒ v1；字段存在且不等于 2 ⇒ 视为未知版本，拒绝加载而不是猜测。

## 3. 加载器怎么分派（双算法）

`contract/audit_chain.py::decode_line()` 已给出可运行参考实现：

| 输入形状 | 判定 | 校验算式 |
|---|---|---|
| JSON 且 `chainVersion=2` | v2 | `seq\|action\|payload\|prevHash`，按 `algorithm` 选 HMAC / SHA-256 |
| 含 tab 且可切 4 列 | v1-java | 旧 tab 行：`seq\|action\|payload\|prevHash`，`prevHash` 由前一条推得；链头 `GENESIS` |
| JSON 无版本且含 `prev_hash` | v1-python | `seq:action:json(payload,sort_keys):timestamp:prev_hash`，seq 从 0，链头 64 个 `0` |
| JSON 无版本且含 `prevHash` | v1-typescript | `seq:action:JSON.stringify(payload,keys.sort()):timestamp:prevHash`，seq 从 0，链头 64 个 `0` |

**分派规则（硬约束）**

1. 一段内版本一致；遇到版本变化必须另起段头，不允许在同一段里混算。
2. v1 行**只读校验**：算出旧算式比对 `hash`，通过即记录 `legacySeen=true`；
   **不重算、不改写、不追加**到旧段。
3. 混合文件时，v1 段按 v1 校验完，新写入一律从新段以 v2 继续；
   新段段头的 `prev=` 记录 v1 段尾哈希，保证跨段连续可追溯。
4. 校验失败一律 fail-closed：报告具体行号与原因，不静默跳过损坏行。

> 本轮项目未被使用，v1 分派只由**构造样例**验证（参考实现已含 java/python/typescript
> 三种 v1 行识别用例），不接触任何真实文件。

## 4. 存量怎么验（本轮为空集）

- 不扫描、不改写、不重算任何现存日志。
- 若将来出现无 `chainVersion` 的文件：按 §3 只读校验，报告中标注
  `legacySeen=true` 与「该段证据按旧算法验证」，并提示当前写入已是 v2。
- **不提供**一键迁移/回填命令 —— 那会诱导就地重算，违反基线。
- 存量文件的处置（保留原件 + 另起新段）写入运维手册，属于 Ops 交接项。

## 6. 回归用例设计

1. **golden 摘要**：`contract/audit-chain.json` 的 5 条向量，三语言各自独立实现后
   逐条比对 `expectedHash` 与 `expectedLine`（含中文负载、字符串负载、链式第二条、
   有/无密钥两种算法）。参考实现自检已 24/24。
2. **跨语言互读**：Java 写 → Python/TS 读并校验；Python 写 → Java/TS 读；TS 写 → 其余两者读。
   这是路径三真正要证明的能力，也是判定线。
3. **版本分派**：构造 v1 三种方言样例，任一语言只读校验通过并标注 `legacySeen`；
   未知 `chainVersion` 值拒绝加载。
4. **降级显式**：无密钥行 `algorithm=SHA256-DEGRADED`；有/无密钥摘要必然不同；
   占位值密钥按 `keyPolicy` 判为未配置。
5. **篡改检出**：改 payload / 删行 / 换序 / 改 timestamp（后者**不应**影响摘要）分别断言。
6. **时间不入摘要**：同一记录仅 `timestamp` 不同，`hash` 必须相同。
7. **加固不退化**：`V19*` 外锚/副本/分段/启动拒绝全部保持；M1 分析器 72/72 保持；
   CP-10 静态扫描 0 违规。
8. **零回归**：Java 主线整轮回归、Python 126、TS 111，施工后按实测更新 `docs/27`。

判定线：**第 2 项全绿**之前，不得把文档措辞改成「审计链已可互验」；
§7 第 ⑤ 步全量 golden 通过之前，仍不得写「三语言契约一致」。

## 8. 假设与待确认

| # | 假设 | 理由 |
|---|---|---|
| A-1 | `payload` 统一为字符串而非强制 JSON 对象 | 不改 M1 分析器与 Java 写入格式；结构化负载由调用方规范化序列化 |
| A-2 | 摘要公式沿用 Java `seq\|action\|payload\|prevHash` | 外锚、副本、防重算、1575 回归都绑它；SDK 向 Java 靠拢而非降级 Java |
| A-3 | 时间记录但不入摘要 | 消除时钟/时区差异导致的跨语言摘要不一致 |
| A-4 | v1 只读、不迁移、不重算 | `docs/35` §6.5 硬约束；项目未被使用，无对象需要迁移 |
| A-5 | 段头格式保持 `#SEGMENT <uuid> prev=<tail>` | Java 分段与跨段连续性已交付，改它无收益 |
| A-6 | `AuditRecord` 构造签名不改 | 1575 回归与 M1 分析器依赖 5 参数构造；v2 附加字段在落盘层补 |
| A-7 | v2 行 `mac` 字段保留为空 | Java 的 `mac` 语义与外锚相关，本轮不重新定义；后续如需链级 MAC 单独评审 |

**需要评审确认的一点**：A-1 与 `docs/35` §6.5 字面写的
「payload : 规范化 JSON」有解释差异 —— 本方案把它解释为
「结构化负载按规范化 JSON **序列化成字符串**」，这样 Java 的描述串 payload
与 SDK 的对象负载能共存于同一条链。若评审要求 payload 必须是 JSON 对象，
则需同步改造 `AuditDecorator`、`AgentSkillAspect` 与 M1 行为分析器，
改动面和零回归风险都会显著上升，应另行评审。
