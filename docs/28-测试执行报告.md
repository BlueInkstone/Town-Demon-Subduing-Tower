3. **执行**：31 个套件逐个运行，捕获 `RESULT pass=N fail=N` 与退出码（失败退出码 = 1）。
4. **连跑两遍**：验证 F-01 幂等。
5. **缺口核查**：对 ⬜ / ⚠️ 项做源码级核查 + 针对性实证探针（见 §5）。
6. **部署态验证**：离线打 fat-jar、真实启动、健康检查（G-10）。

### 1.3 复现命令

```bash

bash .workbuddy/run_all.sh                      # 连跑两遍全仓

cd towndemontower-core
"/c/Program Files/Java/jdk-21.0.12/bin/java" -Dfile.encoding=UTF-8 \
  -cp "$(cygpath -w $PWD/target/classes);$(cygpath -w $PWD/target/test-classes);$(cat cp.txt)" \
```

## 5. 专项核查发现（超出清单既有描述）

### 5.1 审计链是"分段链"，`/integrity` 两个计数字段口径不同（S-09）

**实测**：审计文件形如

```
#SEGMENT <uuid> prev=<上段尾哈希>
1  ACTION  <hash>  <payload>
2  ACTION  <hash>  <payload>
#SEGMENT <uuid> prev=<上段尾哈希>
1  ACTION  <hash>  <payload>
```

`scan()` 遇段头把 `prev` 复位为 `GENESIS` → **每段独立起链**。由此：

| 观测 | 口径 |
|---|---|
| `auditStore.all().size()` | **当前段**条数（重启后实测为 0） |
| `audit.anchorRecords()` | **全文件累计**条数（实测 269） |
| `verifyChain()` | **仅当前段**；全文件完整性由启动时 `scan()` 保证（不匹配即拒绝启动） |

→ `/integrity` 同时返回 `auditRecords: 1` 与 `auditAnchorRecords: 269`，**未标注两者口径不同**，运维极易误读为"日志几乎是空的"。
→ **建议**：字段改名（如 `auditRecordsCurrentSegment` / `auditRecordsTotal`）或在返回体中显式标注口径。

### 5.2 E-06 精确行为：非静默，但"已执行未留证"（C-65 冲突）

审计写在 `AuditDecorator` 中位于 `next.execute()` **之后**。写盘失败时实测：

| 指标 | 实测值 | 判读 |
|---|---|---|
| 工具是否已执行 | **是** | 副作用已发生，框架无法回滚 |
| 新增证据行 | **0** | 该次执行**零留证** |
| 调用方是否收到假成功 | **否**（抛 `IllegalStateException`） | ✅ 不是静默丢证据 |
| 治理错误码 | **被 IO 异常覆盖** | ❌ 违反 C-65「拒绝码不混用」 |

根因：`AuditDecorator` 的 `catch` 分支会**再写一次审计**，该次同样抛异常 → 原始裁决码被盖掉。
**建议**：审计写失败时返回专用错误码（如 `AUDIT_WRITE_FAILED`），并考虑"先写意图、后执行"的预写策略。

### 5.3 C-07 标 ✅ 但仓库无对应用例

全仓 `src/test` **不含任何多线程用例**（`new Thread` / `ExecutorService` / `CountDownLatch` 均为零命中）。
`V16SecureDefaultsTest` ④-1 只覆盖串行的"首调放行 / 二调拒绝 / 换工具仍拒绝"。
本次补做实证：**200 轮 × 32 线程并发调用 `tryConsume`，每轮恰好 1 次放行**（`allowedCount=1`、审计恰好 1 行）→ **机制正确**。
**建议**：把该实证固化为回归用例，否则 C-07 / E-04 的 ✅ 状态无自动化背书。

### 5.4 G-2 / C-21：审批卡点确为空壳

`PLAN_APPROVAL_REQUIRED` 全仓**仅 1 处引用** —— `ErrorCodes` 中的常量定义本身。
`ApprovalCenter` 的 TTL / 禁自批 / 落盘等能力齐备且有测试，但**没有任何业务路径会产出该错误码**。
→ 文档表述准确，**建议**：补 Plan-and-Execute 入口，或在自检里显式标注"该环节未启用"。

### 5.5 S-03 / G-1：治理链可被进程内代码绕过（当前最大结构性缺口）

- 无 `.github/workflows` 或任何 CI 配置 → **CP-10（CI 静态扫描）确未实现**。
- `docs/18` 自查表亦记为「⬜ 未做」。
- 影响面与清单描述一致：绕过注解直调 Service → 治理静默失效且无审计。

### 5.6 新增风险：审计日志无跨进程文件锁（清单未列）

实测两个 `FileAuditStore` 指向同一文件：

```
onDisk=3  s1.inMemory=2  s2.inMemory=1
s1.anchor=2  s2.anchor=2      ← 文件实有 3 条，锚点少计
```

各实例的 `written` 计数互相覆盖 → **锚点条数可能少计**。多实例共用一个 `audit.log` 会**削弱 C-38（截断检出）/ C-45（整目录回滚检出）** 的判定强度。
（本次实测中该现象确实出现：delivery demo 的 `audit.log` 锚点记 269 而文件实有 295 条 —— 两个 demo 实例先后指向同一文件所致。）

**建议**：文档明确"一个 `audit.log` 只允许一个写入进程"；或在 `FileAuditStore` 引入文件锁 + 启动时校验锚点与文件条数一致。

### 5.7 G-9：多租户隔离不只是"未评估"，而是**未实现**

`tenantId` 在 `ExecutionContext` 中是**纯透传字段**；全仓**没有任何一处读取它做隔离决策**（`PermissionEngine` 按 agent-id 存，审计单文件）。
→ 清单写"跨租户串数据风险未评估"**偏轻**：实际是**结构性可能**，而非"未评估"。

## 13. v1.14 补充 · 审计写入吞吐压测（2026-11-04）

> 对应 v1.14 列为技术债的第一项：计划审批接入后，一次计划生命周期会同步写 3 条审计，
> "一条审计多少钱"直接决定计划审批的吞吐上限。本次只观测、不改核心写入逻辑。

### 13.1 方法与口径

运行器：`V114AuditThroughputBench`（core，`main` 直跑，默认 2000 条/场景）。

- 只计 `AuditStore.appendAuto` 这一个真实写入口；`all()` / `verifyChain()` 是 O(n) 读取路径，不混入计时；
- 每场景独立目录，落盘类场景在 `target/bench-audit-*` 下；
- 吞吐数字**不做绝对值断言**（机器与磁盘差异会造成随机失败）；
- 稳定断言 8 项：条数、链完整、文件行数、锚点位置、副本末条、以及一条极宽护栏（默认配置 p99 < 200ms/条，只挡数量级回退）。

### 13.2 结果（n=2000，Windows 本地盘）

| 场景 | 总耗时 ms | 吞吐（条/秒） | p50 µs | p95 µs | p99 µs | 日志字节/条 |
|---|---|---|---|---|---|---|
| 内存·SHA-256 | 67.1 | 29819 | 8.2 | 32.3 | 85.9 | — |
| 内存·HMAC | 98.6 | 20275 | 5.6 | 14.6 | 41.0 | — |
| 文件·每条锚定（默认 `anchorBatch=1`） | 7983.9 | **250.5** | 3717.6 | 5834.0 | 7505.6 | 196.2 |
| 文件·批量锚定（`anchorBatch=100`） | 720.0 | **2777.8** | 253.9 | 575.0 | 3450.2 | 196.2 |
| 文件·每条锚定 + 文件副本 | 18029.7 | **110.9** | 7412.7 | 15849.8 | 29962.3 | 196.2 |

写放大：

| 配置 | 每条审计的落盘动作 | 相对默认吞吐 |
|---|---|---|
| 默认 `batch=1` | 日志追加 1 次 + 锚点重写 1 次 | 1.0× |
| `batch=100` | 日志追加 1 次 + 锚点重写 0.01 次 | **11.1×** |
| 默认 + 文件副本 | 再加账本追加 1 次（168.5 B/条） | **0.4×** |

计划审批换算（默认配置）：单次生命周期约 3 条审计 ≈ **12 ms**；1000 次计划审批 ≈ **12 s**，
即默认配置下计划审批的同步写入上限约 83 次/秒。

### 13.3 结论

1. **主要成本是锚点，不是哈希**。`batch=1` 时每条都要写 tmp 再原子改名，p50 3.7ms；
   哈希本身在内存在 30µs 量级。
2. **批量锚定是唯一的量级杠杆**。`batch=100` 提升 11.1 倍，代价是最多落后 99 条未锚定
   （崩溃窗口内这 99 条无法证明未被篡改）。
3. **副本扇出代价显著**。默认 + 副本吞吐降到 110.9 条/秒；若副本是硬要求，
   更应同时开批量锚定，而不是保持 `batch=1`。
4. **内存模式两档的 p99 不可直接比较**。内存实现用写时复制列表，单次 add 会复制整表，
   p99 受扩容与 GC 影响；本次未做规模梯度实测，**"n 增大后单条成本线性上升"只是代码层推论**，
   需专项实测才能定论。

### 13.4 未做与建议

- 未做跨进程并发写、远端 HTTP 副本、长时间稳定性（GC 停顿/文件句柄）测试；
- 未改任何写入策略。若要保留"零落后"又不牺牲吞吐，需要把锚点从"每条全量重写"
  改为"追加式锚点日志 + 启动取末条"，属设计变更，不在本版范围；
- 建议生产按容忍的崩溃窗口在 `anchorBatch=10~100` 之间取值，并把这笔账写进运维文档。

**过程中的返工**（如实记录）：

1. `@RestControllerAdvice(basePackages="com.towndemontower.spring.admin")` **不接管未知路由的 404**——
   `NoResourceFoundException` 由资源处理器抛出，不在该包内。处置：404 只断言状态码，统一错误体改用
   "已知接口 + 缺参数"验证。写进 `docs/33` 而不是假装覆盖。
2. 测试 `application.properties` 里写着 `spring.main.web-application-type=none`，属性优先级压过
   `SpringApplicationBuilder.properties(...)`，容器始终起不来（`AnnotationConfigApplicationContext` 无法转
   `ServletWebServerApplicationContext`）。处置：改用**命令行参数** `--spring.main.web-application-type=servlet`。
3. `PlanAdminController` 直接注入 `PlanApprovalService` 触发 2 条 `CP10-R4`（`Controller` 注入 `*Service`）。
   R4 不在可豁免范围内，处置是**结构性修正**：新增 `PlanAdminOperations` 用例层，Controller 注入它。
   修正后扫描 `warnings=0`——是"消掉命中"，不是"改判定"。
