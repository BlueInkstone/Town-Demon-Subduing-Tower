# 防绕过方案

> 前置结论（见 `docs/17-强制力与绕过面分析.md`）：当前治理是**框架层（进程内）强制**，
> 强制点是"Spring 代理 + 注解"，因此"不写注解 / 不走代理 / 换掉策略 Bean"都能绕过。
>
> 本方案不试图把它变成内核级强制（那需要重写成 sidecar 或 eBPF，超出本产品形态），
> 而是做三件事：**把绕过从"无痕"变成"有痕"、从"默认可用"变成"默认被拒"、从"靠自觉"变成"可验证"**。

## 1. 防护目标与威胁模型

### 1.1 要保护的资产

| 资产 | 被绕过的后果 | 当前保护程度 |
|---|---|---|
| 工具调用权（shell / 写文件 / 部署） | 任意代码执行、数据损坏 | 中（链内有效，链外为零） |
| 权限注册表（`PermissionEngine`） | 任意主体获得任意权限 | 低（`grant` public，无审计） |
| 审计账本（`HashChainAuditStore`） | 事后无法追溯，等于没有治理 | 低（内存、无签名、可注入） |
| 治理配置（`enabled` / 策略 Bean） | 一次性关停全部治理 | 低（关开关 = 全放行） |
| Agent 身份（`agentId`） | 冒用身份、责任错配 | 无（无认证） |

### 1.2 对手模型（决定方案的取舍）

| 对手 | 能力 | 本方案态度 |
|---|---|---|
| **A. 误用者**（业务开发者，无意） | 写代码、习惯性自调用 | **主战场**。这类占实际事故的绝大多数，且当前完全无感 |
| **B. 越权开发者**（有代码/配置权） | 换 Bean、关开关、改注解 | **必须留痕**。不求挡住，求"挡住+记录"或"记录到能被发现" |
| **C. 未认证调用者**（能访问端口） | 直接打 REST | **必须挡住**。这是唯一能彻底解决的，成本也最低 |
| **D. 宿主 root / 能改 jar 的人** | 改字节码、读内存、重算链 | **不设防，只检测**。承认超出边界，别在文档里承诺 |

一句话原则：**对 A 要拦得住，对 B 要看得见，对 C 要进不来，对 D 只求事后能发现。**

## 3. 核心防护策略

### 3.1 总原则：四个"从…到…"

| 维度 | 现状 | 目标 |
|---|---|---|
| 入口 | 治理点 = 注解（写注解才受管） | 治理点 = **能力令牌**（没有令牌就执行不了） |
| 开关 | 关掉 = 不装配 = 全放行 | 关掉 = **全拒绝**（killswitch，不是 bypass） |
| 策略 | 可被静默替换 | 替换**必须显式声明**并留痕 |
| 审计 | 内存、可重算 | **HMAC + 进程外锚点** |

### 3.2 第一道：能力令牌（治本，解决 BS-01/03）

把"经过代理"从**约定**变成**前置条件**：

```java
// core：一次性通行证，ThreadLocal 承载，防重入
public final class GovernancePass {
    private static final ThreadLocal<Deque<String>> ACTIVE = ThreadLocal.withInitial(ArrayDeque::new);

    /** 链尾发放（SandboxedToolExecutor 内、真正执行前）。 */
    public static void issue(String tool) { ACTIVE.get().push(tool); }

    /** 受治理方法的实现首行调用。 */
    public static void require(String tool) {
        Deque<String> d = ACTIVE.get();
        if (d.isEmpty() || !tool.equals(d.peek())) {
            throw new UngovernedInvocationException(tool);   // 无令牌 = 绕过
        }
    }

    public static void revoke(String tool) { /* pop */ }
}
```

```java
// 业务侧：每个受治理方法的实现首行加一行（这是唯一需要开发者配合的动作）
@AgentSkill(name = "restartService", risk = "R1", requiredPerms = {"ops:restart"})
public void restart(String service) {
    GovernancePass.require("restartService");   // ← 自调用时这里就炸
    // ... 真正的业务逻辑
}
```

**为什么这条最有效**：`this.restart()` 确实绕过了 AOP，但**绕不过方法体首行**。攻击者要绕过它，必须删掉这一行——而删掉是可 review、可 grep、可 CI 校验的（§5 D1）。这是把"隐式失效"变成"显式违约"。

边界：令牌必须一次性（`peek` 后 `pop` 在 finally），否则递归调用会误放行；跨线程（`CompletableFuture`）传递时应清空，宁可误拒不可误放。

### 3.3 第二道：fail-closed 开关（解决 BS-06）

现状：`enabled=false` → 切面不装配 → 注解是摆设。这是"为了演示方便"的设计，必须改：

```java
// core
public final class RejectAllExecutor implements Executor {
    private final AuditStore audit;
    public SkillResult execute(IntentObject i, ExecutionContext c) {
        audit.appendAuto("GOVERNANCE_DISABLED_CALL", i.tool + "|" + c.agentId);
        return SkillResult.denied(ErrorCodes.GOVERNANCE_DISABLED,
                "治理已停用，调用被拒绝（fail-closed）");
    }
}
```

```java
// starter：把"不装配"改成"装配一个全拒实现"
@Bean
@ConditionalOnProperty(prefix = "towndemontower", name = "enabled", havingValue = "false")
public Executor disabledExecutor(AuditStore audit) { return new RejectAllExecutor(audit); }
```

于是 `enabled=false` 的语义从"我想省事"变成"我要紧急熔断"，且**每一次被熔断的调用都有审计**。想在开发环境放开，必须显式配置 `towndemontower.integrity.dev-bypass=true`（启动横幅 + 首条审计 + 该配置在 prod profile 下被硬拒）。

### 3.4 第三道：策略溯源（解决 BS-05）

```java
// core：所有可替换策略实现此接口
public interface PolicyProvenance {
    /** 内置实现返回 "builtin"；自定义必须返回 "custom:<用途>"，不得留空。 */
    String provenance();
}
```

启动时（`GovernanceIntegrityChecker`）检查六个策略的实际实现类：

| 检查项 | 合规 | 不合规处置 |
|---|---|---|
| `RiskGate.class` 的 `provenance()` | `builtin` | strict 模式启动失败；否则 WARN + 审计 `POLICY_SUBSTITUTED` |
| `AuditStore` / `ApprovalPolicy` / `ModeToolPolicy` / `Executor` | 同上 | 同上 |
| `autoGrantDeclaredPerms` | `false` | WARN + 审计（不阻断，避免破坏存量） |
| `agentId` 来源 | `Credential`（非 `properties`） | WARN |
| 审计链 `verifyChain()` | `true` | **fail-closed**：全局拒绝写入 |
| 沙箱策略 | `DockerSandboxStrategy` 或显式声明无沙箱 | WARN + 审计 |

关键不是"禁止替换"（企业确实需要自定义 RiskGate），而是**让替换这件事在启动日志、审计账本、健康检查里各留一份，且无法只留一份**。

### 3.5 第四道：审计不可否认（解决 BS-11）

三层递进，成本从低到高：

| 层级 | 做法 | 挡住什么 |
|---|---|---|
| L1 | `append` 从 public 收为包内可见；只允许 `appendAuto` | 外部注入自洽记录 |
| L2 | 记录哈希改 `HMAC-SHA256(key, seq\|action\|payload\|prev)`，key 由 `CredentialBroker` 提供、不落源码 | 无密钥者无法重算链 |
| L3 | 每 N 条 / 每 60s，把 `(seq, hash)` 作为锚点写到**进程外**（独立 append-only 文件 / syslog / 远端），启动时校验最后锚点 | 进程内整体重写。锚点不在同一台机器时也无解 |

同时保留"内存存储"作为演示默认，但**在健康检查里报 `audit.durability=VOLATILE`**——不要让使用者误以为重启后账本还在。

### 3.6 第五道：命令模板化（解决 BS-08/09）

AST 黑名单这条路走不通（命令空间无限，正则永远漏）。换成"只允许预定义形态"：

```java
// core：命令由模板定义，参数只能填占位符，不拼 shell 字符串
public record CommandSpec(List<String> argv, Set<String> allowedFlags) {
    // 例：new CommandSpec(List.of("systemctl", "restart", "{service}"), Set.of())
}
// SkillDescriptor 增加两个字段（用重载构造器保持兼容）：
//   String commandParam      —— 哪个参数是命令（默认 "command"）
//   CommandSpec commandSpec  —— 有模板则按模板拼 argv，无模板则要求 R3
```

`DefaultRiskGate` 取参逻辑改为：

1. `descriptor.commandParam` 指向的参数存在 → 用它过 AST；
2. **声明了但参数缺失 → 直接 `INTENT_FORMAT_INVALID`**（不能靠"改名"让检查消失）；
3. 无 `commandParam` 声明但参数里出现 shell 特征（`;`、`|`、`$(`、`&&`）→ 无条件升 R2；
4. 有 `commandSpec` 的工具不走 AST，改为校验 argv[0] 在白名单且参数不含 shell 元字符；
5. 无 `commandSpec` 且 `sideEffect=true` 的 shell 工具 → 固定 R3 + 双人审批。

## 4. 关键控制点（Control Points）

| ID | 位置 | 检查内容 | 失败行为 | 挡住 |
|---|---|---|---|---|
| CP-1 | 受治理方法实现首行 `GovernancePass.require()` | 本次调用是否由链尾发放令牌 | **抛异常 + 审计** | BS-01/03/12（部分） |
| CP-2 | `AgentSkillAspect` 进入时 | 是否已有同名令牌在栈上（重入检测） | 拒绝 | 伪造令牌 |
| CP-3 | 启动期 `GovernanceIntegrityChecker` | 六项配置/策略溯源 | strict→启动失败；否则 WARN+审计 | BS-05/06/07 |
| CP-4 | 每次 `executor.execute` 前 | `verifyChain()`（或每 N 次抽样） | 断链→全局只读 | BS-11 |
| CP-5 | `DefaultRiskGate.classify` | 参数声明一致性 + shell 特征 | 缺参拒、特征升 R2 | BS-08 |
| CP-6 | `SchemaDecorator` | 除必需参数外，**禁止出现未声明参数**（白名单） | 拒绝 | 参数夹带（如 `extraArgs`） |
| CP-7 | `PermissionEngine.grant` | 调用者是否为 `AccessProvisioner`（栈检查/包可见） | 拒绝 + 审计 | BS-07/12 |
| CP-8 | HTTP 入口 Filter | `Authorization` → `agentId` 映射，且 Agent 必须 `ACTIVE` | 401 / 403 | BS-10 |
| CP-9 | `DockerSandboxStrategy.buildDockerArgs` | `extraArgs` 白名单（仅 `-u`/`--pids-limit`），出现 `-v`/`--privileged`/`--net=host` | 拒绝启动 | BS-13 |
| CP-10 | CI（ArchUnit / 注解处理器） | `@AgentSkill` 方法体内出现 `ProcessBuilder`/`Runtime`/`Files.write`/`HttpClient`/`DriverManager` | 构建失败 | BS-04/02 |
| CP-11 | 定期对账任务 | 档案 `permissions` vs `permissionsOf(agentId)` 差值 | 差异→告警 + 审计 `ACCOUNT_MISMATCH` | BS-12 |

CP-1 与 CP-10 是"治本"的两条：一个管运行时，一个管提交时。

## 5. 检测措施（可落地）

### D1 启动自检（`GovernanceIntegrityChecker`）

```java
public record GovernanceSnapshot(
        boolean enabled, boolean autoGrant, boolean devBypass,
        String riskGateClass, String riskGateProvenance,
        String auditStoreClass, String approvalPolicyClass, String executorClass,
        String sandboxStrategyClass, String agentIdSource,
        boolean auditChainValid, String activeProfiles) {}

public record Finding(String code, Severity severity, String detail) {}

public final class GovernanceIntegrityChecker {
    public List<Finding> check(GovernanceSnapshot s);   // 纯函数，零依赖，可单测
}
```

发现项固定编码，便于告警规则匹配：`GOVERNANCE_DISABLED`、`DEV_BYPASS_ACTIVE`、`POLICY_SUBSTITUTED`、`AUTO_GRANT_ENABLED`、`AUDIT_VOLATILE`、`AUDIT_CHAIN_BROKEN`、`AGENT_ID_FROM_CONFIG`、`SANDBOX_SOFT`。

启动时：`finding.severity == CRITICAL && strict` → 抛 `IllegalStateException` 中止启动（不是 WARN 后继续）；否则打印清单并写首条审计 `GOVERNANCE_SELF_CHECK`，内容为各发现项的 hash。

### D2 调用来源校验（`GovernancePass`）

见 §3.2。计数指标 `ungoverned_invocations_total`，**任何一次非零都应当报警**——正常情况下它必须是 0，非零就意味着有代码在绕过。

### D3 CI 静态扫描

- **注解目标检查**：`@AgentSkill` 只允许出现在 `public`、非 `final`、非 `static`、非 `private` 方法上（BS-02）；
- **方法体检查**：禁止 `ProcessBuilder` / `Runtime.getRuntime` / `Files.write` / `new FileOutputStream` / `HttpClient` / `DriverManager`（BS-04）；
- **首行检查**：`@AgentSkill` 方法体首条语句必须是 `GovernancePass.require(...)`，且参数与注解 name 一致（BS-01）；
- **直调检查**：Controller 层不得直接注入 `*Service`（除只读查询白名单）（BS-03）。

前三条用 ArchUnit 或自写注解处理器均可，纯离线可跑。

### D4 配置漂移检测

启动时计算"治理相关配置"的规范化摘要（`enabled/autoGrant/strict/tx.enabled/沙箱策略/agentId 来源`）→ SHA-256 → 写入审计 `CONFIG_FINGERPRINT`。与上一次启动的指纹比对，变化即 `CONFIG_DRIFT` 告警。运维改配置不再是"静默"的。

### D5 对账（`ACCOUNT_MISMATCH`）

定时（或每次列表查询时顺带）比对：档案里的 `permissions` 与 `PermissionEngine.permissionsOf(id)`。
- `SUSPENDED`/`RETIRED` 而实然权限非空 → **严重**（有人在用反射/直接 grant 复权）；
- `ACTIVE` 而缺少档案里的权限 → 中（同步漏了）。

这条专门抓"绕过门面直接改内存"（BS-12），因为反射无法被阻止，但**结果必然与档案不符**。

## 6. 拦截措施（Enforcement）

| 编号 | 措施 | 实现要点 |
|---|---|---|
| I1 | fail-closed 开关 | `RejectAllExecutor` + `DEV_BYPASS` 显式配置（§3.3） |
| I2 | 策略钉住 | `PolicyProvenance` + strict 启动失败（§3.4） |
| I3 | 授权收敛 | ✅ v1.9：`grant/revoke/revokeAll` 包内可见，写入只能经 `PermissionProvisioner`（带审计）；`permissionsOf` 返回不可变副本（已是） |
| I4 | 审计加固 | ✅ v1.9：HMAC-SHA256 链 + 外锚（条数/末条哈希/MAC）；⏳ `append` 收权未做 |
| I5 | 命令模板 | `CommandSpec` + `commandParam` 声明制（§3.6） |
| I6 | 身份强制 | ✅ v1.8：Servlet Filter，`loopback`/`token`/`off` 三档，无凭据 401、跨机写 403、拒绝进审计；⏳ 未做：凭据映射不到 `ACTIVE` Agent 时 403、`ExecutionContext.agentId` 收权（随 I3 一起做） |
| I7 | 沙箱收敛 | `extraArgs` 白名单；镜像 digest 固定（不用 `alpine:latest`）；要求 rootless docker；docker 不可用保持 `SANDBOX_UNAVAILABLE`（fail-closed，现状已正确） |
| I8 | 参数白名单 | `SchemaDecorator` 只放行 `requiredArgs` ∪ 声明的可选参数，多一个就拒 |

I8 值得单独强调：现在 `SchemaDecorator` 只校验"必需参数在不在"，不管"多带了什么"。而 `DockerSandboxStrategy.extraArgs` 正是从参数一路带到命令行——**参数夹带是容器逃逸的现成通道**。

## 8. 边界情况处理

| 情况 | 处理 |
|---|---|
| **存量代码大量自调用，一次性加令牌会崩** | 灰度：`enforcement=warn` 模式先只记 `UNGOVERNED_INVOCATION` 不抛，跑一周产出清单，再切 `deny`。warn 模式本身要写进审计，避免变成永久后门 |
| **测试需要绕过治理** | 只允许 `@Profile("test")` + `GovernancePass.testBypass()`（带审计标记）；CI 校验 `src/main` 中不出现该调用 |
| **无数据库的轻量部署，审计无外锚** | 至少写本地 append-only 文件 + 每次启动把上一段链头哈希打到应用日志；健康检查报 `anchored=false`，不假装有 |
| **进程重启导致链断** | 分段：每段以 `GENESIS-<uuid>` 开头，段头记录前一段尾哈希；`verifyChain` 按段校验并输出"跨段连续性"单独指标 |
| **HMAC 密钥轮换** | 双密钥窗口：`keyCurrent` 校验、`keyPrevious` 兼容；记录每条记录的 `keyId` |
| **docker 不可用** | 保持 `SANDBOX_UNAVAILABLE` fail-closed，**不允许**自动降级到 `ProcessSandboxStrategy`。降级等于静默取消隔离，是最坏的一种"可用性优化" |
| **高并发下审计成为瓶颈** | 单写者队列 + 批量刷盘；序号与哈希必须在同一临界区，否则链序错乱。宁可排队，不可乱序 |
| **企业确实需要自定义 RiskGate** | 允许，但需：实现 `PolicyProvenance` 返回 `custom:<理由>` + 通过 `RiskGateContractTest`（契约测试：R3 不得被降级、未知默认 R2、AST fallback 保持 R2）+ 启动审计 |
| **第三方库内部做 IO** | 不在治理面，承认边界。兜底靠 OS 层：容器只读根文件系统、`--network none`、出网白名单。这是"承认框架层管不到的地方交给运行时" |
| **反射改内存（BS-12）** | 阻止不了，转为检测：对账任务 + 定期快照 `permissionsOf` 全量比对。目标是"事后 5 分钟内发现"，不是"阻止" |
| **紧急熔断与业务连续性的冲突** | `enabled=false` 全拒会让业务停摆，因此必须同时提供"只读模式"（R0 放行、写全拒），避免运维在故障时被迫选择"全开" |
| **治理引擎内部异常**（外部评审补充观点，见 `docs/08`「未来发展方向」A-1） | 现状 `AuditDecorator` 捕获后转 `INTERNAL_ERROR` 拒绝并写审计 —— 结果 fail-closed，但异常**不外抛**、业务方法不中断。观点主张抛 `GovernanceInternalException` + `GOVERNANCE_ENGINE_ERROR` 强拦截。取舍未定；**定论前不得对外宣称"绝不静默失效"已覆盖内部故障** |

## 9. 落地路线

| 阶段 | 内容 | 改动面 | 收益 |
|---|---|---|---|
| **一期**（不动架构） | I1 fail-closed、D1 启动自检、D2 令牌校验、I3 授权收敛、I6 HTTP 认证 | core 新增 2 类 + starter 1 Bean + agents 1 Filter | 挡住 C 类对手、B 类留痕、A 类可发现。**ROI 最高** |
| **二期**（契约扩展） | I5 命令模板 + `commandParam`、I8 参数白名单、I4 HMAC 审计、D4 配置指纹 | `SkillDescriptor` 加重载构造器、`DefaultRiskGate` 改取参、`HashChainAuditStore` 换哈希函数 | 关闭 BS-08/09/11，风险闸门从"猜"变"声明" |
| **三期**（架构级） | ~~CP-10 CI 静态扫描~~（**v1.11 已交付判据**，接入由使用方决定）、D5 对账、I7 沙箱收敛、D6 外锚 | 构建链 + 运维 | 关闭 BS-02/04/12/13 |

不建议一上来做三期：静态扫描会一次性报出大量存量违规，没有一期二期建立的"warn 模式"和"豁免流程"，会直接被团队关掉。

## 10. 明确不设防的部分

写清楚边界，比夸大能力有价值：

1. **能改 jar / 能 attach 调试器的人**——可改字节码、读内存、重算 HMAC 链（密钥在进程内）。只能靠"锚点在另一台机器"把成本抬高，不能根除。
2. **工具方法体内部的任意 Java 能力**——`@AgentSkill` 治理的是调用，不是 JVM。真正的边界只能靠容器/网络策略。
3. **有 `docker` 组权限的用户**——等价宿主 root，沙箱对他无效。
4. **业务语义错误**——权限、风险、审批都对，但业务逻辑本身写错了。治理不管对错，只管"该不该做、做没做、能不能查"。
