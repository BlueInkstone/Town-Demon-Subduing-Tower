# Town Demon-Subduing Tower · 产品定位与工程思想

> **本文定位**：产品定位与工程思想的权威说明（2026-11-12 正式确立）。
> 能力边界、版本进度与排期以 `README.md`、`docs/08-版本任务清单.md` 为准。
> 本项目**有一定传播工程思想的性质**：它不只是一个可接入的治理中间件，也希望读者理解
> 「为什么这样设计、为什么不做另一些设计、这套机制管不到哪里」。因此本文先讲问题与取舍，
> 再讲能力，最后才是怎么用；能力清单里的每一条都有对应代码或未实现标记，不把设计稿写成功能。

---

## 1. 一句话定位

**给 Agent 装「刹车和行车记录仪」的嵌入式运行时治理层**：在 Agent 每次调用工具时，
用一条顺序写死的检查链裁决「能不能执行」，并把所有结果（含拒绝与异常）写进只追加的哈希链供事后追溯。

更技术化的说法：面向做 Agent 应用的开发者，嵌进他们自己的 Spring Boot 应用里的治理层；
加依赖 + 注解接入，不单独部署；强制力边界是 **JVM 进程内**，定位是**同信任域的防误操作 + 事后追溯**。

## 2. 它是什么、不是什么

| | |
|---|---|
| **是** | 嵌入宿主应用的库 / starter；运行时进程内拦截；固定 10 环节检查链；不可篡改的审计追溯；配套构建期防绕过扫描 |
| **不是** | 开发时或 CI 时的工具（构建期扫描只是补漏，防的是「运行时拦截被静默跳过」）；服务器 / 主机 / 内核层安全（不碰 seccomp、LSM、网络层，OS 层兜底交给接入方）；跨信任域的防恶意机制；SaaS 或可视化编排平台；给终端用户用的产品 |

`docs/17-强制力与绕过面分析.md` 的原始结论：管理机制是**框架层（进程内）强制**，治理边界 = JVM 进程边界；
它挡得住「用错」，挡不住「想绕」。能承诺的是「走注解的调用 10 环节一定按序执行、被拒也留痕」，
不能承诺防住「不写注解的调用」「换个恒真策略 Bean」「工具方法体里自己开子进程」「重算哈希链」「未认证 HTTP 调用者」。

## 3. 它解决什么

Agent 已经能写文件、跑命令、发部署。让人不敢放手的从来不是"它不够聪明"，而是三件事没人能回答：
**它改坏了什么、谁让它改的、能不能收回来**。这三件事靠提示词、靠日志、靠事后读代码，都回答不了。

## 4. 工程思想（本项目想传播的部分）

1. **模型只提议，闸门硬裁决**。模型输出结构化意图对象，「能不能做」由外部闸门分级、审批、执行、回滚。
   不试图用提示词说服模型别干坏事——提示词是建议，闸门是机制。
2. **机制写死，策略可配**。装饰器链的顺序与层数固定，配置不能改拓扑；策略对象可替换，但必须与契约测试对齐。
   「每加一个观测能力就改一次链拓扑」会把机制写死这句话变成空话。
3. **三层 AND**：业务态允许（状态机） + 动作允许（风险闸门 R0-R3） + 工具允许（当前模式白名单）。
   状态机允许不代表动作允许，动作允许不代表当前模式允许。
4. **默认配置即安全**。不配置也不该降低安全性：权限不再自动授予、治理关闭 = 全部拒绝、审计默认落盘、
   观测端点需令牌。想放松必须显式写出来，并被自检记录、被审计留痕。
5. **审计是证据，不是控制输入**。审计链只追加、可校验；后台不应直接拿日志频次去改权限。
   日志被重放、重复上报或注入时，把证据当控制输入会反过来制造拒绝服务。这是方向 C 里
   「只出报告 / 建议单需人批准 / 后台自动收紧不解禁」这条取舍的根因。
6. **承认边界，而不是把边界藏起来**。治理对象是「这一次调用」，不是它产生的效果；
   框架层管不到的地方（工具方法体内自己做 IO、OS 层隔离）明确交给接入方，不假装覆盖了。
7. **文档不撒谎**。设计稿标「尚未实现」、基线标注「未整轮重跑」、三语言结构未统一时不写「契约一致」、
   内部故障强拦截未落地时不写「绝不静默失效」。可复算、可验证、如实标注，比好听的结论重要。
8. **可追溯、可快照、可回滚、可急停**：写前快照三样，审计追加写 + 哈希链，急停取消在途调用。
   被拒绝的调用同样进审计——没有「失败就不记录」的死角。

> 这些不是宣传语，每条都对应一处具体约束或实现；第 5、7 条也在排期决策里直接约束了
> 「降权建议单要做、后台自动收紧不解禁」「产品定位进文档」这类拍板结果。

## 5. 主要能力

| 能力 | 具体形态 |
|---|---|
| **治理链** | 10 环节固定顺序：审计 → 模式白名单 → 意图格式 → Schema → 能力 → RBAC → 风险闸门 → 污点检查 → 快照 → 沙箱 |
| **Agent 注册表** | ID、角色、技能、权限、状态。档案里的"应然权限"与 RBAC 里的"实然权限"可逐项对账，停用/注销立即整员回收 |
| **可追溯** | SHA-256 追加写审计链（有密钥时 HMAC），任何分支（含被拒调用）都留痕，链可校验；另有外锚与锚点副本 |
| **可回滚** | 有副作用的工具执行前留快照 |
| **可观察** | 交付进度看板（13 条本产品真实里程碑）、OpenAPI 3 + Swagger UI、只读 + 人工决策的治理管理接口（默认关闭） |
| **跨语言** | Python / TypeScript SDK；已定稿 wire schema 与错误码口径字典（`contract/`），`SkillResult` wire 结构已统一 |

## 6. 价值：四件事

**能查**——谁、在什么模式、用什么工具、参数是什么、被哪个环节拒的。
**能拦**——R2 转人工审批、R3 直接拒绝、污染会话禁止写与外发。
**能回**——写前快照，改坏了有现场。
**能收**——Agent 停用或注销，权限当场失效，不留后门。

## 7. 目标用户

**适合**：个人开发者与 1~3 人小队；正把 Agent 从"聊天"接到"动真格"（写文件、跑命令、部署）；
技术栈是 Java / Spring Boot；认同"治理应当是固定管线，而不是可拖拽的图形"。

**也适合**：想参考一套「怎么把安全约束做成机制而不是提示词」的工程实践的人——
本项目带有传播工程思想的性质，文档按「问题 → 取舍 → 局限 → 架构与契约 → 验证 → 用法」组织。

**不适合**（当前版本确实做不到）：需要可视化流程设计器的场景；需要多 Agent 协作与任务派发的场景；
需要多租户隔离、账号体系、多人审批的团队协作场景。

## 8. 怎么读这套文档

按「先决定要不要参考，再决定能不能用」的顺序，而不是一上来就跑命令：

| 顺序 | 读什么 | 回答什么 |
|---|---|---|

| 2 | `docs/02`（架构）、`contract/`（已定稿 wire schema 与错误码口径）、`docs/33`（接口契约） | 结构与契约长什么样 |

## 9. 相较以往的改进（历史记录）

1. **主体从"裸字符串"变成"有档案的注册对象"**。v1.0~v1.3 里 `agentId` 只是调用方随手传的字符串，
   权限散落在各处装配代码中，只授不撤。v1.4 引入 Agent 注册表：ID 即身份，注册授予、改档覆盖式、
   停用注销整员回收，接口同时返回应然与实然权限并标记是否一致。
2. **看板从"演示数据"变成"自身真实进度"**。13 条里程碑的时间逐条取自仓库真实文件时间戳，
   打开看板即知这个产品做到哪一步，而不是看一份虚构样例。
3. **工程完备度**：补齐 OpenAPI 3 + Swagger UI（静态资源走本地 webjar，零 CDN，离线可用）；
   core 始终保持零外部依赖。

## 10. 明确不是什么

不是可视化编排平台，也不是多 Agent 协作引擎。编排层（`agenthub.yml` / `@Flow` / 单文件脚本三种形态）
目前是**设计稿，尚未实现**——这一点写在文档里，而不是写进功能列表。
