## 14. 建议补齐顺序

不建议按 Phase 数字顺序继续往后做，因为后面几期都建立在上面五个断点之上：

| 顺序 | 补什么 | 理由 |
|---|---|---|
| 1 | `ModeStateMachine` 接入 starter（`ExecutionContext.mode` 从状态机取，不接受外部传入） | 不补这条，模式白名单的全部价值都建立在一个可被参数绕过的前提上 |
| 2 | `PipelineStateStore` 接入主链（每次决策后 save） | 是断点续跑、门禁留档、审计关联的共同底座 |
| 3 | 快照改为真实落盘 + 恢复入口（或从对外承诺里删掉"可回滚"） | 二者选一，不能既宣称又不做 |
| 4 | 门禁签名换 HMAC + 密钥外部注入 | 成本极低，收益明确 |
| 5 | 审批通道（真实审批人 + 持久化 + 超时拒绝） | R2 是"快慢分离"与"人工闸门"的支点，现在是空转 |

| 7 | ContextBuilder + 提示词层 | 规格中"模型看不到的工具不可调用"依赖它，工作量最大，应在前六项稳定后启动 |

前 6 项都不改变 `ExecutorFactory` 的链顺序，也不改变现有对外契约。

## 25. v1.13 回写：Plan-and-Execute 入口

### 25.1 补上了什么

`PLAN_APPROVAL_REQUIRED` 从 v1.0 就在错误码表里，但一直没有产生方——
"先出方案、人工确认后再动手"只停留在文档。v1.13 把这条链接上：

| 环节 | 落点 | 行为 |
|---|---|---|
| 声明 | `AgentSkill.requiresPlanApproval` → `SkillDescriptor` | 工具显式声明"执行前必须有已批准的计划"；缺省 `false`，存量工具零影响 |
| 提交 | `PlanApprovalService.request(agent, task, summary)` | 生成 PENDING 计划单；同 (agent, task) 的 PENDING/APPROVED 重复提交幂等复用 |
| 审批 | `approve / reject(ticketId, approver, note)` | **禁自批**；REJECTED 不可补批，必须重新提交 |
| 闸门 | `RiskGateDecorator.verifyPlanApproval` | 在命令模板与风险分级**之前**判断；未批准 → `PLAN_APPROVAL_REQUIRED`，业务方法不执行 |
| 审计 | 同一 `AuditStore` 哈希链 | `PLAN_REQUESTED` / `PLAN_APPROVED` / `PLAN_REJECTED`；**摘要不入链** |

### 25.2 三个刻意的取舍

1. **fail-closed**：声明了要求却没装配 `PlanApprovalService` → 拒绝。  
   "忘了接线"不能等价于"不需要审批"，否则一个漏配就静默降级。
2. **按 (agent, task) 生效**：批的是"这个任务的这份计划"，不是"这个人以后都行"；换任务必须重批。  
   防止一次审批被无限复用。
3. **不可补批**：REJECTED 之后 `approve` 直接抛错，必须重新提交。  
   允许"先否再改口"，审批记录就失去意义。

### 25.3 如实标注的边界

- **内存态**：计划单不跨重启留存。重启后闸门仍然 fail-closed（重新提交即可），
  但"跨重启回放"尚未实现。
- **任务级粒度**：批准后该任务内所有声明要求的工具都放行，尚未细化到"单工具/单步骤"。
- **摘要非结构化**：plan 目前是一段文本摘要，不是结构化步骤（PlanArtifact 明细留待后续）。

## 26. v1.14 回写：计划回放与结构化

### 26.1 补上了什么

v1.13 留了两个边界：计划单只在内存、闸门只到任务级。v1.14 两个都收掉：

| 边界 | 本版做法 |
|---|---|
| 重启即丢 | `PlanApprovalStore` 每次状态流转追加快照；`FilePlanApprovalStore` 默认落盘，启动回放 |
| 任务级放行 | `PlanStep(tool, intent)`；计划点名工具后，闸门只放行名单里的工具 |
| 单号撞车 | 回放时把序号推到历史最大值，重启后继续递增 |
| 同毫秒歧义 | `latest()` 先比时间、再比序号，避免 Map 遍历顺序影响"最新单" |
| 坏文件 | 任何无法解析的行直接抛错、拒绝启动，不跳过 |
| 扩大范围 | 已批准后 `request` 幂等返回原单，改用显式 `revise(...)` 生成新 PENDING 单重新审批 |

旧格式（只有摘要）的计划仍按任务级放行，存量调用方零改动。
`revise` 生成的新单待批期间，该任务的所有计划要求工具都会暂停（fail-closed），
不会出现"新范围还没批、旧范围继续用"的空档。

### 26.2 三个刻意的取舍

1. **追加写、不回改**：每次状态流转写一条完整快照。文件会线性增长，但换来"任何时刻的状态都能回放"；
   压缩/归档留给运维侧，不在审批链里做隐式清理。
2. **结构化才收窄**：只有点名的工具才构成范围；一个步骤只写意图、不写工具，不会顺带放行任何工具。
3. **损坏即拒绝**：计划是审批事实来源，读不出来就拒绝启动；"跳过坏行继续跑"等于把已批准计划静默作废。

### 26.3 如实标注的边界

- 追加式存储不自动压缩，状态变更频繁时需要轮转/归档。
- 本地文件防误读不防篡改；生产应放在受控目录，并用审计哈希链对账。
- 计划仍是"人给的方案"，不是自动规划器产出的步骤。

### 26.8 补充实测：计划单按大小轮转 / 归档（已完成，2026-11-05）

**要解决的问题**：v1.14 起计划单默认落盘到 `plans.log`，而每次提交/批准/否决/修订都追加一行，
文件只增不减；长期运行会拖慢启动回放（`load()` 全量读）并让单文件无限膨胀。

**方案（按大小轮转）**：

| 决策点 | 选择 | 理由 |
|---|---|---|
| 触发条件 | 字节数（`maxBytes`），默认 `0` = 关闭 | 与"文件大小"直接对应；默认关闭保证 v1.14 行为不变 |
| 压缩粒度 | 每个计划单只保留**最后一条**快照 | 回放只需要最新状态；中间流转已在审计哈希链里 |
| 归档方式 | 原文件整体移到 `<name>.<millis>.archive`，同毫秒冲突加序号 | 不覆盖历史；归档不参与回放，出问题可人工追溯 |
| 写入安全 | 先写 `.tmp` → 移走原文件 → 原子替换；替换失败把归档移回 | 任一环节失败都不会让主文件消失 |
| 并发 | `save` / `load` / 轮转共用同一把 `ioLock` | 避免"压缩中读到半个文件" |

**配置**：`towndemontower.plan-max-bytes`（字节，默认 `0`）。例如设为 `1048576` 表示主文件超过 1 MiB
时执行一次压缩。

**测试**：

- core `V115PlanRotationTest` 29 项：默认纯追加、压缩、回放一致、极小阈值不丢单、单号续接、
  归档不覆盖、损坏文件 fail-closed 且主文件不变、4 线程并发读写、负阈值拒绝、父目录自动创建。
- starter `V115PlanRotationWiringTest` 8 项：属性绑定、真实产生归档、主文件不超过单数、
  计划单全部可查、审计链仍完整、重启回放、序号不回退。

**测试基线（实测，2026-11-05）**：core 719（690 + 29）、starter 275（267 + 8）、
delivery 219、agents 241，**全仓 1454 / 1454（44 个自运行器，全 rc=0）**；
静态扫描 `files=248 violations=0 warnings=0`。

**已知取舍**（如实标注）：

- 归档文件不会自动清理，需要调用方按运维策略定期归档/删除；本次只解决"主文件无限增长"。
- 阈值按字节、不是按记录数：单条记录约 200 字节时，1 MiB 约容纳 5000 条。
- 压缩会丢"同一单的中间流转"（只保留最新快照）；完整流转仍在审计链，但归档文件不再参与回放。

### 26.9 审计异常数据暂存 / 清理 / 远端补传（已完成，2026-11-05）

**要解决的问题**：`HttpAnchorReplica.push` 同步推、失败即抛。远端一抖，那条锚点就没送出去；
如果进程随后崩溃或副本长期不可用，第三方证据的缺口会一直留在链上。

**六条需求的落点**：

| 需求 | 实现 |
|---|---|
| ① 本地持久化、重启不丢、只留异常数据 | `AuditSyncSpool.capture()` 只在推送失败时写 `.rec`（tmp + 原子改名）；**成功不落盘**，避免把完整数据复制到本地 |
| ② 定时清理 | `cleanup()` 按"保留 7 天 + 64 MiB"双阈值、先删最旧；`AuditSyncRelay` 每 60 秒跑一轮补传 + 清理 |
| ③ 完整数据远端同步 | 正常路径仍走 `HttpAnchorReplica`；失败记录在远端恢复后逐条补传，成功即删除（远端已有，本地不再留） |
| ④ 异常/完整分流 | 暂存目录只存"失败的副本名 + 快照行"；`dead/` 单独隔离；完整数据不经过暂存区 |
| ⑤ 监控与日志 | capture / 补传成功 / 补传失败 / 转 dead / 清理各打一条 `System.Logger`；`Stats` 暴露 11 个计数 |
| ⑥ 重试 | 每轮 `attempts+1`；达到 `max-attempts` 移入 `dead/` **保留不删**，等人工补传 |

**配置（starter）**：`audit-sync-spool-enabled`（默认 `true`）、`audit-sync-spool-dir`（默认 `<audit-file>.spool`）、
`audit-sync-retention-hours`（`168`）、`audit-sync-max-bytes`（64 MiB）、`audit-sync-max-attempts`（`5`）、
`audit-sync-retry-interval-ms`（`60000`）。

**刻意的取舍**：

- 暂存写失败不拖垮治理主链：`AuditAnchor` 内包住 `capture`，只丢一条待补传记录，失败计数由 spool 记。
- 副本从配置里移除时**跳过补传但保留记录**——"改配置"不等于"证据作废"。
- 损坏的 `.rec` 移入 `dead/` 而不是静默跳过，避免"看起来没有待办、实际有坏数据"。
- `dead/` 也受超期清理约束，否则"永不删除"会变成另一种磁盘耗尽。
- 首轮补传延迟一个周期（`initialDelay = interval`），避开启动瞬态。
- 不保证幂等：同一快照失败两次会落两条，宁可重复补传（远端按锚点覆盖，不会造出两条链）。

**测试**：core `V116AuditSyncSpoolTest` 55 项（重启回放、补传成功/失败、dead、双阈值清理、
损坏隔离、并发 capture、可观测计数）；starter `V116SyncSpoolWiringTest` 16 项（本地 HttpServer
先 503 后 200，验证"失败落盘 → 重启不丢 → 恢复补传 → 远端真收到"）。

**基线（实测）**：core 774、starter 291、delivery 219、agents 241，**全仓 1525 / 1525
（46 个自运行器，全 rc=0）**；静态扫描 `files=252 violations=0 warnings=0`。

### 26.10 治理管理接口（已完成，2026-11-05）

**要解决的问题**：v1.9~v1.16 把审批、审计、暂存区的内核都做出来了，但运维只能靠读文件、翻日志。
"能不能接 UI"的结论是：**部分可接**——决策类动作需要后端入口，而模式切换、权限授予、放行 R3
这类高危操作不能只靠一个令牌就开放。本次只补"可接但缺入口"的那一层。

**接口范围（14 个端点，4 组）**：

| 组 | 端点 | 能做什么 |
|---|---|---|
| R3 人工审批单 | `GET /towndemontower/admin/approvals`、`GET /{id}`、`POST /{id}/approve`、`POST /{id}/deny` | 查待办、看影响面/回滚预案、批准或驳回 |
| 执行计划单 | `GET /towndemontower/admin/plans`、`GET /{id}`、`POST /{id}/approve`、`POST /{id}/reject` | 查计划与步骤、按任务/agent/状态过滤、批准或否决 |
| 审计 | `GET /towndemontower/admin/audit`、`GET /audit/verify` | 按 action/关键字/时间过滤查询；校验链完整性并回报锚点落后情况 |
| 同步暂存区 | `GET /sync-spool`、`GET /dead`、`POST /retry`、`POST /cleanup` | 看 pending/dead 与计数、手动补传一轮、手动触发双阈值清理 |

**统一约定**：

| 项 | 做法 |
|---|---|
| 开关 | `towndemontower.admin-api-enabled`（默认 `false`）；关闭时控制器根本不装配，不是"装配了再拦" |
| 鉴权 | 复用 `metrics-token`（`X-Governance-Token`）；未配令牌返回 403 `ADMIN_API_DISABLED`，令牌不匹配 401 `UNAUTHORIZED`，比较用 `MessageDigest.isEqual` |
| 响应 | `ApiResponse{code,message,data,error}`；成功 `code=0`、`error=null`；失败 `code` 与 HTTP 状态一致、`data=null` |
| 错误映射 | `@RestControllerAdvice(basePackages="com.towndemontower.spring.admin")`，只作用于本包，不改写接入方契约 |
| 参数校验 | 分页 `limit` 默认 100 / 上限 500、`offset` 不得为负；非法状态值 → 400 `INVALID_STATUS`；缺 `approver` → 400 `VALIDATION_FAILED` |
| 不解自批 | 审批人等于申请方（agentId / requestedBy）→ 400 `SELF_APPROVAL` |
| 并发/重复决策 | R3 单非 PENDING → 409 `NOT_PENDING`；已否决的计划单补批 → 409 `PLAN_REJECTED`；重复批准/驳回按幂等返回当前单 |

**刻意不开放（写进文档而不是留白）**：

- 模式切换（`OBSERVE` / `DEV_EXECUTION` 等）——一个 HTTP 调用就能改变全局强制力，超出管理面职责。
- 权限授予 / 角色变更——等同于绕过 v1.9 的授权收口。
- 放行 R3、绕过闸门、`--strict` 豁免——会把"人工确认"降级成"点一下"。
- 删除待补传记录 / 改写审计——证据只允许"补传成功即删"，不允许人为抹除。

**实现要点**：

| 文件 | 作用 |
|---|---|
| `spring/admin/ApiResponse` | 统一响应体（record） |
| `spring/admin/AdminGuard` | 令牌校验，fail-closed |
| `spring/admin/AdminParams` | `text()` / `limit()` / `offset()` 三个只做边界校验的取值器 |
| `spring/admin/AdminExceptionHandler` | 统一错误映射（400/401/403/404/409/500） |
| `spring/admin/ApprovalAdminController` / `PlanAdminController` / `AuditAdminController` / `AuditSyncAdminController` | 四组端点 |
| `spring/admin/PlanAdminOperations` | 计划审批的用例层：让 Controller 不直接注入 `PlanApprovalService`，从而不触发 `CP10-R4` |
| `core/audit/AuditSyncSpool#dead()` | 新增只读快照，供 `GET /dead` 使用（不改变补传/清理语义） |

**测试**：starter `V117AdminApiTest` 50 项，起**真实 Servlet 容器**（随机端口）+ `java.net.http.HttpClient`
真调，而不是 MockMvc：三段式验证"默认不装配 → 未配令牌 403 → 配了令牌全功能"。
覆盖鉴权、计划列表/过滤/详情/自批/缺参/批准幂等/否决后补批 409、R3 列表/详情/批准/重复决策 409/驳回、
审计过滤与链校验、`limit` 非法与 `offset` 越界、暂存区统计与手工补传、清理、
以及用本地 `HttpServer` 注入"503 → 200 → 再 503"验证补传与 dead-letter 联动。

**基线（实测，2026-11-05）**：core 774（21 个运行器）、starter 341（17 个运行器）、
delivery 219、agents 241，**全仓 1575 / 1575（47 个自运行器，全 rc=0）**；
静态扫描 `files=263 violations=0 warnings=0`（新增 1 个测试文件，R4 计数仍为 0）。

**过程中的修正**（如实记录）：

- `PlanAdminController` 起初直接注入 `PlanApprovalService`，扫描报 2 条 `CP10-R4`；因 R4 不可豁免，
  改为经 `PlanAdminOperations` 取用例 —— 是"消掉命中"而不是"改判定"。
- 未知路由的 404 **不走** `@RestControllerAdvice`：该 advice 只覆盖 `admin` 包，资源处理器的
  `NoResourceFoundException` 不会被它接管；测试因此只断言 404 状态，统一错误体改用已知接口验证。
- `spring.main.web-application-type=none` 写在测试 `application.properties` 里，属性优先级压不过它，
  必须用**命令行参数** `--spring.main.web-application-type=servlet` 才能起容器。

**边界**：管理接口只做"读 + 人工决策"，不含任何自动化编排；未做 UI（按用户要求后置）；
未做分页游标（全量在内存，`limit/offset` 仅是切片）；令牌无角色区分——拿到令牌即拥有全部 14 个端点的权限。
