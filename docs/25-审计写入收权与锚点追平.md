# 25 · 审计写入收权（I4-b）与锚点追平

> 本版是 I4 的第二刀。I4 上一版（docs/23）解决的是"**链能不能自证没被重算**"（HMAC + 外锚）；
> 这一版解决的是"**记录是谁塞进来的**"（写入口收权），以及外锚每写一条就落一次盘的成本
> （批量追平）。两件事都不改变链的语义，只改变"谁有能力制造证据"。

---

## 1. 收权：拿掉的到底是什么

改之前，`AuditStore` 接口上有一条：

```java
void append(AuditRecord record);   // ← 调用方自带 seq / prevHash / hash
```

`AuditRecord` 是 `public` 的、全字段可传的。于是任何拿到 `AuditStore` 引用的代码都能：

```java
audit.append(new AuditRecord(999, "SKILL_INVOKED", "tool=rm|OK", "GENESIS", "随便写"));
```

存储不做校验地照收。结果分两种，**两种都坏**：

| 伪造者水平 | 结果 |
|---|---|
| 哈希写错 | `verifyChain()` 立刻返回 false —— 一条坏证据把整条链弄脏，运维只能看着"链断了"却分不清是真篡改还是代码缺陷 |
| 按当前算法算对哈希 | 一条**看起来完全合法**的假证据入库，`verifyChain()` 通过，事后没人能分辨 |

第二种是真正的问题：**证据链的可信度不该取决于调用方是否老实**。

### 改成了什么

```java
public interface AuditStore {
    void appendAuto(String action, String payload);   // 唯一写入口
    List<AuditRecord> all();
    boolean verifyChain();
}
```

- 序号 `seq`、前驱 `prevHash`、本条 `hash` 全部由存储自己算；调用方只提供"发生了什么"。
- 原来那条 `append` 变成 `HashChainAuditStore` 的**包内可见**方法 `appendRecord`（保留给落盘实现与同包测试）。
- 越权构造 `AuditRecord` 依然可以，但它**进不了链**——没有写入口，伪造对象就是死物。

### 这条约束的边界（别夸大）

**它是编译期的，不是运行时的。**

- 同包代码（`appendRecord` 只是 `package-private`）、反射、字节码改写，都能绕过去；
- 它挡的是"顺手把记录拼好扔进来"这类**正常代码里的错误用法**，以及"以为自己在写审计、
  其实在写伪证"的误解；
- 挡不住已经拿到进程内执行权的人。后者只能靠进程隔离，不在本框架能力范围内
  （同 docs/17 的结论）。

一句话：**收权提高的是"误用不会发生"，不是"攻击不可能"。**

## 2. 顺手修掉的一个 O(n)

`FileAuditStore.appendAuto` 原来的写法是：

```java
super.appendAuto(action, payload);
List<AuditRecord> all = all();               // ← 整条链复制一份
writeLine(all.get(all.size() - 1));          // ← 只为了拿最后一条
```

`all()` 是 `new ArrayList<>(records)`。也就是说**每写一条审计，就把整条链复制一遍**，
记录越多越慢，而且慢在治理主链上（每次工具调用都要走一次）。

改成父类提供扩展点：

```java
// HashChainAuditStore
protected void onAppended(AuditRecord record) { }   // 内存实现空转
```

`FileAuditStore` 覆写它，直接拿到刚写的那条去落盘。O(n) 变 O(1)。

## 3. 锚点追平：默认不变，批量要显式开

### 为什么默认仍是"每条追平"

锚点（docs/23 §4）记的是"日志一共 N 条 + 第 N 条的哈希 + MAC"。它挡的是**尾部截断**：
删掉最后几条"不该被看见"的记录时，链本身依然自洽，只有链外的锚点会露馅。

**锚点一旦落后，落后的那几条被删就没人能发现。** 所以：

> `audit-anchor-batch` 的默认值是 **1**（每条都追平）。
> 这不是"还没优化"，是**刻意不为吞吐让步**——按"默认只变严不放松"的口径，
> 把默认值改成 16 就是一次静默的证据强度降级。

### 配置项

| 配置 | 默认 | 含义 |
|---|---|---|
| `towndemontower.audit-anchor-batch` | `1` | 每 N 条追平一次；`<=1` 一律按 1 处理 |
| `towndemontower.audit-anchor-interval-ms` | `0` | 距上次追平超过 T 毫秒也追平一次；`0` = 不按时间 |
| （关闭行为） | 自动 | 容器关闭时调 `flushAnchor()`，见下 |

两个条件是"先到者"，所以批量模式下：

- 高频写入 → 每 N 条追平，落后的条数有上限；
- 低频写入（几分钟才一条） → 靠 `interval` 兜底，不会永远卡在"未入锚"。

### 退出必须追平

```java
@Bean(destroyMethod = "flushAnchor")
public AuditStore townDemontowerAuditStore(...)
```

不追平的后果很具体：进程正常退出时最后那几条永远在锚点之外，而**滚动重启、缩容**
恰恰是最常见的"日志尾部消失"场景——不是攻击，是运维动作，但结果是证据链出现一个
无人知晓的缺口。`HashChainAuditStore.flushAnchor()` 是空实现，所以两种存储都能挂同一个
`destroyMethod`，装配处不必分支。

### 配错不会静默关掉锚点

`audit-anchor-batch=0` 或负数会被 `setAuditAnchorBatch` 夹到 1，**不是**"关掉追平"。
同理 `audit-anchor-interval-ms` 负数夹到 0。写错配置的默认走向是"更严格"，不是"更宽松"。

### 可观测

- `/towndemontower/integrity` 增加 `auditAnchorRecords`（锚点覆盖到第几条）、
  `auditAnchorLag`（还差几条）、`auditAnchorBatch`（批大小）。
- `lag > 0` 在批量模式下是**正常**状态；持续单调上涨才说明追平跟不上写入。
- 自检新增 `AUDIT_ANCHOR_BATCHED`(**INFO**)：开了批量化就把它写进启动日志，
  代价写在启动日志里而不是只写在文档里。

## 4. 锚点校验的两个增强

### 4.1 位置哈希：落后期间前缀仍受保护

旧逻辑只比"总条数 + 末条哈希"，且只在 `records == anchor.records()` 时比对末条。
一旦开了批量化（`records > anchor.records()`），**什么都不检查**——前 N 条可以整段重写。
这在批量模式下等于把"防重算"打了个洞。

现在：

```
锚点记 (N, hash@N)
 → 扫描时取回第 N 条的哈希
 → records < N           ⇒ 截断，拒绝启动
 → hash@N ≠ 锚点里的 hash ⇒ 改写，拒绝启动
 → records > N           ⇒ 允许（这是落后的正常态），但前缀已被验证
```

落后期间丢掉的只是"尾部那几条被删的可见性"，不再丢掉整个前缀。

### 4.2 日志文件被整体删除

旧逻辑把锚点校验放在 `if (Files.exists(file))` 里面。于是最省事的攻击是
**把日志文件删掉**：文件不存在 → 跳过校验 → 以 `(0, GENESIS)` 重新盖一个锚点 →
之前的证据全部无声消失，链还是"完好"的。

现在校验放在 `if` 外面：文件没了就是 `records=0`，锚点说以前有 N 条，一样按截断拒绝。

### 运维后果（重要）

> **轮转、清理、迁移审计日志时，必须把同级的 `.anchor` 文件一起删。**
> 只删日志、留下锚点，启动会直接拒绝（"日志被截断：锚点记录 N 条，实际只剩 0 条"）。

这是有意的 fail-closed：让"证据被丢弃"这件事必须是一次**显式动作**，而不是顺手一删。
升级说明里要写清这一条——它会让"以前习惯性删日志"的脚本第一次失败。

## 5. 测试

`V19AuditSealTest`（core，56）：

| 组 | 覆盖 |
|---|---|
| 收权 | 接口方法集合里没有 `append`；只有一个 `void` 写方法；`appendRecord` 非 public 且仍然存在；裸构造记录不入链 |
| 唯一写入口 | `seq` 连续、`prevHash` 接前条、哈希由存储算出（与 `AuditCrypto.chain` 对得上） |
| 默认不变松 | `anchorBatch==1`、`anchorLag==0`、锚点条数 == 文件条数 |
| 批量（条数） | 满 3 条才追平、落后量递增、`flushAnchor` 幂等、重开不误报 |
| 批量（时间） | 未超时不追平、超时后追平 |
| 落后期间 | 前 4 条整段重写并重算哈希 → 仍被"改写"拒绝 |
| 批量的代价 | **落后窗口内删尾部确实发现不了**（如实断言，不粉饰）；越过锚点立刻被发现 |
| 文件删除 | 删日志留锚点 → 拒绝启动，原因指向截断 |
| 空基线 | 空日志重开不误报 |

## 6. 已知代价与未覆盖

| 项 | 状态 | 说明 |
|---|---|---|
| 收权是编译期约束 | **代价** | 同包代码与反射仍可写；运行期隔离不归本层管 |
| 批量模式丢尾部可见性 | **代价** | 最多 `batch-1` 条被删不可见；默认 1 时不丢 |
| 锚点与日志同机 | **已解**（v1.10 / I4-c） | 见 [26 · 锚点副本与回滚检出](./26-锚点副本与回滚检出.md)；不配副本时仍是敞口，自检报 `ANCHOR_SINGLE_COPY` |
| 密钥由环境变量提供 | **未解** | 没有 HSM/KMS 托管，密钥泄露即锚点 MAC 失效 |
| `appendAuto` 仍可写任意 action/payload | **边界** | 进程内调用方"写什么"依然自由；能约束的只有"怎么算哈希" |
| 写入吞吐的真实上限 | **未测** | 没有压测数据；批量模式的价值目前只有机制，没有数字 |
